# 记忆、会话与框架归属

这份文档回答四个问题：Agent 怎么"记住"、上下文怎么压缩、多轮对话存在哪、框架哪些是自己写的。

---

## 0. 先把三个概念分开（混淆会导致所有设计都错）

| 概念 | 是什么 | 生命周期 | 存哪 |
|---|---|---|---|
| **会话（Session/Thread）** | 一次持续的对话，有 ID | 天~月 | MySQL 业务事实 + PG checkpoint |
| **上下文（Context Window）** | 这一次请求**真正喂给模型**的 token 串 | 一次请求 | 不存在，请求结束即释放 |
| **记忆（Memory）** | 跨会话保留、可被检索复用的信息 | 周~永久 | PG + 向量 + Redis |

**核心关系：上下文是会话与记忆的「投影」，不是它们本身。**

这一句是整个设计的地基。它推出两条铁律：

1. **存储永远全量，压缩只发生在渲染层。** 历史消息一条不删；所谓"压缩"只是决定这次请求带哪些、带多细。
2. **压缩必须可逆。** 只要原文还在库里，压缩策略就可以随便试错、随时换、出问题能回溯。反过来，如果压缩时就把历史改写了，就再也回不去了。

> 很多项目做错的地方：把"压缩"实现成"删除旧消息 + 存一条摘要"。
> 一旦摘要漏了引用编号或权限标记，后续所有回答都是错的，且无法追溯。

### 0.1 append-only 的确切边界：只有一张表是纯追加

"会话只追加"这个说法方向对，但**不能说成"整个会话系统只 append"**。四张表的写入语义完全不同：

| 表 | 写入语义 | 说明 |
|---|---|---|
| `chat_message` | **纯 append**，不改不删 | 唯一严格 append-only 的表。user / assistant 各一条 |
| `chat_turn` | 每轮 append 一条 | 但不是"累积"，是一轮一个独立聚合行 |
| `langgraph_checkpoint` | append + 链式引用 | 每步新增一行，通过 `parent_id` 串成链；**不覆盖前一行** |
| `session` | **会被 update** | `last_active_at`、`status`、`title` 都要改 |

所以准确表述是：**"消息是不可变的追加日志，会话元信息与图状态是可更新的。"**

三条例外必须显式处理：

1. **assistant 消息什么时候落库**：流式生成中途失败，不能落半条。做法是生成完成才写 `chat_message`，中途失败写 `chat_turn(status='failed')` 并从上下文里排除——**半成品不能进历史，否则下一轮会把它当成已说过的话**。
2. **压缩产物绝不写回 `chat_message`**：摘要写回就等于改写历史，append-only 立刻被破坏。摘要只存 `trace.context_snapshot`。
3. **合规删除用墓碑**：真需要删时置 `deleted_at` + 内容脱敏，保留 `id` 与 seq 以维持链完整；物理删除只走离线审计流程。

### 0.2 不是"知识的投影"，是三个来源各自投影后拼接

这里有个容易含糊的地方，含糊了会导致归因做不了。

模型看到的那段上下文，实际由**三个不同真相源各自投影**后拼成：

```
上下文 = 系统指令
       + 【会话投影】历史消息 ── 按 token 预算截断 + 摘要（时间维度）
       + 【知识投影】本次召回 evidence ── 按相关度筛选 top-K（空间维度）
       + 【记忆投影】语义/情景记忆 top-3
       + 本轮 user message
```

| 投影 | 来源 | 有损方式 | 失效表现 |
|---|---|---|---|
| 会话投影 | `chat_message` | 截断 + 摘要 | 忘记上下文、重复提问、指代错乱 |
| **知识投影** | `kb_chunk`（**独立真相源**） | 检索筛选 | 答不出、答错、引用不存在 |
| 记忆投影 | `mem_*` | 向量召回 + 过滤 | 风格不对、重复误解 |

**关键区别**：知识不是"会话的投影"，知识库是**独立的、不随会话变化的真相源**；模型看到的只是它本次被召回的一小部分。把两者混成一个"投影"，就会出现归因错误——比如回答错误的真实原因是**召回没召回**（知识投影问题），却去改压缩策略（会话投影问题），越改越差。

这也正好对上 `03-评测体系.md` 的归因分类：E2/E3（召回类）属于知识投影，E6（上下文丢失）属于会话投影，两者修复手段完全不同。

### 0.3 append-only 的真正红利：投影层可以自由重算

大多数人把不可变日志理解成"为了留档/审计"。但对 Agent 来说，它的价值在别处：

> **因为历史不可变，所以"怎么给模型看"这件事可以被无限次重新决定。**

具体红利有三个：

- **压缩策略可以热切换**：从"最近 6 轮原文"改成"最近 3 轮 + 结构化摘要"，改完立即对所有历史会话生效，不需要数据迁移。
- **可以离线重放对比**：拿历史会话跑 A/B 两种投影策略，直接比较 faithfulness。这是评测体系能成立的前提——**如果历史被改写过，就无法重放**。
- **出问题可回溯**：用户投诉"你上次说的不是这个"，能查到当时真正喂进去的是什么（`context_snapshot`）。

反过来，一旦把压缩结果写回存储，这三条全部失效。

### 0.4 一个必须防的性能陷阱：不要每轮重算全量摘要

append-only 的代价是"每轮都要重新投影"。如果天真实现成"每轮把全部历史重新摘要一遍"，成本是 **O(n²)**——第 10 轮摘要 9 轮，第 20 轮摘要 19 轮。

正确做法是**滚动摘要 + 水位缓存**：

```
summary_cache(thread_id, upto_seq, summary_text, covered_msg_ids)
```

- 只对"上次摘要之后新增的轮次"做增量合并
- `upto_seq` 记录摘要覆盖到哪条消息，是这个缓存的唯一 key
- 缓存丢失可从 `chat_message` 全量重建（因为原文永远在）——**这正是 append-only 兜住的地方**

## 1. Memory 三层

配置在 `domain.yaml`，两个域用法不同：

```yaml
# 知识域
memory: { working: true, semantic: true, episodic: false }
# 排障域
memory: { working: true, semantic: false, episodic: true }
```

| 层 | 内容 | 写入时机 | 存储 | 读取方式 |
|---|---|---|---|---|
| **工作记忆** | 当前 thread 的最近对话 + 当前任务中间状态 | 每轮 | Redis（热，TTL 2h）+ checkpoint（冷，恢复用） | 直接拼进上下文 |
| **语义记忆** | 用户偏好、常查主题、术语习惯、所在部门语境 | **异步、抽稀**（会话结束 / 每 N 轮） | PG `mem_semantic` + 向量 | 按 `user_id` 过滤后向量召回 top-3 |
| **情景记忆** | 历史相似案例（已完成的历史工单 + 其结论） | 任务成功结束后 | PG `mem_episodic` + 向量 | 按症状向量召回 top-3 |

### 1.1 工作记忆

不引入新概念，就是**最近 K 轮原文 + 当前图状态**。

```
工作记忆 = 最近 6 轮完整问答（原文）
         + 更早轮次的滚动摘要（见第 2 节）
         + 当前 thread 的任务中间变量（如"已排除的假设""已确认的订单号"）
```

"任务中间变量"容易被忽略，但在排障域是刚需：假设树走到第 3 层时，必须记得"假设 A 已被证伪"，否则会绕回来重复验证。这**不是对话历史**，是图的状态，存在 checkpoint 里。

### 1.2 语义记忆（知识域在用）

只记三类，不记一切：

1. **偏好**："我一般看制度类文档""回复尽量短" → 影响回答风格
2. **常用实体**：常查的部门、系统名 → 用于查询改写时的消歧
3. **纠错记录**：用户说"不对，我问的是报销不是付款" → 避免重复误解

**明确不记**：用户的每一次提问原文（那是会话，不是记忆）。

### 1.3 情景记忆（排障域在用）

排障域的核心价值就靠它：`build_hypotheses` 生成候选根因时，先召回 3 条相似历史工单，用它们的真实根因作为先验。

```
症状文本 → 向量召回历史工单 top-3
        → 提取其 root_cause + 验证过的证据模式
        → 作为先验概率喂给 build_hypotheses
```

这条链路是 `F2（假设缺失）` 的主要修复手段，在 `03-评测体系.md` 里有对应归因项。

**只存成功的工单**。存失败案例会把错误先验带进新任务——这是情景记忆最危险的污染源。

### 1.4 遗忘机制（不做的话，记忆会变成负担）

| 手段 | 规则 |
|---|---|
| TTL | 工作记忆 2h；语义记忆 180 天无命中即降权 |
| 容量上限 | 单用户语义记忆 ≤ 50 条，超出按"最近命中时间 × 置信度"淘汰 |
| 置信度衰减 | 每次被使用且未纠错 → +0.05；被用户纠错 → 直接置 0 并标记 |
| 冲突合并 | 同类偏好新值覆盖旧值，旧值转 `superseded` 保留审计，不物理删 |
| 可撤销 | 提供"我记错了"入口，用户可查看并删除自己的记忆条目 |

### 1.5 三个必须防的坑

| 坑 | 后果 | 防法 |
|---|---|---|
| **污染检索** | 用户偏好写进 `kb_chunk`，导致文档召回出现"张三喜欢简答" | 记忆**独立命名空间**，永不进知识库索引；召回时两路合并而非同库混检 |
| **写放大** | 每轮都抽取写入，成本与延迟都爆 | 异步 + 抽稀：会话结束、或累计 5 轮、或出现明确纠错信号才写 |
| **跨用户泄漏** | A 的偏好被 B 命中 | `namespace = user:{id}`，向量检索**强制带 namespace 过滤**，与权限同一原则 |

## 2. 上下文压缩

### 2.1 触发时机（分级，不是一刀切）

| 触发 | 阈值 | 动作 |
|---|---|---|
| **工具结果超长** | 单次返回 > 1500 token | 立即压缩（最高优先级） |
| **上下文水位** | 占模型窗口 65% | 启动对话摘要 |
| **轮次** | 超过 12 轮 | 强制滑窗 |
| **证据过多** | 召回 + 图扩展后的证据 > 8 条 | 按相关度保留 top-5，其余只留引用骨架 |

**顺序很重要：先压工具结果，再压对话历史，最后才动检索证据。**
因为工具结果通常最冗余（一个 SQL 返回 200 行），压它的收益最大、信息损失最小；而检索证据一旦压掉，回答就没依据了。

### 2.2 四层压缩手段

| 层 | 手段 | 压缩比 | 信息损失 |
|---|---|---|---|
| L1 | **工具结果结构化**：SQL 结果保留列名 + 前 20 行 + 聚合统计，明细转"共 N 行，明细见 artifact" | 10~50x | 低（明细可在 artifact 里取回） |
| L2 | **对话滑窗 + 滚动摘要**：最近 6 轮原文，更早的合并成一段结构化摘要 | 5~10x | 中 |
| L3 | **证据压缩**：每条证据只留 `doc_id + 段落标题 + 命中句 ± 1 句` | 3~5x | 中高（需保证引用可回溯） |
| L4 | **可重建内容丢弃**：原文已在 PG 里，上下文里不留全文，只留引用 | 最高 | 无（可重建） |

L4 是 RAG 场景特有的红利：**凡是能从库里按 id 重新取回的内容，都没必要占用上下文。**

### 2.3 压缩的三个 RAG 特有陷阱

这三个是"通用对话压缩"不会遇到、但 RAG 一定会踩的：

**陷阱一：摘要吃掉引用编号。**
压缩后模型看到的是摘要文字，引用编号 `[1][2]` 丢了，生成时就会编造引用。
→ **压缩时引用必须结构化保留**：摘要里以 `{eid}` 占位符形式携带证据 id，最终渲染时再还原成 `[1][2]`。引用不是文本，是数据。

**陷阱二：摘要吃掉权限标记。**
某文档在会话中途被撤销授权，但摘要里还留着它的内容，模型继续引用 → 越权。
→ **压缩产物必须携带 `acl_epoch`**（权限版本号）。渲染前比对，epoch 变了就重新过滤，而不是信任摘要。

**陷阱三：摘要不可逆，评测无法回溯。**
评测要复现"当时模型看到了什么"，如果只存摘要，就永远复现不了。
→ **压缩产物与原文快照都落 trace**：`trace.context_snapshot` 存实际喂进去的压缩结果，`trace.source_refs` 存被压缩掉的原始 id。两者都要能查。

### 2.4 压缩质量也要被评测

压缩不是"能跑就行"，它直接影响 faithfulness。所以进评测集：

| 指标 | 定义 | 目标 |
|---|---|---|
| 压缩后引用准确率 | 压缩前后引用一致性 | ≥ 98% |
| 压缩后答案一致性 | 同问题压缩前后答案的语义相似度 | ≥ 0.92 |
| 关键信息保留率 | 人工标注的关键句在压缩产物中是否留存 | ≥ 95% |

**第 3 个指标最能说明问题**：很多系统压缩后指标看着没掉，其实是"掉的那些问题本来就答不对"。只有人工标注关键句，才知道压缩到底压掉了什么。

## 3. 多轮对话怎么存

### 3.1 四张表，职责不同

```sql
-- MySQL（业务事实，Java 读写）
session        (id, user_id, domain, title, created_at, last_active_at, status)
chat_message   (id, session_id, seq, role, content, created_at)   -- 全量，永不删改
chat_turn      (id, session_id, user_msg_id, assistant_msg_id,
                trace_id, input_tokens, output_tokens, latency_ms,
                citation_json, acl_epoch)                          -- 一次问答的聚合视图

-- PG（图状态，Python 读写）
langgraph_checkpoint (thread_id, checkpoint_id, parent_id, state_jsonb, created_at)
```

| 表 | 给谁看 | 为什么不合并 |
|---|---|---|
| `chat_message` | 用户、审计 | 全量原文，不可变；压缩策略变化不影响它 |
| `chat_turn` | 分析、评测、成本核算 | 一轮问答的聚合（token/延迟/引用），按 `trace_id` 关联观测；按消息粒度存会重复 |
| `langgraph_checkpoint` | 机器恢复 | 图的中断状态（HITL 暂停点、假设树中间态），**业务消息表达不了** |

**为什么必须双写（消息 + checkpoint）**：

- 只存 checkpoint → 无法按用户/时间检索、跨图版本迁移困难、用户侧展示要反序列化图状态
- 只存消息 → HITL 中断后无法恢复到"图暂停的那个节点"，只能从头重跑
- 双写，**以消息为业务准、以 checkpoint 为恢复准**，`thread_id` 是两者的连接键

### 3.2 一轮问答的完整落库时序

```
用户提问
  → Java 写 chat_message(user) + 建/复 session
  → REST 调 agent（带 thread_id）
  → Python: 拼上下文（Redis 热窗口 + checkpoint 状态 + 记忆召回）
  → 跑图 → 每个节点落 checkpoint
  → 流式返回，结束后写 chat_message(assistant)
  → 异步：写 chat_turn（token/延迟/引用快照/acl_epoch）
  → 异步：抽稀写记忆（若触发条件满足）
```

**注意 `chat_turn.acl_epoch`**：记录这一轮回答时的权限版本。当文档失权后回看历史会话，靠它判断"这个引用当时是否合法、现在是否已失效"。

### 3.3 历史会话与权限的交叉（容易漏）

用户在 3 个月前问过一个问题，当时引用了文档 D，现在 D 的权限被撤销了。历史会话怎么展示？

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 原样展示 | 保留原答案与引用 | ❌ 等于开了个后门：撤销权限后还能从历史里看到内容 |
| B. 整条隐藏 | 会话直接删掉 | ❌ 过度，用户会认为数据丢了 |
| **C. 保留骨架 + 标记失权**（采用） | 答案文字保留，引用条目标记"原文已失效"，点击不可跳转、不可展开 | ✅ 既合规又可解释 |

实现上就在渲染时比对 `citation.acl_epoch` 与文档当前 `acl_epoch`，不一致则置灰。

**这条是"权限贯穿全链路"的第 8 个出口**，`05-权限设计.md` §5 的表格里完整列了八个出口，第八条就是本节的场景。

### 3.4 Redis 的角色

只做热数据，不做事实：

| 用途 | Key | TTL |
|---|---|---|
| 工作记忆窗口 | `wm:{thread_id}` | 2h |
| 会话锁（防同 thread 并发跑图） | `lock:thread:{thread_id}` | 30s（续租） |
| 主体属性缓存 | `subject:{user_id}` | 见 `05-权限设计.md` |
| 语义缓存 | `sem:{domain}:{acl_epoch}:{q_hash}` | 1h |

**注意语义缓存的 key 必须含 `acl_epoch`**，否则权限变更后仍会命中旧答案。

## 4. 框架归属：哪些是复用，哪些是自己写的

这是面试高频问题，答案必须分层，不能笼统说"我用了 LangGraph"或"我自己写的"。

| 层 | 归属 | 具体 | 为什么 |
|---|---|---|---|
| 模型 | **外部调用** | 商用/开源 LLM API | 不自训，不是本项目命题 |
| 编排内核 | **复用 LangGraph** | 状态图、checkpoint、`interrupt`、`Command(resume)` | 中断恢复与任意点重放自研成本极高，且它是事实标准 |
| 存储后端 | **复用接口 + 自写实现** | `PostgresSaver` / `RedisSaver` | checkpoint 存在自己的 PG 里，schema 自己定 |
| **Agent Runtime** | **自研** | 工具注册表、Domain Pack 加载、记忆子系统、护栏、观测埋点、评测适配器 | **这才是项目的核心资产**，也是 JD 第 4 条要考的东西 |
| 领域逻辑 | **自研** | 两张状态图、检索线、图谱构建、假设验证、权限求值 | 业务价值所在 |
| 评测 | **复用 + 自研** | RAGAS/DeepEval 做指标与 CI，**归因分类法自研** | 通用指标谁都能跑，归因才是差异化 |
| 观测 | **复用标准** | OpenTelemetry + Langfuse | 不重造轮子 |

### 4.1 为什么不用 DeepAgents 这类高层封装

`02-技术选型.md` 已经否决过，这里补充完整理由：

| 理由 | 说明 |
|---|---|
| **黑盒与考点冲突** | DeepAgents 内置 planning/subagent/文件后端，是黑盒。而 JD 第 4 条要考的正是"你理解 planning 和 multi-agent 怎么实现"——黑盒讲不出机制 |
| **控制流不匹配** | 它假设的是"长任务 + 文件系统读写"的编码/研究场景；本项目是"有权限约束、有停止条件、要 HITL 审批"的业务流程，停止条件要精确可控 |
| **可观测性缺口** | 内置封装会吞掉中间步骤，而本项目要求每个假设的验证过程都能回放 |
| **定位不同** | 它是 CLI/编码 Agent 的运行时；本项目是**服务型业务 Agent**，部署形态、并发模型、权限模型都不同 |

**但有一条要学它**：DeepAgents 和各类 harness 的**上下文工程规范**（分层指令、压缩策略、状态交接）是宝贵的经验总结。本项目借鉴其思想，不引入其代码——**思想可以复用，运行时不能。**

### 4.2 harness 是什么，为什么"不直接套"

`harness` 不是某个产品，是**围绕模型的那层工程基础设施**（指令、工具、环境、状态、反馈）。它有几个流派：

| 形态 | 典型 | 与本项目的关系 |
|---|---|---|
| CLI 编码 Agent 的 harness | Claude Code / Codex / DeepSeek 的工程实践 | **借鉴思想**：单一大指令必然失败 → 指令分层；上下文必然溢出 → 分级压缩；跨会话必失忆 → 进度交接文件 |
| 通用 Agent 框架 | LangGraph / AutoGen / CrewAI | **复用 LangGraph 做编排** |
| 本项目 Runtime | 自研 | 服务化、双域、权限内建、可评测 |

一句话口径：

> 编排内核用 LangGraph，因为中断恢复不该自研。
> Runtime 自己写，因为工具治理、记忆分层、双域抽象、评测归因才是这个项目要证明的东西。
> harness 那套工程规范我借鉴了思路（指令分层、压缩分级、状态交接），但它是给"写代码的 CLI Agent"设计的，跑业务 Agent 服务时部署模型和权限模型都对不上。

## 5. 面试口径

**Q：你的 Memory 机制是怎么设计的？**
> 分三层：工作记忆是最近 6 轮原文加图的任务中间态；语义记忆是用户偏好，异步抽稀写、带遗忘；情景记忆是历史成功工单，只在排障域用，做假设生成的先验。
> 一个关键原则：**上下文是会话的投影，不是会话本身**。所以存储全量不删，压缩只在渲染层做，随时可回滚、可复现。

**Q：上下文怎么压缩？**
> 按 L1 到 L4 分级：先压工具结果（收益最大、损失最小），再压对话历史，最后才动检索证据。因为证据一压掉，回答就没依据了。
> 有三个 RAG 特有的坑：摘要会吃掉引用编号、吃掉权限标记、导致评测无法复现。所以压缩产物要结构化保留 `eid` 和 `acl_epoch`，并且和原文快照一起落 trace。
> 压缩本身也进评测：引用准确率 ≥98%、答案一致性 ≥0.92、关键句保留率 ≥95%。

**Q：多轮对话怎么存？**
> 四张表职责分开：`chat_message` 全量原文不可变，`chat_turn` 是一轮问答的聚合（token、延迟、引用快照、权限版本），checkpoint 存图的中断状态。
> 必须双写，因为业务消息表达不了图的中断点——HITL 暂停后要能恢复到那个节点，不能从头跑。
> 还有一条容易漏的：历史会话回看时，已失权的引用要置灰而不是原样展示，靠 `acl_epoch` 比对判断。这是权限的第八个出口。

**Q：Agent 是你自己写的还是用现成框架？**
> 分层：编排内核是 LangGraph，中断恢复和任意点重放我不自研；存储后端是自己实现的；Runtime 层的工具注册表、Domain Pack、记忆、护栏、评测适配器全部自研。
> 我没用 DeepAgents 这类高层封装，因为它内置的 planning 和 subagent 是黑盒，而我要讲的恰恰是这些机制怎么实现；而且它的控制流假设是长任务读写文件，和"有权限约束、要审批"的业务流程对不上。
> 但它的上下文工程规范我借鉴了——思想可以复用，运行时不能。
