### 1.1 这一版语料做了什么

上一轮的结论是「**管线式在 18 个 chunk 上已经触顶，Agentic 的 rewrite 没有触发理由**」。
根因不是 Agentic 没用，是语料太小、太散，问什么都一次能召回。

所以本轮按真实业务域重造了语料：

| 维度 | 之前 | 现在 |
|---|---|---|
| 文档数 | 7 | 48（旧 7 + 新 41） |
| chunk 数 | 21 | 293 |
| 字符数 | ~1.2 万 | ~5.2 万 |
| 业务域 | 4 个制度主题 | 人事/财务/采购/仓储/订单/IT/客服 七域 |
| 受限文档 | 1（D10.9） | 18（D10 / D10.9 / payroll 三档） |
| 黄金集 | 22 | 198 |
| 越权集 | 6 | 82 |

**语料设计的三条刻意安排**：

1. **有跨文档才能答的问题**：出差流程在 HR 制度、住宿金额在财务细则；远程办公在 HR 制度、
   数据密级在 IT 规范。这类题（`cross_doc`）才是 Agentic rewrite 该发力的地方。
2. **有同义不同词的问题**：问「超时没发货」而文档写「超时未发货 → E-4001」，
   考的是召回而不是字符串匹配。
3. **有正向看不见、也有反向看不见**：D20（分公司/外包）看不到总部文档（82 条越权题在测的）；
   而「总部看到的反而更少」这一向**还没有语料**——现有 15 份 ACL 全是 `D10 / D10.9 / payroll` 三档收窄，
   没有一份是只对 D20 开放的。补这一类要先造 D20 专属文档，列入阶段 A 后续。

## 3. 接下来 4~6 周做什么

约束：**单人、1~2 个月、砍掉 GraphRAG**。所以顺序只按一条原则排：
**先让已有的东西可被验证，再让没做的部分能演示。**

### 阶段 A（本周，收口）— 语料与评测

| # | 事项 | 验收 |
|---|---|---|
| A1 | 语料 v2 + 评测集 v2 入库、跑完双图对照 | 报告落 `eval/report-v2.md` |
| A2 | 修掉本轮暴露的召回缺陷（`@@@` 合取 → `\|\|\|` 析取） | Recall@50 = 1.0，单测全绿 |
| A3 | 修掉「模型抄 `{eid}` 占位符 → INTERNAL」 | 该场景降级为拒答而非 500，有单测 |
| A4 | 提交 + 推送，README 状态段更新 | `git log` 可追 |
| **A5** | **修「答案已发出却判拒答」**：`_finish_reason` 在已发正文+引用时落 `answered` + `degraded=budget_truncated`；deadline 检查点前移到"下一轮检索前" | 同一批 82 条，协议正确率追平内容命中率（±2pt），`abstained 且正文非空` 计数归零 |

**为什么先收口**：所有后续工作（M4 排障域）都要复用这套评测框架。
评测框架带着「有 0 召回 bug」的状态往下走，后面所有数字都不可信。

### 阶段 B（第 1~2 周）— M4 排障域最小闭环

排障域是**广度**的证明（对应 JD 第 4 条），但不需要做全。最小闭环只做五件事：

| # | 事项 | 关键决策 | 验收 |
|---|---|---|---|
| B1 | 诊断图：`analyze_symptom → build_hypotheses → gather_evidence → evaluate → propose_action` | 复用 Runtime 图内核，不新写状态机 | 5 节点可跑通一条真实订单排障 |
| B2 | 工具注册表接入 5 个只读工具（订单查询 / 库存快照 / 物流轨迹 / 支付流水 / 操作日志） | 工具 schema 用 JSON Schema 校验，超时 3s、重试 1 次 | 每个工具有单测 + 错误回灌 |
| B3 | SQL Guard 四道闸（只读账号 / 语句白名单 / 强制 limit / 禁止 DDL） | 用真实业务库的只读副本，不造 mock 表 | 注入 5 条危险 SQL 全部拦截 |
| B4 | HITL：写动作前 `interrupt` + checkpoint + 审批回灌 | 审批只在「执行动作」前，不在诊断过程中 | 一次中断-恢复全链路可回放 |
| B5 | 回放评测集 30 条（历史工单格式） | 先做 30 条，跑通再加到 100 | Root Cause Top-1 ≥ 60% |

**这一阶段的取舍**：不做实时日志流、不做真实写操作、不做多轮追问。
理由——排障域的价值是证明「工具调用 + 假设验证 + 人工确认」这套机制成立，不是覆盖全部故障类型。

### 阶段 C（第 3 周）— A2A 跨域

| # | 事项 | 验收 |
|---|---|---|
| C1 | 两个 Agent Card + Task 状态机（submitted/working/input-required/completed） | Card 可被另一端发现 |
| C2 | 知识域 Agent 在处理履约类问题时发 Task 给排障域 | 一次请求跨 2 个进程 |
| C3 | 跨进程 trace 透传 + 一条完整回放 | trace 树能串起来 |
| C4 | 对端宕机时的降级（超时 → 单域作答 + degraded 标记） | 拔掉排障域，知识域仍可用 |

**为什么只做「一个方向」的 A2A**：双向互调会让状态机复杂度翻倍，而演示价值几乎不变。
单向（知识→排障）已经足够证明「域边界即服务边界」。

## 4. 已知缺陷（按优先级）

| 优先级 | 缺陷 | 影响 | 处理时机 |
|---|---|---|---|

| ~~P0~~ | ~~`max_steps=8` 偏紧，改写回环实际要 3 步（rewrite→retrieve→grade），第 9 步 verify 撞预算 → 答案已生成却被标 abstained~~ | ~~正确率被低估~~ | **已改为 10** |
| ~~P0~~ | ~~判定器 `classify` 的 `max_tokens=512` 在思考链中途截断，原始输出不是 JSON → `grade_verdict` 为空 → 一律拒答~~ | ~~agentic 正确率塌到 30.5%~~ | **已改为 1024，并在 `grade_verdict is None` 时不再直接拒答** |

## 5. 砍掉的东西（以及为什么敢砍）

| 砍掉 | 理由 | 面试怎么答 |
|---|---|---|
| **GraphRAG（M3）** | 建图成本高（每篇文档一次 LLM 抽取 + 社区摘要），在 48 份文档上收益测不出来；要测出来得先到 500 篇量级 | 「我做完 M1/M2 的对照后发现，多跳问题只占 7%，且现有混合检索 R@10 已 0.98，建图在这个规模上无法证明收益。所以我把它砍了，把时间给了排障域——那边是 JD 明确要求的能力。」 |
| 多模态解析（图片/表格深解析） | 与「双域」主线无关 | 定位是知识域深度，不是解析器竞赛 |
| 多租户 / 权限管理后台 | ACL 已在检索层证明，后台是 CRUD 体力活 | 权限的关键在求值位置，不在管理界面 |
| MinerU 云端兜底 | 本地 Docling 已覆盖 95%+，云端解析引入外部依赖 | 降级方案保留代码，不投入联调时间 |
| 实时日志流 | 排障域用「历史工单回放」已能证明假设验证机制 | 真实系统里日志是拉取不是推送 |
