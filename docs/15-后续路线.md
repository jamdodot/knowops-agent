### 1.1 这一版语料做了什么

上一轮的结论是「**管线式在 18 个 chunk 上已经触顶，Agentic 的 rewrite 没有触发理由**」。
根因不是 Agentic 没用，是语料太小、太散，问什么都一次能召回。

所以本轮按真实业务域重造了语料：

| 维度 | 之前 | 现在 |
|---|---|---|
| 文档数 | 7 | 48（旧 7 + 新 41） |
| chunk 数 | 21 | 293 |
| 字符数 | ~1.2 万 | ~5.2 万 |
| 业务域 | 4 个制度主题 | 人事/财务/采购/仓储/订单/IT/客服 七域 |
| 受限文档 | 1（D10.9） | 18（D10 / D10.9 / payroll 三档） |
| 黄金集 | 22 | 198 |
| 越权集 | 6 | 82 |

**语料设计的三条刻意安排**：

1. **有跨文档才能答的问题**：出差流程在 HR 制度、住宿金额在财务细则；远程办公在 HR 制度、
   数据密级在 IT 规范。这类题（`cross_doc`）才是 Agentic rewrite 该发力的地方。
2. **有同义不同词的问题**：问「超时没发货」而文档写「超时未发货 → E-4001」，
   考的是召回而不是字符串匹配。
3. **有正向看不见、也有反向看不见**：82 条正向题测「D20 看不到总部」，
   12 条反向题测「总部看不到 D20」——3 份 D20 专属文档（社保细则 / 外包门禁 / 职场租赁）
   只对分公司开放。**只测单向时，把 `depts` 写成"附加可见"而不是"限定可见"全绿**，
   两个方向都有题才拦得住。

## 2. 核心指标（本轮实测）

口径：198 条黄金集 + 8 条拒答集 + 94 条越权集（共 300 条），`v4-pipeline`，rerank 开，
`KW_DEFAULT_DEADLINE_MS=30000`，跑批结果 `eval/runs/v4-pipeline.json`。

| 指标 | 实测 | 必须一起说出口的限定 |
|---|---|---|
| 语料 | 51 份有正文 / 315 chunk | `kb_document` 有 52 条 ACL 记录，其中 1 条无 chunk（见 §4 P2）。跑 `v4` 时是 48 份 / 293 chunk，重灌后变了 |
| 带 ACL 的文档 | 18 份 | D10 / D10.9 / payroll 三档收窄 |
| 检索 Recall@50 | **0.9949** | rerank 开关同值 |
| 检索 Recall@10 | 0.9899 | 跨文档题型只有 **0.818**，别报总分 |
| 检索 MRR@10 | 0.9621 | rerank 关掉是 0.9105，这是 rerank 唯一实测出的价值 |
| 端到端正确率 | 99.5%（197/198） | **74% 是单跳题**，跨文档只有 11 条，不能外推 |
| Agentic 正确率 | 99.5%（197/198） | 30s deadline；唯一失败那条是 A5 的 bug，内容其实命中了 |
| Agentic 代价 | tokens 4455（×3.0）、p50 12.0s（×4.5）、步数 6.52（×2.1） | **换回来 0 增益**，多出的预算花在 grade 判定上（输出 token 137→1035，其中答案长度不变） |
| 拒答准确率 | 100.0%（8/8） | 8 条里 2 条是软拒答，没有落 `abstained`，下游不会转工单 |
| 越权泄漏率 | 1.06%（1/94） | 唯一一条 `u-105` **不是 ACL 漏**，是"该拒不拒"（检索没有相关性下限），见 §4 P1 |
| p50 / p95 | 2857ms / 5685ms | pipeline；其中 rerank 单项占 ~1.1s |

**这张表最危险的一行是「99.5%」。** 它的成立条件非常具体：单跳题为主、标注锚点与
生成证据同源、拒答集只有 8 条。拿去讲的时候要主动把这三条讲掉，否则一经追问
「跨文档多少」，0.818 的检索召回会把 99.5% 打回去。

真正能代表上限的是检索层跨文档那一列，以及 agentic 图在同一批题上的表现（见 `eval/report-v2.md`）。

### 2.1 换一个模型，掉不掉点

留一个只换生成模型、别的都不动的对照批（`eval/runs/qwen-pipeline.json`，
`KW_ROLE_OVERRIDE` 把 `generate`/`plan` 换成 Qwen2.5-72B，其余配置同 `v4-pipeline`）：

| 指标 | DeepSeek（v4） | Qwen2.5-72B（qwen） | 读法 |
|---|---|---|---|
| 黄金集正确率 | 99.5%（197/198） | 98.99%（196/198） | 差 1 条，在噪声内 |
| 拒答准确率 | 100%（8/8） | 87.5%（7/8） | 少的是软拒答，不是硬拒答 |
| 越权泄漏率 | 1.06%（1/94） | **0.0%（0/94）** | 泄漏那条靠的是模型常识，换模型就换了运气 |
| p50 / p95 | 2857 / 5685 ms | 3047 / 6550 ms | 同一量级 |
| tokens/次 | 1507.6 | 1281.4 | **跨厂商 tokenizer 不同，这列不能直接比价** |

结论：**抽象层没锁死模型**。同类模型换一家，精度在 1 条题内波动，越权那条因为
依赖模型常识而随机翻转——这恰好说明它不是 ACL 漏洞，是"没证据也敢答"的行为问题，
该在收敛侧修，不该指望换模型。

### 2.2 排障域回放（30 条）

口径：`eval/datasets/replay_ops_v1.jsonl`，6 类根因各 5 单，证据分散在 3~4 张表；
走 `POST /v1/fulfillment/tasks` → 自动满足澄清与审批 → 取 `result.root_cause`。
跑批结果 `eval/runs/ops-v1.json`（Qwen2.5-72B 在线）。

| 指标 | 实测 | 限定 |
|---|---|---|
| Root Cause Top-1 | **83.3%（25/30）** | 30 条是**自己造的单**，类内同构，比真实工单简单得多 |
| 未收敛（escalated） | 0% | 没有一条转人工——**这比错判更值得警惕**：它意味着模型从不承认"查不出来" |
| 收敛到错根因 | 16.7%（5/30） | 见下面的失败分析，5 条是**同一个**失败模式 |
| p50 / p95 | 29.6s / 39.9s | 在线模型；mock 模式同一批 700ms 级 |
| 审批中断 | 35 次 / 30 题 | 5 题重入 2 次（先要澄清缺订单号，再要审批） |

分根因看，`rule_misjudge` 只有 **20%**，其余四类满分：

| 根因 | Top-1 | 说明 |
|---|---|---|
| carrier_stuck | 100% | 轨迹里有 `STUCK_ALERT`，直接命中 |
| out_of_stock | 100% | 库存快照 `sufficient=false` |
| address_invalid | 100% | 地址校验码 + 客服工单互证 |
| payment_failed | 100% | 支付流水状态明确 |
| duplicate_outbound | 80% | 1 条被判成"库存不足" |
| rule_misjudge | **20%** | 4 条被判成"承运商滞留" |

**5 条失败是同一个模式：模型停在"最响的证据"上，没有往下追一层。**

- `rule_misjudge` 那 4 单，物流轨迹里确实写着"因台风/暴雨交通管制延误"——**这是真的**。
  但真根因是"赔付规则没排除不可抗力，系统于是误判超时"。模型把**直接原因当成了根因**。
  `r-29` 的结论文里甚至写了"系统规则误判未排除不可抗力因素"，`root_cause` 字段却填了
  `承运商滞留`——它看懂了，但没敢下结论。
- `r-23` 那单可用库存是 **-11**，模型判"库存不足"。负库存本身就是"重复出库"的症状，
  真根因在出库单里重复了两条。

所以这不是"能力不够"，是**判据少了一层**：`gather_evidence` 只看"证据支持哪个假设"，
没有要求"这个假设能不能解释其他异常"。修法有两个方向，都还没做：
① 给 `check_rule` 强制调用——涉及规则类根因必须先有规则比对证据，像日志那样兜底；
② 在 `evaluate` 里要求：多个假设同时成立时，选**能解释其他症状的上游根因**。

**这个 83.3% 不能当能力指标读。** 六类根因的证据分布是写 seed 时按"能被查出来"设计的，
真实工单里最难的恰恰是"证据不全"和"两类根因同时存在"。要验证的是链路通不通、
归因分不分得开——前半件成立，后半件在"症状 vs 根因"这一层暴露了短板。

### 2.3 一个被我自己否掉的改动：相关性下限

`u-105` 那条泄漏查下来，根因不是权限，是**检索没有下限**：库里没有答案时，稀疏路
仍会返回 5 条词面命中的文档，模型于是用常识补出答案。直觉上"加个阈值"就能修。

先标定（`scripts/probe_relevance.py`，292 条首名分数）：golden 中位 0.973 / p10 0.828，
越权题中位 0.050。阈值 0.2 时 **golden 误伤 0%、越权题拒掉 78.7%**——看起来是白捡的。

上线跑 A/B（同模型 300 条，`qwen-pipeline` vs `qwen-floor`）：

| 指标 | 无下限 | 下限 0.2 | 变化 |
|---|---|---|---|
| 黄金集正确率 | 98.99% | 97.98% | **-1.0pt** |
| 其中 cross_doc | 100% | 90.9% | **-1 条** |
| 拒答准确率 | 87.5% | 75.0% | **-12.5pt** |
| 越权泄漏率 | 0.0% | 0.0% | 无变化 |
| tokens/次 | 1281 | 514 | -60% |
| p50 | 3047ms | 2741ms | -10% |

**标定错了在哪：只量了首名。** 真正被裁掉的是**次名**——跨文档题要的正是第二份文档，
它的分数本来就低。用首名分布推"不误伤"，等于只量了不会受伤的那一半。
拒答准确率下降同理：拒答集里有几条本来会命中文档、靠"软拒答"得分，现在证据被裁空、
连软拒答都没了。

结论：**回退默认值，但保留开关**（`KW_MIN_RELEVANCE`，默认 0）。
留着是因为它确实把 tokens 砍了 60%，对"宁可多拒不可乱答"的严格场景是可用配置；
不留成默认是因为这次 A/B 说得很清楚——收益在成本侧，代价在正确侧，而这个系统的
正确侧更贵。

真修法不在检索层：应当在 `synthesize` 判"证据够不够支撑一个答案"，而不是靠上游硬裁
把证据删掉。这条记在 §4 P1。

### 2.4 演示页：同一个问题，两种控制流

§2.1 说"agentic 无增益"，这句话在报告里是数字，在演示页上是可以当场按的按钮。
实测同一道题（"单笔 6 万元的费用报销要谁审批？"，普通员工 D10，Qwen2.5-72B 在线）：

| 控制流 | 步数 | tokens | 耗时 | 徽章 |
|---|---|---|---|---|
| 管线式 | 4 | ~1100 | **4.5~5.7s** | 已作答 |
| Agentic | 6 | 4830 | **44~94s** | 已作答 |

同一批 8 次连跑，管线式 8/8 成功，耗时 5.4~25.7s（上游 rerank 抖动大）。

**两处踩坑值得记**：

1. 演示页原先默认加载的是 `domain.yaml` 声明的 agentic 图，而服务默认 deadline 只有 60s。
   于是任何人第一次提问都会等 60 秒、然后看到 `degraded`——**这是配置问题，不是能力问题**，
   但看的人只会得出"这东西又慢又不可靠"。现在默认走管线式，服务 deadline 放到 180s。
2. 60s 下 agentic 的失败**不是报错，是 `abstained`**（撞预算 → `stop.on_budget=abstain`）。
   表现为"证据不足、2 步、无引用"，看起来像模型不会答。这条比超时更误导：
   超时至少明显是故障，而"证据不足"会被当成能力结论。诊断时先看 `steps`——
   真的缺证据时步数是满的，撞预算时步数会停在半路。

**界面这一轮改了什么**（都是"看起来能不能用"层面的问题，不是功能）：

| 改动 | 原因 |
|---|---|
| 右上角加控制流切换 | 两种图的差异能当场对比，比文字说明有说服力 |
| 徽章中文化（已作答 / 已降级 / 证据不足） | `degraded`、`abstained` 是内部状态码，演示页上没人看得懂 |
| 引用侧栏默认只列被引用的 | 5 条里 3 条灰着标"未引用"，把真正被引用的两条淹了 |
| 权限对比加结论条 | 只摆两段答案，看的人得自己数引用条数才知道权限起没作用 |
| 权限对比换默认问题 | 原问题两个身份都命中 5 条，演不出差异；换成"工资条在哪查"后，普通员工 3 条全无关→拒答、薪酬专员 3 条全命中→作答 |
| 去掉恒为 0 的 cost | `$0.00000` 不是"便宜"，是"没配价目表"，摆着像算错了 |
| 评测看板旧批折叠 | 五张同结构的检索表并列，得先分辨哪张才算数 |

**权限对比那个默认问题值得展开一句**：换问题之前，我先用三个身份 × 8 个问题探了一遍，
发现"薪酬数据谁能查看？"这类问题上两个身份**都拿到 5 条**——因为 ACL 的分叉不是
"有/没有"，而是"命中的文档集不同"。演示要选的不是"谁被拦"，而是"谁看到了什么"。

### 2.5 排障域终于有界面了（以及两个把功能跑挂的坑）

之前排障域**只有 REST API，演示页里根本没有入口**——它能跑，但要 curl 才看得到。
这轮补上第四个视图「订单排障」，走 `:8002` 的完整任务流。

实测一单（`O20261100001`，承运商滞留，Qwen2.5-72B + Qwen2.5-7B）：

| 阶段 | 结果 |
|---|---|
| 创建任务 → 审批点 | 20.2s，4 个节点，4 条证据判定（1 支持 / 3 无关），tokens 4104 |
| 待审批动作 | `retry_push_carrier` · 风险 medium · 参数 `{order_id, carrier:"SF"}` |
| 审批通过 → 恢复 | **7ms，steps=1，零新增 LLM 调用**（从 checkpoint 续跑） |
| 最终 | `completed`，根因「承运商滞留」，置信度 0.80 |

**为什么直连 8002 而不是让知识域代理**：代理等于把排障域的写操作 API 伪装成知识域的
能力，"域边界即服务边界"这句话就当场失效。演示页只是个前端壳，跨域访问两个后端才是
真实形态。白名单显式给（`KW_DEMO_ORIGINS`，默认 8001），不用 `*`——这个服务能触发审批。

**两个坑，都是"功能明明写对了却跑不通"**：

1. **`decision` 枚举是 `approved` / `rejected`，不是 `approve` / `reject`。**
   前端按动词写了，`resume` 直接 400 `INVALID_SCHEMA`。这条只有真点一次按钮才会暴露——
   单测覆盖不到"前端传了什么字符串"。
2. **把 `classify` 换成 Qwen3-8B，整单 `MODEL_TIMEOUT`。**
   排障域的 `analyze_symptom` 和 `evaluate` 都走 `classify` 角色，一个任务要调多次。
   Qwen3-8B 是**思考模型**，同样的判定负载 14.3s，而非思考的 Qwen2.5-7B 只要 1.2s，
   累积起来直接撞穿 90s 超时。表现是"模型调用超时"，看起来像上游挂了。
   教训：`classify` 是高频判定角色，不能用思考模型——这也解释了为什么它在
   `models.yaml` 里被单独标了 `cache: true`。

**指标行的口径也改了两处**，因为原来的数字自相矛盾：

- `steps` 改叫「节点」并改用全程节点数。一个任务被审批切成两段流、每段一个 ledger，
  只显示最后一段的 usage 会出现"跑了 4 步却写着 steps 1"。
- `elapsed` 只累计诊断耗时，**不含审批等待**。审批可能等人几十分钟，
  算进耗时就失去了意义。tokens 同理，两段累加。

### 2.6 真流式：从"整段蹦出来"到"边生成边出现"

先摆事实。改造前在同一道题上插探针，量每一帧的到达时刻：

```
1.684s  meta        （检索完成）
1.685s  citation    （证据回来）
3.259s  delta       '单笔金额超过 5 万元的费用报销，须报财务总监审批…'
3.261s  delta       '{e_费用报销管理办法-c3}'
3.262s  done

首帧 3.259s  末帧 3.261s  跨度 0.001s
```

**正文和 done 在同一个瞬间到达。** 用户看到的是"转圈 3.2 秒，然后整段蹦出来"——
所以"没有流式输出"这个判断是准确的，不是错觉。

根因不在前端：SSE 解析（`consumeSSE`）、增量渲染（`paintAnswer` + rAF 合并）、
引用角标都写好了。问题在 `runtime/llm.py`：抽象层只有同步的 `chat()`，
`synthesize` 先拿到全文，再按句切开发出去。切得再细，首字节也等于整段生成耗时。

#### 改了三层

| 层 | 改法 | 关键坑 |
|---|---|---|
| `llm.py` | Provider 加 `stream()`，解析 OpenAI 兼容 SSE | usage 在**尾帧**且要显式请求（`stream_options.include_usage`），不请求就一个 token 数都拿不到，账本静默记 0 |
| `runtime` | 加 `llm_stream()`，逐块 yield | 计费放 `finally`：调用方提前 break 时尾帧还没到，按已收到字符估算——**记 0 会让预算约束看起来在工作** |
| `nodes.synthesize` | 换成边收边发 | 见下面「切点」 |

#### 唯一需要想清楚的是：切点选在哪

- **按句切**最安全（`{e_xxx}` 不会跨越句号），但第一句写得长时，首字就要等一整句。
  实测首字 2.3~6.5s，抖动全在上游首包。
- **按固定长度切**能把首字压到"前十几个字生成完"，但带来两个新风险：
  引用标记被切成 `{e_` + `xxx}`（前端按 eid 精确匹配，切碎等于没引用）；
  以及**脱敏失效**——手机号被切成两段，两段都匹配不上正则。

所以规则是三者叠加：

1. 遇到句边界（`。；！？\n`）立即发，但**花括号必须先配平**——`{e_a.b}` 这类含点的
   eid 会让"句号"落在括号内部；
2. 没有句边界时，攒够 12 个字、括号配平、且**不含数字与 `@`** 就放行；
3. 含数字的片段一律等句子结束。宁可慢半秒，不可漏一个手机号。

#### 效果

同一道题、3 次独立请求（`session_id` 每次不同，否则会被幂等缓存整条重放成 0.04s）：

| 项 | 改造前 | 改造后 |
|---|---|---|
| 首个正文帧 | 3.26s，且只有 1 帧正文 | 2.14s / 2.68s / 2.79s |
| 帧数 | 2（正文 + 引用） | 4 |
| 首末跨度 | 0.001s（同一瞬间） | 3.3s |

样本只有 3 条，且上游首包抖动大，**不要把 2.14~2.79 当成 p50 报**。
能确定的是两件事：首字节不再等于整段耗时；帧与帧之间确实有间隔了。

#### 流式带来的一个连锁问题：判罚时点

正文一旦流式发出就不可撤回。此时 `verify_citations` 若因为"整段没有引用标记"
判 `no_citation → abstained`，就是 A5 修过的那个矛盾的**另一副面孔**：
屏幕上摆着完整答案，API 说他没答。

改成按"发没发出去"分流：

| 情况 | 判 | 理由 |
|---|---|---|
| 已交付（citation + delta 都发过） | `degraded` | 交付了，但引用不成立；不能否认已交付的内容 |
| 没交付 | `abstained` | 什么都没发，拒答就是拒答 |

两条单测分别钉住，见 `tests/test_stream_answer.py`。
注意这会让 golden 集里"无票作答"的 case 从 abstained 变 degraded，
而评测口径里 `degraded` 算"内容命中仍算对"——**报数时要单列这部分**，不能混进正确率。

#### 附带修的一个评测污染源

第一次带流式跑 300 条，`28/300` 撞上 `HTTP 503`，结果全是空答案、归因 E10，
正确率被拉到 **85.35%**（基线 98.99%）。查下来是上游抖动，不是代码回归——
但这个数字如果直接写进报告，就是"基础设施抖动被读成能力下降"的典型反面教材。

于是补了重试（`tests/test_llm_retry.py`，7 条）：

- 非流式：5xx / 429 退避重发，最多 3 次；4xx 不重试（重发只会再被拒一次，还白花额度）；
- 流式：**只有还没吐出第一个字时**才允许重发。开口之后重试会把同一段答案发两遍，
  这比失败更难解释。

带重试重跑同一批 300 条（`eval/runs/qwen-stream2.json`）：

| 指标 | qwen-pipeline（非流式基线） | qwen-stream（无重试） | qwen-stream2（流式 + 重试） |
|---|---|---|---|
| 上游失败（`finish=?`） | 18 | **28** | **0** |
| golden 正确率 | 98.99% | 85.35% | **98.48%** |
| 拒答准确率 | 87.5% | 75.0% | 87.5% |
| 越权泄漏率 | 0.0% | 0.0% | 0.0% |
| p50 / p95 | 3.05s / 6.55s | 3.53s / 7.78s | 3.43s / 8.62s |
| tokens/次 | 1281 | 1300 | 1408 |

**怎么读这张表**：

- `0` 条上游失败说明重试确实把抖动挡住了，而 98.48% vs 98.99% 差 1 条题，在噪声内
  ——**流式改造没有伤到正确率**。
- 新增的 2 条失败（`g-119` / `g-159`）都是 E6「答案覆盖不全」，不是截断、不是引用失败。
  答案是完整句子、带完整 `eid`、带句号，只是没答全要点。这类差异归因于采样，
  但**样本只有一批，不能排除流式之外的其他因素**，要坐实得再跑一批。
- p95 涨了 31%，主因就是重试：原本会失败的请求现在用两次退避换回来了。
  **用时间换成功率是这一档的明确取舍，不是退化。**
- tokens 涨 10% 需要说明：尾帧 usage 缺失时会按字符数估算（见 `llm.py` 注释），
  这批里有估算成分，跨批比较 token 数时要留意。

### 阶段 B（第 1~2 周）— M4 排障域最小闭环

排障域是**广度**的证明（对应 JD 第 4 条），但不需要做全。最小闭环只做五件事：

| # | 事项 | 关键决策 | 验收 |
|---|---|---|---|
| B1 | 诊断图：`analyze_symptom → build_hypotheses → gather_evidence → evaluate → propose_action` | 复用 Runtime 图内核，不新写状态机 | ✅ 5 节点跑通真实订单；`_refine` 改写回环首次被真实触发（签名 bug 当场暴露） |
| B2 | 工具注册表接入 5 个只读工具（订单查询 / 库存快照 / 物流轨迹 / 支付流水 / 操作日志） | 工具 schema 用 JSON Schema 校验，超时 3s、重试 1 次 | ✅ 全部查 `v_order` 脱敏视图；`datetime→ISO`、`Decimal→float` 在工具层就转好，不让模型看 `"2026-11-01T00:00:00+08:00"` 猜 |
| B3 | SQL Guard 四道闸（只读账号 / 语句白名单 / 强制 limit / 禁止 DDL） | 用真实业务库的只读副本，不造 mock 表 | ✅ `tests/test_sql_guard.py` 19 条，**每条断言具体是哪一道闸拦的**；`SELECT * FROM op_log LIMIT 50` 判对象层（LIMIT 是扫完才截断的） |
| B4 | HITL：写动作前 `interrupt` + checkpoint + 审批回灌 | 审批只在「执行动作」前，不在诊断过程中 | ✅ 中断-恢复可回放；补了两条：被拒后**升级而不是重讲一遍**、恢复阶段**零新增 LLM 调用** |
| B5 | 回放评测集 30 条（历史工单格式） | 先做 30 条，跑通再加到 100 | ✅ Top-1 83.3%（25/30），过 60% 线；5 条错判是同一个模式（停在症状上），见 §2.2 |

**这一阶段的取舍**：不做实时日志流、不做真实写操作、不做多轮追问。
理由——排障域的价值是证明「工具调用 + 假设验证 + 人工确认」这套机制成立，不是覆盖全部故障类型。

**埋过的两个坑，值得单独记**：

1. `gather_evidence` 原先让模型自己决定调哪个工具，结果"承运商滞留"这个假设只查了轨迹，
   漏掉 `STUCK_ALERT` 那条操作日志，判成 0 支持 → 转人工。**日志是横切证据，不该由模型
   决定查不查**。改成节点兜底拉一次订单级 `search_op_logs` 后，同一单置信度 0.95。
2. 工具返回 `datetime` 时 `json.dumps` 直接抛 `TypeError`，表现是"工具调用失败"，
   排查方向会被带偏。兜底 `default=str` 只保证不崩，不保证好用——两件事分开做。

### 阶段 C（第 3 周）— A2A 跨域

| # | 事项 | 验收 |

| C2 | 知识域 Agent 在处理履约类问题时发 Task 给排障域 | ✅ 跨进程实跑：`TASK_STATE_COMPLETED` / `root_cause=carrier_delay` / 707ms |
| C3 | 跨进程 trace 透传 + 一条完整回放 | ✅ 一条树：`knowledge.answer → a2a.http.serve → fulfillment.node.* → shared.llm.chat`。**A2A 端点必须自己 `begin_http_span`，否则 trace 断在进程边界** |
| C4 | 对端宕机时的降级（超时 → 单域作答 + degraded 标记） | ✅ 三态可分：`a2a_unreachable` / `a2a_timeout` / `a2a_capability_mismatch`，用 `httpx.MockTransport` 造 |

**为什么先做「一个方向」再补反向**：单向时"谁会调谁"写死在代码里，不可能成环，所以协议层
只需要验证"能不能调通 + 挂了怎么降级"。反向不是简单多写一个 client——它第一次让
`knowledge → fulfillment → knowledge` 成为一条**可能成立**的路径，于是必须同时引入委派链：

- 出站时 `scope.chain` 追加本域，服务端看到链里有自己直接拒（`a2a/server.py` 的 `/a2a` 入口，handler 之前）；
- 跳数上限 `MAX_HOPS=2`，因为第 3 跳已经没有新的信息增益，只有成本；
- 知识域的 `maybe_delegate` 也读链——它可能在 pipeline 图里被调后再次外发。

**反向委派的实际价值**：`check_rule` 只回答"这个规则 id 的触发条件"，回答不了
"用户签的那版赔付条款原文怎么写的"。后者在知识域的 `kb_chunk` 里，而且它的可见性
由静态共享/动态共享/审批单共同决定——**让有权限的一侧去检索，而不是绕过它**，
这才是走 A2A 而不是进程内直读的原因。

**委派为什么要 `diagnose_only`**：排障域被调用时只出根因，不提议动作、不进审批。
上游是知识问答界面，**没有审批入口**——发回去一个"待审批"的动作，等于把死胡同丢给用户。
