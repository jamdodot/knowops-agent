# ADR-0002 A2A 只用于跨域委派，应用调 Agent 一律走 REST

- **状态**：已接受
- **日期**：2026-11-02
- **影响范围**：服务间通信方式、Agent Card 契约、网关实现、故障降级策略

---

## 背景

项目里存在三类调用，早期设计把它们都标成了 A2A：

```
Java 网关      →  knowledge-agent        （被标为 A2A）
Java 网关      →  fulfillment-agent      （被标为 A2A）
knowledge-agent ↔  fulfillment-agent     （被标为 A2A）
```

这是概念错误。A2A（Agent2Agent）的前提是**两端都是自主的 agent**：各自有 Agent Card 声明能力、有 Task 状态机、能拒绝或协商任务。Java 网关是确定性的业务服务——它没有 Agent Card，不自主决策，只做鉴权、会话、审计。把它当 A2A 的一端，协议的核心语义（能力发现、任务状态、中断续跑）一个都用不上，只剩下一层多余的 HTTP 封装。

同时另一个问题需要正面回答：`knowledge` 与 `fulfillment` **是同镜像、同 Runtime、同一个人写的**。按 A2A 最严的适用标准（"跨你不拥有的边界"），它们不该用 A2A，用 LangGraph 子图更省。这个决定必须明确，否则面试一问就崩。

---

## 决策

**1. A2A 只保留一处：`knowledge-agent ↔ fulfillment-agent`。**
**2. 应用调 Agent（Java 网关 → 任一 agent）统一为 REST + SSE + OpenAPI 契约。**
**3. 图节点内部的工具接入统一为 MCP，不与上面两者混用。**

对齐到四层：

| 层 | 机制 | 用于 |
|---|---|---|
| 进程内 | 函数调用 | 节点内部逻辑 |
| agent → 工具 | MCP | 检索、查库、日志、规则 |
| 应用 → agent | REST + SSE | 网关入口 |
| agent ↔ agent | **A2A** | knowledge ↔ fulfillment |

---

## 为什么 K ↔ F 仍然用 A2A（只认成立的部分）

**不成立的理由，先排除掉**：

- ❌ "它们是两个 agent" —— 弱理由，同一进程内两个函数也是两个逻辑体
- ❌ "组织边界" —— 个人项目，没有两个团队，不装
- ❌ "跨语言" —— 都是 Python，同镜像

**成立的理由**：

1. **状态边界（决定性）**
   诊断是长时任务：单次 30s、多步工具调用、中途可能需要人补充信息。
   这要求可回放的 Task 状态机与中断续跑（`TASK_STATE_INPUT_REQUIRED` → 用户追问 → 续跑）。
   用 REST 实现这套要自己发明状态协议、自己定义恢复点；A2A 已经把 Task/Message/Artifact 的语义定死了。

2. **故障与资源边界**
   知识域吃检索（内存+CPU），排障域吃工具调用（IO+长等待），资源画像不同，要独立扩缩容。
   排障域不可用时，知识域必须降级为"仅文档答案 + 数据不可得"，**这个降级需要一个显式契约才写得出来**。

3. **契约强制力**
   Agent Card 把两个域的耦合面收敛成一个小 schema（一个 skill、四个入参、两类 Artifact）。
   协议版本的破坏性变更（v1.0 移除 `Part.kind`、枚举改 `TASK_STATE_*`）会强制双方同步升级，而不是悄悄改字段。

> 一句话：**我买的是 Task 状态机 + 降级契约，不是"通信能力"。通信本身用 REST 就够了。**

---

## 否决的方案

| 方案 | 否决理由 |
|---|---|
| 全部用函数调用（同一进程） | 失去独立扩缩容与故障隔离；排障域卡死会拖垮知识域 |
| 全部走 REST | 长任务中断续跑要自研状态机；降级契约无处挂载；能力无声明，网关得硬编码路由 |
| 全部走 A2A（含网关） | 网关不是 agent，用不上任何 A2A 语义，纯增复杂度 |
| 用 LangGraph 子图编排 | 曾认真考虑。**单进程内它确实更省**。否决原因：本项目要验证的正是"跨进程协作"这条能力，且扩缩容需独立部署单元 |

## 后果

### 正面

- 概念干净：四层协议各司其职，每一层都能说清"为什么不是另一层"
- 故障隔离可验证：手动 kill fulfillment，知识域应正确降级而非报错
- 可回放：一次跨 2 进程的完整 trace，Task 状态迁移全程可见

### 负面（必须承认）

- **多一次网络跳**：诊断链路延迟 +50~150ms
- **协议复杂度**：要维护 Agent Card、Task 存储、`input-required` 的续跑逻辑
- **A2A 本身在演进**：v1.0（2026-03）有 16 项破坏性变更，v1.0.1 才勘误完成，SDK 生态仍在收敛
- **本项目的 A2A 不满足最严适用标准**：这是作品集项目的取舍，真实生产中若两域确由同一团队维护，应退回编排框架

### 重审触发条件

出现以下任一情况，应重新评估是否保留 A2A：

1. 两个域最终合并为单进程部署
2. 跨域调用占比超过总请求 50%（说明本就该在一个域内）
3. 需要强事务一致性（此时 A2A 的最终一致模型不适用）

## 面试口径

**Q：你这个项目为什么要用 A2A？**

> 只用在一处：知识域委派排障域。因为它不是一次请求-响应，是一个 30 秒、多步、可能中途要问用户的长任务，需要可回放的 Task 状态机和中断续跑；而且排障域不可用时知识域要能降级而不是陪葬。
>
> 我买的不是通信能力，通信用 REST 就够了。我买的是状态机语义和降级契约。

**Q：那 Java 调 Python 也是 A2A 吗？**

> 不是。Java 那层是应用，没有 Agent Card，不自主决策。那是 REST + SSE。我早期设计里标错过，后来改掉了。

**Q：两个 agent 都是你写的，为什么不直接用 LangGraph 编排？**

> 单进程内确实更省，这也是业界共识。我用 A2A 是因为要独立扩缩容和故障隔离，且这个项目要验证的正是跨进程协作这条能力。如果是生产环境、两个域确实同团队维护、也不要求独立部署，我会退回编排框架——A2A 的复杂度只有在"对方不在你的边界内"时才值得付。
