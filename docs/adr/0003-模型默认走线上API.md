# ADR-0003：模型默认全部走线上 API

- **状态**：已接受
- **日期**：2026-11-02
- **相关**：`docs/08-模型接入方案.md`、`docs/10-部署形态与硬件配置.md`、`config/models.yaml`

---

## 背景

开发与演示环境是**一台 16GB 内存、无独显的普通电脑**。项目需要三类模型：生成（LLM）、向量化（embedding）、重排（rerank）。

早期文档（`08`）写过"Embedding 自托管优先""OCR 必须 GPU 自托管"，这个表述有两个问题：

1. 把"自托管"和"GPU"绑定，造成"没有显卡就做不了"的误判。实际上 MinerU 的管道后端在 CPU 上可跑，解析又是入库时的一次性开销，不在请求链路上。
2. 把"自托管"当成了更专业的默认选项，但**没有说清它到底换来什么**。

同时核对到一个事实：项目价值并不在模型上。约 80% 的技术含量在数据库侧——权限条件与向量检索写进同一条 SQL、两路召回融合、评测归因分类，这些都与模型放在哪里无关。

---

## 决策

**模型调用（LLM / Embedding / Rerank / Judge）走线上 API；文档解析全部本地。**

| 类别 | 归属 | 具体 |
|---|---|---|
| 生成 / 规划 / 判断 / 抽取 | 线上 | DeepSeek（OpenAI 兼容） |
| Embedding（dense） | 线上 | 硅基流动 `BAAI/bge-m3` |
| Rerank | 线上 | 硅基流动 `BAAI/bge-reranker-v2-m3` |
| Judge（评测打分） | 线上，**与生成异源** | 硅基流动（非 DeepSeek 模型） |
| 解析·L0 直取 | **本地库** | PyMuPDF（注意 AGPL）/ 退化 pypdfium2 |
| 解析·L1 主力 | **本地库** | Docling（MIT，CPU） |
| 解析·兜底 | **本地** | MinerU 管道后端（云 API 保留为开关，默认关） |

本地只保留：一个 PostgreSQL 容器 + 三个进程（Java 网关、两个 agent）+ 四个解析库。常驻内存约 3GB，入库峰值约 8GB。

> **2026-11-02 第一次修订**：原决策写"除文档解析外全部线上，解析本地 CPU"，把解析整体当成"必须本地"。
> 复核后发现这个划分在**表述**上不成立——**PyMuPDF / pdfplumber / Camelot 是纯库、根本没有线上形态，
> 所以"本地"对它们是唯一选项，不是决策**；Docling 只有自托管 `docling-serve`，也没有公开 SaaS；
> **只有 MinerU 真的两种形态都有**（本地管道后端 + 官方在线 API）。所以决策应改为"按有没有线上形态分流"。
>
> **2026-11-02 第二次修订（当前生效）**：上一步一度把兜底那一路切到了云 API。
> **最终决定不切，全部本地。** 理由是那 3GB 内存不值六件事：多一个 key、受配额约束、
> 原文出域、断网不可用、成本不可预测、出错只能提工单。
> 关键在于：**"能上云"和"该上云"是两个问题**。前一步只回答了第一个。
> 保留 `parse_mode: local | hybrid` 开关（默认 `local`），因为云 API 的异步任务制约束
> 值得提前写进配置，而不是等要用时再设计。详见 `docs/09-文档解析设计.md` 5.6。
> 详见 `docs/09-文档解析设计.md` 5.6。

## 理由

**1. 硬件不是瓶颈，因为瓶颈不在算力**

权限判定、检索融合、会话状态、评测数据全在 PG 里。模型换供应商改三行配置，权限改一次是重写。拿硬件规格做项目可行性判断，前提就错了。

**2. 成本可以量化，且远低于硬件投入**

作品集阶段全程约 150~300 元（建库 30~80 + 开发期问答 50~120 + 评测回归 30~60）。升级到能跑 32B 模型的显卡要上万，而质量仍不如线上强模型。

**3. 本地小模型质量撑不住生成链路**

7B/14B 的指令跟随与引用准确性不足，而这个项目的脸面就是"答案带正确引用、不越权"。生成质量下降会直接摧毁演示效果，省下的钱换不来任何东西。

**4. 抽象层已经存在，切换成本可控**

`ModelProvider` 协议 + `config/models.yaml` 是唯一的模型入口。将来要私有化，改 mode 与 provider 配置即可，业务代码不动。**正因为能随时换，现在才敢先用线上。**

---

## 备选方案与否决

**方案 A：本地自托管 BGE-M3（GPU 推理服务）**
否决。理由是收益与成本不匹配：省不了几十块 API 费用，却要背一个推理服务的运维。而且稀疏那一路本来就用 PG 的 BM25，不需要 BGE 的 sparse 输出。

**方案 B：本地跑 7B/14B LLM 做生成**
否决。生成质量是演示核心，本地小模型在长上下文、结构化引用、指令遵循上都不达标。

**方案 C：全本地（含 LLM），追求"完全自主可控"**
否决。这是话术需求不是技术需求。真要离线演示，用录制回放解决，成本几乎为零（见下文）。

**方案 D：混合——LLM 走 API，embedding 自托管**
**保留**。这是未来的第一站，但不是现在的起点。触发条件见下节。

## 后果

### 正面

- 环境极简：一个 PG 容器 + 三个进程，16GB 无独显可跑
- 无 GPU 依赖，任何机器都能复制这套环境
- 成本可测：每 trace 记 token，日/月预算熔断，跑评测不会失控
- 模型能力始终是最新的，不受本地硬件上限约束

### 负面（必须承认，并且要有对策）

| 负面后果 | 对策 |
|---|---|
| **数据出域**：传给 embedding 的文本就是原文本身 | 只用公开文档与自造数据；真实企业数据接入前必须先切自托管（见触发条件） |
| **供应商静默升级权重**：Recall 会莫名下降 | `embed_lock` 三锁 + 定期跑黄金集回归；怀疑时就 bump version 重测 |
| **限流与超时不可控**：免费额度会 429 | 令牌桶 + 队列削峰 + 指数退避；入库任务永不裸并发 |
| **断网或 API 故障时演示不可用** | `MockProvider` + 响应录制回放，**界面明确标注"演示模式"**，不假装在线 |
| **judge 与生成同源会污染评测** | `roles.judge` 强制指向不同厂商的模型，写在配置里而不是靠自觉 |
| **合规风险**：DeepSeek 托管于境内，但仍属第三方处理 | 内部分级：公开→可云；内部→脱敏后可云；机密→必须自托管 |

### 一个必须记住的实现细节

**rerank 没有统一协议。** chat 和 embedding 基本都兼容 OpenAI 规范，但 rerank 各家路径不同（硅基流动是 `/v1/rerank`，Cohere 是 `/rerank`，Jina 又是另一种）。所以"一套 SDK 通吃所有 provider"这句话**对 rerank 不成立**，`ModelProvider` 里 rerank 必须独立建模，走独立的适配器。

## 重审触发条件

出现以下任一情况，重新评估本决策：

| 触发 | 先转什么 | 理由 |
|---|---|---|
| 接入真实企业文档（涉密/内部） | **embedding + 解析**，LLM 最后转 | 传出去的文本就是原文，敏感性最高 |
| chunk 数 > 50 万 | embedding 自托管 | API 费用超过一台机器折旧 |
| 需要完全离线演示 | LLM 也本地，或启用全量回放 | 回放优先，成本最低 |
| 月 API 支出 > 500 元 | 重新算自托管 TCO | 到这个量级才开始值得精算 |
| 黄金集 Recall 出现无法解释的下降 | 先查供应商是否换了权重，再决定是否迁 | 这是 `embed_lock` 存在的意义 |

**顺序很重要：embedding 和解析先私有化，LLM 最后。** 因为 LLM 出域的是"问题与召回片段"，而 embedding 出域的是"全部原文"——敏感性完全不是一个量级。
