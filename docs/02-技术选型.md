# 02 技术选型

> 选型的原则：**在当前规模下选最简单的可行方案，并为换型留好触发条件。**
> 每一项都写清「为什么选它」「什么情况下必须换」。

规模前提（先钉死，否则选型无意义）：
文档 5k~2w 份，chunk 量级 50w~200w，日活用户 300，峰值并发 20，问答 QPS 峰值 ~5。

---

## 1. 文档解析

**先说清一件事：解析不是"选一个工具"，是"按页路由"。** 详细设计见 `09-文档解析设计.md`，这里只给选型结论。

| 方案 | 路线 | 强项 | 短板 | 许可 |
|---|---|---|---|---|
| **MinerU 2.x** | **双后端（pipeline + VLM）** | 中文与公式强；自带**页眉页脚移除**与**跨页表格合并**；一套工具覆盖两层 | 依赖重、GPU 更顺 | Apache-2.0 **+ 附加条件** |
| **Docling**（IBM） | 管道 | `DoclingDocument` 统一 IR，PDF/DOCX/PPTX/HTML 全覆盖，TableFormer 表格好，**CPU 可跑** | 中文复杂表格略弱 | **MIT（最干净）** |
| PaddleOCR-VL | VLM 直出 | 0.9B 小模型、中文强、许可证友好 | 生态偏中文 | Apache-2.0 |
| Unstructured | 管道 | 格式最全、接入最快 | 表格还原一般 | Apache-2.0 |
| LlamaParse / 商业 API | 云 | 效果省心 | 数据出域、按页计费 | 闭源 |
| **PyMuPDF** | 数字原生直取 | 零 GPU、毫秒级、**比 OCR 更准** | 双栏/扫描件无解 | **AGPL-3.0（闭源商用需授权）** |
| pdfplumber / Camelot | 表格与文本抽取 | 轻量、依赖少 | 复杂表格弱（Camelot 依赖 Ghostscript） | MIT |

**结论：按页探测四路路由，主力 Docling（MIT + 全格式 + CPU），MinerU 作兜底专家。**

```
Office 格式        → Docling 原生解析（PDF/DOCX/PPTX/HTML 统一 IR）
覆盖率 > 90%       → PyMuPDF 直取（不跑 OCR，更快更准）；规则表格用 Camelot
覆盖率 40~90%      → Docling parse（CPU）
覆盖率 < 40%       → MinerU pipeline + OCR
质量闸门不通过     → MinerU 兜底一次 → 仍不合格进人工复核队列（阻塞不了流水线）
```

**为什么主力是 Docling 而不是 MinerU**（和常见推荐相反，理由见 `09` 第 5.1 节）：
许可证 MIT 无附加条件 > 准确率高 2 分；而且它一个引擎吃掉 PDF + Office 全格式，
避免"两个引擎都在关键路径上"的复杂度翻倍。MinerU 只在**中文复杂版面 / 扫描件 / Docling 质量不达标**时出现，
所以它 CPU 慢（2~10 秒/页）和内存峰值高（3~5GB）都不构成问题——**因为它不在关键路径上**。

**VLM 直出不在生产路径**：没有 GPU、且端到端输出无法归因（错了不知道是版面、识别还是顺序）。
保留为预研项，不排期。

**三条关键判断**：

1. **有文字层的 PDF 不走 OCR。** 直取毫秒级，OCR 反而引入识别错误。很多项目直接跳到"选哪个 OCR"，
   忽略了最便宜也最准的一层。
2. **清洗和识别同等重要。** 页眉页脚不清洗，切块后会变成一批高度相似的垃圾块，
   在向量空间里挤掉真正该召回的内容。这属于"没洗掉"而非"识别错"，所以特别难查。
   Docling 能做基础的行级去重，MinerU 做得更彻底（自动识别 + 跨页表格合并），
   这也是它作为兜底引擎的第二个价值——不只是准确率，还有清洗质量。
3. **先看 LICENSE 再看 benchmark。** 2026 年各工具的准确率差距已经很小，许可证差距反而是硬门槛——
   MinerU 是 Apache-2.0 加营收门槛条件，Docling 是干净 MIT。严格商用场景这个顺序要倒过来，
   本项目正是据此把 Docling 定为主力。

**为什么不用商业 API**：企业文档不出域是硬约束，且需要"解析失败可归因"，黑盒 API 给不了。

**换型触发条件**：单份 100 页 PDF 解析耗时 > 60s，或表格 TEDS < 0.8，或 `header_footer_leak > 5%`，
则加 GPU / 换后端 / 补清洗规则。

## 2. 检索存储与混合检索

这是最需要讲清楚取舍的一项。混合检索 = 稠密召回 + 稀疏/关键词召回 + 融合 + 重排。

| 方案 | 稠密 | 关键词/稀疏 | 权限过滤 | 运维成本 | 适用 |
|---|---|---|---|---|---|
| **PostgreSQL + pgvector + ParadeDB(pg_search/BM25)** | pgvector（HNSW/IVFFlat） | 真 BM25 | **同库 SQL，最干净** | 一个库 | 首选 |
| PostgreSQL + pgvector + tsvector(zhparser) | 同上 | ts_rank 近似（非 BM25） | 同库 | 一个库 | 降级方案 |
| **Qdrant** | 原生 HNSW + filterable HNSW | 原生 sparse vector | payload filter，过滤下推 | 中 | 横向扩展首选 |
| **Milvus** | 分布式 | sparse + dense 原生 hybrid | scalar filter / partition | 高 | 亿级、多租户 |
| Elasticsearch / OpenSearch | kNN | **BM25 最强** | filter context | 中高 | 已有 ES 集群时 |
| Redis Stack | RediSearch 向量 | 全文 | filter | 低 | 小规模、缓存场景 |

**结论（当前规模）**：**PostgreSQL 单库方案**。
理由三条：
1. 权限过滤、向量检索、BM25、业务元数据在同一个事务边界内，`acl_jsonb` 条件可以和向量查询写在同一条 SQL，
   **不存在"检索完再过滤"的窗口**——这是本项目最核心的安全诉求。
2. 你的团队已经在用 MySQL，PG 的学习与运维成本可接受，不需要新增中间件。
3. 50w~200w chunk、HNSW 在这个量级完全够用（单机 PG 亿级向量以内都不是瓶颈）。

**必须知道的坑**：
- pgvector 的 HNSW 是近似索引，带强过滤条件时可能召回不足（候选集被过滤光）。
  0.8+ 的 iterative index scan 可缓解；否则对受限内容单独分区（`kb_chunk_restricted`）+ 小索引，
  两条查询各自近似、再合并结果。注意**不是**把权限展开成 id 清单去缩小范围——那会退回 05 §2.1 的老路。
- PostgreSQL 原生 `ts_rank` **不是 BM25**。要真 BM25 用 ParadeDB `pg_search`，或接受 ts_rank 的近似（效果差 3~5 个点）。
- 中文分词必须装 `zhparser` 或 `pg_jieba`，默认分词对中文近乎不可用。

**换型触发条件**（写进 ADR，面试可直接讲）：
- chunk > 500w 或 P95 检索 > 300ms → 迁 Qdrant（保留 PG 做元数据与 ACL，双写靠 outbox）
- 需要按租户物理隔离 / 单集群多业务 → Milvus partition key
- 已有 ES 且团队熟 → 直接 ES，稠密用 kNN + filter context

## 3. Embedding 与重排

| 模型 | 维度 | 特点 | 备注 |
|---|---|---|---|
| **BGE-M3** | 1024 | dense + sparse + multi-vector 三合一，8192 上下文 | **只有自托管才暴露 sparse**；托管 API 通常只回 dense |
| bge-large-zh-v1.5 | 1024 | 中文强、成熟 | 只有 dense |
| Qwen3-Embedding (0.6B/4B) | 1024/2560 | MTEB 表现强，多语言 | 显存要求更高 |
| 在线 API（如 text-embedding-3-large） | 3072 | 免运维 | 国外服务，数据出域，不选 |
| **BGE-M3 的托管 API**（硅基流动 / 百炼等） | 1024 | 免 GPU、**只返回 dense** | 起步首选：国内可合规、省运维 |

**结论：dense 用 BGE-M3，稀疏走 PG 的 BM25，不做"单模型双输出"。**

这条要解释清楚，因为它看起来放弃了 BGE-M3 的优势：

- BGE-M3 确实能同时输出 dense + sparse + ColBERT，但**这是模型能力，不是所有部署方式都能暴露**。
  绝大多数 embedding API 只返回 dense；要用 sparse 就得自托管 GPU。
- 而稀疏那一路我本来就要用 PG 的 ParadeDB 真 BM25（见第 2 节），**它已经能提供关键词召回**。
  为了"用上 BGE 的 sparse"去背一个 GPU 集群，不划算。
- 自托管的正确理由是**数据不出域**和**量大后边际成本更低**，不是 sparse。这两个理由在 M4 之后再考虑。

所以分两阶段：**起步用 BGE-M3 托管 API + PG BM25；机密文档或量级上来后，再自托管 BGE-M3 换掉 API。**
两者对上层是同一个 `ModelProvider` 接口，切换只改配置（见 `08-模型接入方案.md`）。

**必须锁死的三件事**：`embed_model_id`、`embed_version`、`dim` 写进索引元表与行级字段，
检索前强制校验，不一致**抛错而不是降级**——建库和查询用了不同模型不会报错，只会悄悄变差。

**重排**：`bge-reranker-v2-m3`，对 top 50 重排取 top 8。CPU 上 50 条约 300~600ms，可接受；
若延迟紧张，只对"证据不足"的路径启用重排（Agentic RAG 的天然优势：按需付费）。

**换型触发条件**：黄金集 Recall@10 < 0.85 且换分块策略无效 → 说明是语义匹配能力问题 → 升级 Qwen3-Embedding。
换模型 = 全库重刷，必须走双写过渡（细节见 `08-模型接入方案.md` §3.3）。

## 4. GraphRAG

| 方案 | 做法 | 成本 | 可控性 |
|---|---|---|---|
| 微软 GraphRAG | LLM 抽实体 → Leiden 社区 → 社区摘要 → global/local search | **极高**（索引期 token 爆炸） | 中 |
| LightRAG | 双层检索（实体级 + 主题级），支持增量更新 | 中 | 中 |
| nano-graphrag | 极简参考实现，代码可读 | 低 | 高 |
| 自建 Neo4j + 规则/词典 + LLM 补抽 | 自己定实体类型和关系 schema | 可控 | **最高** |

**结论**：**自建 Neo4j，参考 LightRAG 的双层检索思路，不直接套微软 GraphRAG。**

理由：
1. 你的领域实体是收敛的（部门、岗位、系统、流程、单据、异常类型、政策条款），
   **词典 + 规则能覆盖 70%**，LLM 只补长尾。纯 LLM 抽取的成本和噪声都不划算。
2. 微软 GraphRAG 全量重建图，文档一变更就要重跑，企业知识库是持续更新的，增量能力是刚需。
3. 只对**制度/流程/关系类子集**建图（约占文档 20%），其余仍走向量。全量建图是浪费。

**检索路由**：
- 全局性问题（"公司整体的报销流程分几层"）→ 社区摘要聚合
- 局部性问题（"XX 系统的负责人是谁"）→ 实体邻域 2 跳
- 结果必须带 `MENTIONED_IN` 回到 chunk，再按 ACL 过滤——**图检索同样不能绕过权限**

**成本核算要写进报告**：建图 token 成本 / 文档、增量更新耗时、社区摘要存储量。
这是面试里"你做过 GraphRAG 预研"和"你看过 GraphRAG 文章"的分水岭。

## 5. 编排框架

| 方案 | 模型 | 适合 | 不适合 |
|---|---|---|---|
| **LangGraph** | 显式状态图 + checkpoint + interrupt | 需要可控、可观测、可中断恢复的生产级流程 | 简单线性链路（过度设计） |
| LangChain Agents | `create_agent` 高层封装 | 快速起步 | 复杂分支、需要精细控制 |
| DeepAgents | 内置 planning / subagents / 文件系统后端 / middleware | 长任务、深度研究类 | 需要精确掌控每一步的业务流程 |
| AutoGen | 对话式多智能体 | 研究、开放式协作 | 生产延迟敏感 |
| CrewAI | 角色扮演 + 任务流水线 | 快速原型、内容生产 | 复杂状态管理 |
| Spring AI / langchain4j | Java 原生 | Java 团队、轻量 tool calling | 复杂图编排、评测生态弱 |

**结论**：**LangGraph 作为唯一编排内核**（Agentic RAG 那张图就是它的用武之地）。
Java 侧不做 Agent 推理，只用 Spring AI 做极轻量的工具调用（如果有），
原因直说：Python 的模型 SDK、评测库（RAGAS/DeepEval）、可观测生态领先 Java 一代，
而权限与事务逻辑又必须在 Java——所以**按能力切分，而不是按语言统一**。

**为什么不用 DeepAgents**：它的 planning/subagent 是黑盒封装，你正好要"讲清楚 planning 和 multi-agent 怎么实现"，
用 LangGraph 显式画出来更有说服力；DeepAgents 可以作为对照组（"我们也试过，封装度高但可控性差"）。

## 6. 评测工具链

| 工具 | 定位 | 用在哪 |
|---|---|---|
| **RAGAS** | RAG 专用指标（faithfulness / context precision / context recall / answer relevancy） | 生成质量 |
| **DeepEval** | pytest 风格 + CI 集成 | 回归测试、门禁 |
| promptfoo | 配置化对比实验 | 快速 A/B prompt |
| 自研 runner | 调度、并发、落库、成本统计 | **主力** |

**结论**：**自研 runner 做骨架，RAGAS + DeepEval 只当"算子"调用。**
理由：现成工具解决不了你的三件事——权限越权集、跨版本配置对比、错误归因到具体 stage。
把 RAGAS 当指标计算函数用，别当平台用。详见 `03-评测体系.md`。

## 7. 可观测

| 方案 | 特点 |
|---|---|
| **Langfuse**（自托管） | 与 LangGraph 天然契合，trace/span 层级清晰，可自建评测，MIT 部分功能开源 |
| LangSmith | 体验最好，SaaS、数据出域 |
| Arize Phoenix | OTel 原生，自托管 |
| OTel + Grafana Tempo | 通用、可控，但 LLM 语义要看自己定义 |

**结论**：**OpenTelemetry 埋点 + Langfuse 自托管**。埋点用 OTel 标准，避免锁定；

## 8. 部署

**Docker Compose**，不上 k8s（20 并发上 k8s 是给自己找事）。

> 下面是**完整形态**的编排（生产参考）。M0~M2 实际只起 1 个 PG 容器 + 3 个进程，
> 见 `10-部署形态与硬件配置.md`；两者是同一份设计的收敛关系，不是两套方案。

```
deploy/
├─ docker-compose.yml      # api, worker, pg, neo4j, mysql, redis, minio, langfuse, prom
├─ init/                   # pg 扩展(zhparser/pg_search)、建表、种子数据
├─ .env.example
└─ loadtest/               # k6 脚本：20 并发混合场景
```

**灰度**：模型/策略双版本并行（`config_version` 打在每个 trace 上），评测集上跑赢了才切流量。

**同镜像两入口**：

```dockerfile
# 一个镜像
ENTRYPOINT ["sh", "-c", "python -m api.main_${DOMAIN}"]
# knowledge 容器：DOMAIN=knowledge, port 8001
# fulfillment 容器：DOMAIN=fulfillment, port 8002
```

好处：Runtime / 评测 / 观测三块 100% 共享，但两个域独立扩缩容、独立发布、独立故障隔离。
面试常被问"为什么不做成一个服务"——答案是资源画像不同（知识域吃嵌入与检索，排障域吃并发工具调用），
且一个域发版不该影响另一个。

## 9. 排障域：工具与数据源选型

排障域的技术难点不在模型，在**如何让 Agent 安全地接触生产数据**。

### 9.1 数据访问

| 需要 | 方案 | 理由 |
|---|---|---|
| 订单/库存查询 | **独立只读账号** + 视图层（不暴露原表） | 从权限上杜绝写操作，不依赖 prompt 约束 |
| 指标聚合查询 | NL2SQL（仅限白名单视图）+ SQL Guard | 见下 |
| 日志检索 | 复用知识域的检索底座（同一套 embedding + 索引） | 避免造第二套检索系统 |
| 规则/政策判定 | 规则引擎（Drools 或轻量 Python 规则表） | 确定性逻辑不该交给模型 |

**SQL Guard 的四道闸**（这段面试很能讲）：
1. **语法层**：只允许 `SELECT`，解析 AST 拒绝 DDL/DML/多语句
2. **对象层**：表白名单 + 强制带分区/时间条件（防全表扫）
3. **执行层**：`LIMIT` 上限、查询超时、只读副本连接
4. **结果层**：行数上限、敏感字段脱敏、成本估算超阈值直接拒绝

### 9.2 工具调用框架

不引入额外框架，直接在 Runtime 里实现（因为要精确控制）：

```python
@tool(name="lookup_order", cost=1, timeout=3, idempotent=True)
def lookup_order(order_id: str) -> OrderFacts:
    """查询订单事实。仅只读。"""
```

必须支持的六件事（每一条都是踩过坑才会想到的）：
- **schema 校验**：模型给的参数先校验再接，别直接 `**kwargs`
- **超时与重试**：只对幂等工具重试，非幂等直接失败
- **结果压缩**：大结果先摘要再喂模型（别把 500 行 JSON 塞进上下文）
- **错误回灌**：工具异常要结构化回给模型，让它换策略而不是崩掉
- **预算计量**：每次调用计 token 与耗时，喂给停止条件
- **副作用隔离**：写操作只产出 `propose_action`，永不直接执行

### 9.3 人机协作（HITL）

用 LangGraph 的 `interrupt` + `checkpointer`：
动作建议 → 图暂停并落 checkpoint → 审批结果通过 **REST webhook** 回灌 → `Command(resume=...)` 续跑。

注意：审批回灌是**应用（Java 审批中心）调 agent**，走 REST webhook，不是 A2A。
A2A 的 Task 状态只用于 knowledge ↔ fulfillment 之间的委派（见 ADR-0002）。

选它而不是自研状态保存的理由：中断点可能在任何节点，checkpoint 天然支持任意点恢复。

## 10. 双域共用的取舍

| 组件 | 共享 | 不共享 | 原因 |
|---|---|---|---|
| 图内核 | ✅ | | 状态机模板与 checkpointer 与域无关 |
| 工具注册表 | ✅ | | 工具实现各自写，注册机制共用 |
| 记忆 | ✅ 机制 | ❌ 数据 | namespace 隔离，知识域存偏好，排障域存工单 |
| 护栏 | ✅ 机制 | ❌ 策略 | 动作白名单、注入检测开关按域配置 |
| 评测框架 | ✅ | ❌ 数据集与指标 | 知识域看 Recall/faithfulness，排障域看根因准确率 |
| 检索引擎 | ✅ | | 排障域的日志检索复用同一套底座 |

> 这张表就是"平台化"的说明书。面试问"你怎么判断哪些该复用"——
> 答：**机制复用，策略隔离；数据隔离，能力复用。**
