# 04 里程碑与面试映射

> 定位：**面试作品集项目**。目标是"能被追问到底、能给出数据、能讲清取舍"，
> 不是"功能全"。所以每个里程碑的验收标准都是**可演示 + 可量化**，而不是"代码写完了"。

---

## 1. 时间与精力假设

业余投入每周 8~10 小时，总计约 11 周。若时间紧张，见第 4 节的"最小可讲版本"。

数据来源建议：**用公开文档 + 自造数据**（开源项目的运维手册、公开的制度模板、自己构造的工单记录）。
不要用公司真实文档与业务数据——作品集项目一旦涉及内部数据，面试时反而不好讲。

---

## 2. 里程碑拆解

### M0 骨架与抽象验证（第 1 周）— 最容易做错的一步

| 任务 | 产出 |
|---|---|
| 数据模型定稿（文档/ACL/chunk/父子块/action_request） | `db/schema.sql` + ER 图 |
| Compose 起依赖（**M0 只起 PG 一个容器**：`paradedb` 带 pgvector + pg_search；mysql / neo4j / redis / minio / langfuse 按里程碑渐进加入） | `make up` 可用，**常驻约 3GB** |
| Runtime 骨架：图模板、工具注册表、记忆接口、护栏接口、OTel 埋点 | `runtime/` |
| **Domain Pack 配置加载 + 两个最小图**（知识域返回固定答案，排障域返回固定诊断） | 两入口 `/healthz` + 一个假链路 |
| Java 侧：上传 + ACL 计算 + Agent 网关（REST/SSE）骨架 | 三个接口 + 单测 |
| **服务间契约**：`api/openapi.yaml` + 双端 codegen（pydantic / Java DTO）+ golden fixtures | 契约冻结 v1.0.0 |
| **Prompt 登记表**：`prompts/manifest.yaml` + 渲染函数 + 变量校验 + `prompt_set_sha` | 渲染单测进 CI |

**为什么 M0 就要跑两个域**：抽象只能被两个实现证伪。
如果先做完整个知识域再加排障域，你会发现 Runtime 里到处是知识域假设（比如"必须要检索"），
重构成本远高于现在多花两天。

**目标运行环境**：**16GB 内存、无独显的一台普通电脑**（详见 `10-部署形态与硬件配置.md`）。
所以 M0 的判定标准不是"容器都起来了"，而是"**在一个 PG 容器 + 三个进程、模型全走 API 的前提下跑通两个假链路**"。
一开始就把依赖压到最简，后面每加一个组件都必须能说出它的不可替代性——这条纪律比 M0 的功能本身更重要。

**验收**：`DOMAIN=knowledge` 和 `DOMAIN=fulfillment` 两个容器从同一镜像启动，
各自跑通一条假链路，trace 在 Langfuse 里都能看到。

### M1 知识域窄链路（第 2~3 周）

| 任务 | 产出 |
|---|---|
| 解析：**L0 直取 + Docling**（覆盖约 80%）+ 统一 IR + `parse_report` | 100 份文档解析报告 |
| 分块：语义分块 + 父子块 + ACL 快照写入 | chunk 落库 |
| 混合检索：dense + BM25 + RRF + rerank | 检索服务 + 单测 |
| 管线式 RAG（先不做 agentic） | 端到端可回答 |
| 评测：黄金集 150 条 + 检索层指标跑批 | 第一份基线报告 |
| 埋点：`retrieval.*` / `acl.*` 属性补齐 | 失败 case 能自动判出 E3 还是 E4（见 `14` §11） |

**验收**：解析成功率 ≥ 95%，Recall@10 ≥ 0.85，回答带可定位到页的引用。

> 这阶段最重要，别跳。**没有 M1 的基线，M2 的"提升"无从谈起。**

### M2 知识域 Agentic RAG（第 4~5 周）

| 任务 | 产出 |
|---|---|
| 状态机：analyze/plan/retrieve/grade/rewrite/synthesize/verify/abstain | 图定义 + 节点单测 |
| 证据充分性打分 + 停止条件 + 预算 | 配置化参数 |
| 引用校验 + 拒答路径 | 无答案集指标 |
| 评测扩到 300 条 + 配置版本化 + 落库 | 对比报告（管线式 vs agentic） |
| 记忆：thread checkpoint + 摘要压缩 | 多轮不失忆 |

**验收**：正确率 +8pt 以上，成本增幅 < 40%，平均检索轮次 ≤ 1.6。

### M3 知识域 GraphRAG（第 6 周）

| 任务 | 产出 |
|---|---|
| 实体/关系 schema（部门/岗位/系统/流程/单据/异常/条款） | schema 文档 |
| 词典 + 规则抽取 + LLM 补抽 + 实体消歧 | 抽取 pipeline |
| 入 Neo4j + `MENTIONED_IN` 溯源 + 增量更新 | 图库 |
| Leiden 社区 + 社区摘要（仅制度/流程子集，约 20% 文档） | 摘要表 |
| 图检索路由 + 权限过滤 + 回落 | Graph Agent |
| 成本核算（建图 token / 文档、增量耗时） | 成本表 |

**验收**：多跳/关系类子集 +10pt，图检索结果 100% 可溯源且不越权。

### M4 排障域（第 7~8 周）

| 任务 | 产出 |
|---|---|
| 诊断图：analyze_symptom / build_hypotheses / gather_evidence / evaluate / propose_action | 图定义 |
| 五个工具 + 六项治理（schema/超时/重试/压缩/错误回灌/预算） | `domains/fulfillment/tools/` |
| 只读数据源 + SQL Guard 四道闸 | 查询服务 |
| 情景记忆：历史工单相似度召回做假设先验 | memory 实现 |
| HITL：interrupt + checkpoint + 审批回灌 | 审批链路 |
| 评测：replay 100 + action_safety 50 | 排障基线报告 |

**验收**：Root Cause Top-1 ≥ 70%、Top-3 ≥ 88%，危险动作出现率 = 0，单次诊断 P95 < 30s。

### M5 A2A 跨域 + 评测平台统一（第 9 周）

| 任务 | 产出 |
|---|---|
| 两个 Agent Card + Task 状态机 + Artifact | A2A 服务端 |
| A2A client：发 Task、处理 input-required、超时降级 | 客户端 |
| 跨进程 trace_id 透传 + 一条完整回放 | 端到端 demo |
| 评测框架双域适配 + 对比视图 + 自动归因（E1~E10 / F1~F7） | 归因报告 |
| CI 门禁：越权 = 0、危险动作 = 0 才允许合并 | CI 配置 |

**验收**：一次提问跨越 2 个进程；任一服务宕机时另一端优雅降级；越权与危险动作两条红线在 CI 里拦截。

### M6 部署与压测（第 10~11 周）

| 任务 | 产出 |
|---|---|
| Compose 全量编排 + 初始化 + 一键起 | `make up` |
| k6 压测：知识域 20 并发 + 排障域 5 并发 | 压测报告 |
| 降级演练：任一依赖宕机 | 演练记录 |
| 双版本灰度（config_version 切流） | 灰度脚本 |
| 架构决策记录（ADR） | `docs/adr/` |

**验收**：知识域 20 并发 P95 < 4s；任一依赖宕机不整体不可用；资源占用可核算。

## 3. 双域工作量对照

| 模块 | 知识域 | 排障域 | 共享 |
|---|---|---|---|
| 解析与入库 | 重（60%） | — | — |
| 检索 | 重（混合+图谱） | 复用日志检索 | 底座 |
| 图编排 | 中 | 中 | 内核 |
| 工具治理 | 轻 | 重 | 注册表 |
| 记忆 | 中（偏好） | 中（情景） | 机制 |
| 评测 | 重（四套集） | 重（回放集） | 框架 |
| 部署 | 中 | 中 | 镜像 |

**结论**：知识域约 60% 工作量，排障域约 30%，共享内核约 10%（但内核的质量决定后两者的上限）。

## 4. 最小可讲版本（如果只有 6 周）

时间不够时，砍功能不砍证据链：

| 保留 | 砍掉 |
|---|---|
| M0 抽象验证 + M1 窄链路 + M2 Agentic RAG | M3 GraphRAG 全量 → 改成"20 篇文档的图谱预研 + 对比数据" |
| 排障域只做"订单查询 + 日志检索 + 假设验证"三个工具 | 砍 HITL 与 SQL Guard 的完整实现，保留设计文档 |
| 越权集 80 + 黄金集 150 | 砍注入集、无答案集（保留 20 条 smoke） |
| Compose 部署 + 一次压测 | 砍灰度 |

**砍掉的东西要在面试里主动说**："GraphRAG 我做了 20 篇文档的预研，成本是 X，
结论是只在关系类子集上启用——完整上线没做，因为边际收益不抵成本。"
**主动说没做什么，比假装什么都做了更可信。**

## 5. 面试叙事

### 5.1 三分钟陈述

```
背景（20s）
  企业里两类问题最耗时：一类是"制度怎么规定"，散在几千份 PDF/Word 里；
  一类是"这单为什么卡住了"，要在订单、日志、规则之间来回翻。
  我原来的做法是把问题转发给第三方平台，结果三个问题：解析质量不可控、
  权限只能事后裁剪、效果好坏无法归因。

判断（30s）
  我判断这两类问题的控制流根本不同：知识是广度优先的"检索-评估-再检索"，
  排障是深度优先的"假设-验证-排除"。但它们的运行时需求高度重合：
  都要工具调用、都要记忆、都要护栏、都要被评测。
  所以我做的不是一个问答系统，而是一个运行时 + 两个域。

做法（90s）
  运行时与域解耦：域用配置注入工具集、停止条件、护栏策略，运行时提供图内核、
  工具注册表、记忆、观测。同一镜像两个入口，代码复用约七成，但独立扩缩容。
  两个域之间用 A2A 而不是函数调用——因为它们的数据源、资源画像、故障域都不同。
  知识域的关键设计是权限条件下推到检索语句里，越权泄漏率做成 CI 门禁；
  排障域的关键设计是写操作零直通，只产出待审批动作。

结果（30s）
  知识域 Recall@10 0.85→0.91，任务成功率 71%→84%，关系类子集 62%→79%；
  排障域根因 Top-1 70%、Top-3 88%，危险动作 0；
  越权泄漏 0；知识域 20 并发 P95 4 秒内。

取舍（20s）
  Agentic 成本 1.9 倍，靠意图分流压回 1.4 倍；GraphRAG 只对 20% 文档建图；
  没上 k8s，因为 20 并发下收益不成立。
```

### 5.2 五句最有杀伤力的话

1. "权限不是检索之后的一个 if，而是检索语句的一部分。"
2. "我做了两个域，不是因为想炫技，是因为一个域测不出抽象成不成立。"
3. "域之间走 A2A，不是我选了协议，是它们的故障域本来就该分开。"
4. "同一个评测框架，两套指标插件，两套归因分类法——我做的不是跑评测，是评测平台。"
5. "写操作在排障域里是零直通的，Agent 只有提议权，没有执行权。"

### 5.3 高频追问与回答要点

**Q：双域会不会两个都做不深？**
> 会，所以我明确分工：知识域做到能出数据（解析质量、召回、图谱增量、Agentic 对比），
> 排障域做到机制完整（工具治理、假设验证、HITL、A2A）但不追求场景覆盖。
> 判断标准是 JD：第 3 条要深度，第 4 条要广度。

**Q：为什么不用一个 Agent 加两套 prompt？**
> 试过。控制流不同——知识域需要"证据不够就再检索"，排障域需要"允许证伪并切换假设"，
> 塞进一张图会让停止条件互相打架。而且工具集差异大，单 agent 的工具选择准确率明显下降。

**Q：A2A 和 MCP 混了吗？**
> 没混，而且我按四层切开：函数调用（进程内）、MCP（agent 调工具，检索和查库都走这个）、
> REST + SSE（应用调 agent，Java 网关就是这一层）、A2A（agent 调 agent，只用在知识域委派排障域）。
> 我早期把"Java 调 Python"也标成 A2A，那是错的——Java 那层没有 Agent Card，不是 agent。

**Q：两个 agent 都是你写的，用 A2A 不是过度设计吗？**
> 部分成立，我承认。单进程内 LangGraph 编排更省，这也是业界共识。
> 我用它的理由是两条能被验证的：诊断是 30 秒、多步、可能中途要问用户的长任务，需要可回放的
> Task 状态机和中断续跑；排障域不可用时知识域要降级，这需要一个显式契约才写得出来。
> 我买的不是通信，是状态机语义和降级契约。如果是生产环境、两域确实同团队维护、不要求独立部署，
> 我会退回编排框架。

**Q：你怎么证明评测集不是自己刷出来的？**
> 三个手段：一是 20% holdout 不参与调参；二是题目来源 40% 来自真实日志（或真实工单回放）；
> 三是 judge 模型做了人工校准，kappa 低于 0.7 就换。

**Q：这套东西搬到生产要改什么？**
> 权限引擎要接公司统一身份；解析要加 GPU 与队列；评测要做离线+在线双轨
> （线上抽样进评测池）；还需要成本熔断和配额。这些我留了接口，但没实现——作品集项目的边界。

**Q：为什么 Java + Python 双服务，不统一一种语言？**
> 权限与事务逻辑在 Java 侧是既有能力，模型 SDK 与评测生态在 Python 侧更成熟。
> 按能力切分而不是按语言统一，代价是多一层 HTTP 边界，收益是两边都用最合适的工具。
> 这个代价我认，因为 Java ↔ Python 之间是**应用调 agent**，用普通 REST + SSE 就够，
> schema 用 OpenAPI 和 pydantic 双向约束；A2A 只用在真正对等的 agent 之间。

## 6. 风险与取舍（主动讲）

| 风险 | 应对 |
|---|---|
| 双域工作量失控 | 主次分明，知识域深、排障域完整但克制；有"最小可讲版本"预案 |
| GraphRAG 成本失控 | 只对 20% 文档子集建图，增量更新，成本单独核算并写进报告 |
| Agentic 延迟高 | 意图分流 + 证据充分即停 + 首 token 先出引用骨架 |
| 评测集过拟合 | 20% holdout + 定期从线上日志补题 |
| A2A 增加故障面 | 全链路超时与降级，对方不可用时回落"仅文档答案 + 数据不可得提示" |
| 双写一致性（MySQL ↔ PG） | outbox 表 + 幂等消费 + 每日对账 |

## 7. 简历写法

正式版本在 `resume/resume.tex`（本项目排在项目经历第一位）。写作口径：

> **KnowOps Agent｜权限感知的双域 Agent 中台**（个人项目 · Java + Python）
> 抽象出域无关的 Agent 运行时（图模板/工具注册表/记忆/护栏/观测/评测适配器），以 Domain Pack 配置化支撑
> 知识问答与履约排障两个业务域；知识域把 ACL 条件下推进检索语句，越权集做成 CI 阻断门禁；
> 排障域实现假设验证式诊断与写操作 HITL 审批；跨域用 A2A 而非函数调用。
> 自建四套评测集、两套错误分类法与配置快照版本化，报告强制分维度。

**三条写作纪律**（避免简历被追问时露馅）：

1. **不写没跑出来的数字**。当前文档里的 Accuracy/Recall/延迟都是**规划目标**，
   简历里只以"验收口径"出现（如"以 20 并发 P95 < 4s 为验收标准"），不写成"实测提升 X%"。
   跑完 M1 之后，再把实测值替换进去。
2. **写机制，不写名词**。"权限条件下推"是可追问的机制，"用了 GraphRAG"只是名词。
   简历上每一个技术名词，都要能在面试里撑住三层追问（是什么/为什么/代价）。
3. **主动写"没做什么"**。比如"GraphRAG 只在 20% 文档上启用，因为建图成本是切块的 3~5 倍"——
   这句比"实现了 GraphRAG"更有说服力，因为它证明你算过账。

## 8. 现在就能开始的三件事

1. **定 Domain Pack 的接口**（域要暴露哪些字段给运行时）——它决定了后面能不能真的复用。
2. **攒 150 条知识域评测题**——看文档时顺手出，不用等系统搭好。
3. **跑通一份 PDF 的解析质量报告**——解析是地基，地基歪了上面全歪。
