# 模型接入方案

三类模型（生成 / 向量化 / 解析）的接入方式**不能一刀切**，因为它们的约束完全不同。
这份文档给出接入矩阵、具体配置、以及必须提前解决的四个坑。

> **当前生效的决策：除解析外全部走线上 API**（`docs/adr/0003-模型默认走线上API.md`）。
> 可执行配置在 `config/models.yaml`，密钥模板在 `config/.env.example`。
> 本文档保留"为什么这么分级"的论证，以及未来切自托管时要怎么切。

---

## 1. 一张表说清三类模型怎么接

| 类别 | 调用频次 | 能否调 API | 建议 | 决定性约束 |
|---|---|---|---|---|
| **LLM**（生成 / 判断 / 抽取） | 每请求数次 | ✅ 完全可以 | **优先 API** | 数据出域、延迟、成本 |
| **Embedding**（向量化） | 每 chunk 一次（入库）+ 每查询一次 | ✅ 可以，但**只给 dense** | **起步 API，量级上来转自托管** | **建库与查询必须同模型同版本**，换模型要全库重刷 |
| **OCR / 版面解析** | 每页一次（仅入库） | ✅ MinerU 有官方 API；PyMuPDF/Docling 没有 | **全部本地** | 要版面结构 / 坐标 / 表格；原文不出域 |

一句话：**LLM 走 API，解析全部本地，Embedding 看量级。** 理由不是"自研更酷"：
解析的**失败代价**（结构错→下游切块全错）和 Embedding 的**一致性要求**（建库与查询必须同源）都远高于 LLM。

> **三处措辞必须说准，否则会误导决策**（详见 `10-部署形态与硬件配置.md`、`09-文档解析设计.md` 5.6）：
> ① **"自托管"不等于"需要 GPU"**。MinerU 的管道后端在 CPU 上可跑（2~10 秒/页），
> 解析是入库时的一次性开销、不在请求链路上，所以慢不等于不可用；
> ② **"解析能不能上云"只有一个真实选项**。PyMuPDF / pdfplumber / Camelot 是纯库、没有线上形态；
> Docling 只有自托管 `docling-serve`（HTTP 壳，不解决算力），没有公开 SaaS；
> 只有 MinerU 有官方在线 API——但**本项目默认不用**，`parse_mode: local`，
> 因为省下的 3GB 内存不值"原文出域 + 多一个 key + 多一层配额 + 断网不能用"。
> 开关留着（`local | hybrid`），切的时候改一个值；
> ③ **Embedding 自托管不是当前最优解**。起步量级下 API 更便宜（整套开发期约 150~300 元），
> 自托管的正当理由只有"数据涉密"和"chunk 过 50 万"两条，写成了触发条件而不是默认选择。
> 更关键的是：**本项目的核心命题全在数据库里（鉴权下推、RRF 融合、归因），不在模型里**，
> 所以模型放哪不影响项目成立。

## 2. LLM 接入

### 2.1 为什么 DeepSeek 好用：协议兼容

DeepSeek 提供 OpenAI 兼容接口，所以 chat 这一路**一套 SDK 通吃**，切换模型只改配置：

```yaml
# config/models.yaml
providers:
  deepseek:                        # kind: openai_compat
    base_url: https://api.deepseek.com
    api_key: ${DEEPSEEK_API_KEY}
```

这意味着 `langchain_openai.ChatOpenAI(base_url=...)` 或 `openai.OpenAI(base_url=...)` 直接可用，
不需要为每家写适配器。这是选择"OpenAI 兼容协议"作为抽象基线的唯一理由。

> **但这个"通吃"有例外，而且例外很关键：rerank 没有统一标准。**
> chat 和 embedding 基本都兼容 OpenAI 规范，rerank 却各家一套路径
> （硅基流动 `/v1/rerank`、Cohere `/rerank`、Jina 又不同）。
> 所以 `ModelProvider` 里 **rerank 必须独立建模走独立适配器**，
> 不能假设"配个 base_url 就能用"。这条如果不提前拆开，换供应商时会连带改业务代码。

**模型名会变，而且变过**（2026-11 核实）：`deepseek-chat` / `deepseek-reasoner`
已于 2026-07-24 退役，请求直接失败。当前可用 `deepseek-v4-flash`（新别名 `deepseek-flash`
指向 V4.1-Flash）与 `deepseek-v4-pro`。`base_url` 和 SDK 全部不变，只有模型字符串变。
**所以模型名绝不能硬编码在代码里，只能出现在 `config/models.yaml`** ——
这是配置驱动的一个现实理由，不是洁癖。

### 2.2 按角色分配模型（不要一个模型打天下）

| 角色 | 用途 | 建议档位 | 理由 |
|---|---|---|---|
| **生成** | 最终答案 | 强模型（DeepSeek-V4.1-Flash 级） | 直接对用户，质量优先 |
| **规划** | 假设生成、查询改写 | 强模型 | 规划错一步，后面全错 |
| **判断** | relevance / grade / 意图分流 | **小快模型** | 高频、判断简单，用大模型是浪费 |
| **抽取** | 实体关系抽取（建图） | 中档 | 量大，成本敏感 |
| **Judge** | 评测打分 | **必须与生成模型不同** | 同模型自评会系统性偏高 |

**Judge 必须异源**：如果生成和打分都是 DeepSeek，模型会偏好自己的输出风格， faithfulness 虚高 5~10 个点。评测体系的可信度从这里开始。

### 2.3 API 的三个硬约束

| 约束 | 应对 |
|---|---|
| 限流（RPM/TPM） | 客户端令牌桶 + 指数退避；入库任务走队列削峰 |
| 超时 | 生成类 60s，判断类 10s；超时降级到备用 provider |
| 成本不可控 | 每 trace 记 token；日预算熔断；判断类结果缓存 |

## 3. Embedding 接入（坑最多，重点看）

### 3.1 先解决一个文档矛盾

`02-技术选型.md` 说"BGE-M3 单模型双输出（dense + sparse）"。
但**绝大多数 embedding API 只返回 dense 向量，不返回 sparse 权重和 ColBERT 多向量**——
这是 BGE-M3 的模型能力，不是所有部署方式都能暴露出来。

所以两条路必须选一条，不能含糊：

| 路线 | dense 来源 | sparse/关键词来源 | 评价 |
|---|---|---|---|
| **A. 自托管 BGE-M3** | BGE-M3 | BGE-M3 自带 sparse | 能力最全，但要独立推理服务（GPU 更快，CPU 可跑但慢） |
| **B. API 嵌入 + PG BM25**（推荐起步） | BGE-M3（API） | **ParadeDB 真 BM25** | 简单、够用、且 BM25 效果不输 BGE sparse |

**结论：起步走 B**。理由是我本来就要用 PG 的 BM25 做关键词那一路（见 `02` 第 2 节），
它已经能提供稀疏召回，**没必要为了"用上 BGE 的 sparse"而背上自托管 GPU**。
自托管的真正理由是**数据不出域**和**量大后成本更低**，不是 sparse。

> 这个判断很重要：不要为了一个你已经有替代方案的能力，去付一个不必要的运维成本。

### 3.2 必须锁死：模型 × 版本 × 维度

embedding 最致命的错误是**建库和查询用了不同模型**——不报错，只是召回悄悄变差，查起来极痛苦。

```python
# 每次检索前强制校验，不一致直接抛错，绝不降级
assert query_cfg.embed_model_id == index_meta.embed_model_id
assert query_cfg.embed_version == index_meta.embed_version
assert query_cfg.dim == index_meta.dim
```

三个字段都写进 `kb_chunk` 的元数据和索引元表：

```sql
kb_index_meta (embed_model_id, embed_version, dim, chunker_version, created_at)
kb_chunk      (..., embed_model_id, embed_version)   -- 行级冗余，便于混版检测
```

**为什么行级也要存**：迁移期会出现新旧向量混存，靠行级字段能查出"这条是哪个版本生成的"，
否则只能全表重建。

### 3.3 换模型 = 全库重刷，必须双写过渡

换 embedding 模型不是改个配置，是所有 chunk 重新嵌入。做法：

```
1. 新增 embed_version=2，双写：入库同时写 v1 与 v2 向量（两列或两表）
2. 后台批跑历史数据回填 v2
3. 评测集上比 v1 vs v2 的 Recall@10
4. 达标 → 读切到 v2，v1 保留 30 天
5. 清理 v1，重建索引
```

**维度变化不能只改字段**：1024 → 2560 意味着 HNSW 索引必须重建，且旧向量无法复用。
所以选模型时**维度要一次定对**，1024 是个安全选择。

### 3.4 嵌入缓存（省钱的必要手段）

同一段文本不重复嵌入。尤其是在重新解析、重建索引时，能省掉大部分调用：

```sql
embed_cache (content_hash PRIMARY KEY, model_id, embed_version, dense vector(1024), created_at)
```

`content_hash = sha256(规范化文本 + model_id + version)`。
**注意 hash 要含模型版本**，否则换模型后会命中旧向量——这是很隐蔽的错误。

### 3.5 重排（rerank）也是模型

召回 top-50 → rerank → top-5 喂模型。rerank 模型（如 bge-reranker）单独一类：

- 自托管：`bge-reranker-v2-m3`，与生成同机不同进程
- API：硅基流动等有 rerank 端点
- **降级**：rerank 不可用时跳过，直接用 RRF 融合结果（效果掉 3~5 点，但不阻塞）

## 4. OCR 与文档解析接入

### 4.1 先分清三件事

"OCR"常被误当成一个整体，实际是三段：

```
① 版面分析（Layout）  → 找出标题/段落/表格/图片/页眉页脚的区域和坐标
② 文字识别（OCR）     → 扫描件、图片里的字转文本
③ 结构还原（Parser）  → 按阅读顺序重建成 Markdown / IR，表格还原成结构
```

**云 OCR 一般只做 ②**，或者做 ①②但不保证 ③。而 RAG 最需要的恰恰是 ③——
因为分块要按章节、引用要能定位到页码、表格必须保持结构否则检索出来是乱的。

### 4.2 为什么不推荐纯云 OCR

| 问题 | 说明 |
|---|---|
| **数据出域** | 企业制度、合同、财务单据全文外传，合规上过不去 |
| **丢版面** | 只给纯文本，阅读顺序和段落边界丢失，分块质量骤降 |
| **表格还原差** | 大多返回文本流，行列结构没了，检索到表格等于废数据 |
| **坐标缺失** | 无法做引用定位（"第 3 页第 2 节"） |

### 4.3 采用方案

| 文档类型 | 处理 |
|---|---|
| 原生 PDF（有文字层，覆盖率 > 90%） | PyMuPDF 直接取文字层，**不走 OCR**（快且准，毫秒级） |
| PDF 覆盖率 40~90% | **Docling** parse（CPU，TableFormer 还原表格） |
| 扫描件 PDF / 图片（覆盖率 < 40%） | **MinerU** pipeline 后端，内置 PaddleOCR 识别 + 结构还原 |
| DOCX / PPTX / MD | Docling（不需要 OCR，且直接出统一 IR） |
| 中文复杂版面 / 复杂合并单元格 | MinerU 兜底（Docling 弱项） |
| 兜底 | 云端 OCR 仅用于"本地解析失败且用户接受出域"的场景，默认关闭 |

> **引擎分工已按硬件条件收敛**：Docling 是主力（MIT 许可 + 全格式 + 纯 CPU），
> MinerU 是兜底专家（只有中文复杂版面、扫描件、质量闸门不通过时出现）。
> 完整论证见 `09-文档解析设计.md` 第 5 节，可执行配置见 `config/parse.yaml`。

**关键区分：有文字层的 PDF 不要走 OCR。** 直接取文字层又快又准，OCR 反而引入错误。
判断依据是 PyMuPDF 抽出来的文本覆盖率 > 阈值。

### 4.4 解析质量必须量化（否则后面全在猜）

```sql
parse_report (doc_id, text_coverage, table_recall, empty_ratio,
              garbled_ratio, ocr_confidence, score, review_status)
```

低分文档进人工复核队列。**这一步不能省**——后面召回差的时候，你要能区分"是解析坏了还是检索坏了"。

## 5. 统一抽象层（避免被单一厂商锁死）

```python
class ModelProvider(Protocol):
    def chat(self, messages, *, model, temperature, timeout) -> ChatResult: ...
    def embed_dense(self, texts, *, model) -> list[list[float]]: ...
    def embed_sparse(self, texts, *, model) -> SparseVec | None: ...   # 可选能力
    def rerank(self, query, docs, *, model) -> list[float]: ...
    def ocr(self, image_bytes) -> OcrResult: ...
```

三个实现，配置切换：

| 实现 | 用于 | 说明 |
|---|---|---|
| `OpenAICompatProvider` | DeepSeek / 硅基流动 / 百炼 / 本地 vLLM | 都兼容 OpenAI 协议，一套代码 |
| `LocalProvider` | FlagEmbedding / TEI / MinerU | 自托管模型 |
| `MockProvider` | CI / 单测 | 返回确定性假数据，**保证测试不花钱、不联网** |

`MockProvider` 容易被忽略，但没有它 CI 就跑不起来（每次测试都真调 API 是不可接受的）。

配置引用 profile 名，不改代码：

```yaml
# domain.yaml
models:
  generate: deepseek/deepseek-v4-flash
  plan: deepseek/deepseek-v4-flash
  judge: siliconflow/<非DeepSeek强模型>   # 必须异源，同源会自评虚高
  embed: siliconflow/BAAI/bge-m3
  rerank: siliconflow/BAAI/bge-reranker-v2-m3
  parse: local/mineru
```

## 6. 成本结构（要能算出来）

| 环节 | 频次 | 主要成本 | 优化手段 |
|---|---|---|---|
| 解析 + OCR | 每页一次（入库） | GPU 时长 | 原生 PDF 跳过 OCR；解析结果缓存 |
| 嵌入 | 每 chunk 一次（入库） | API/GPU | `embed_cache`；只对变更文档重嵌 |
| 建图抽取 | 每 chunk 一次（20% 文档） | LLM token | 只对制度类建图；增量更新 |
| 生成 | 每请求 | LLM token | 意图分流省检索；语义缓存 |
| rerank | 每请求 | API/GPU | 只对 top-50 做，不扩到 top-200 |
| Judge | 评测批跑 | LLM token | 抽样；用小模型初筛 + 人工校准 |

**一次性成本**（建库）和**边际成本**（每查询）要分开报。
面试里能说清"10 万份文档首建约 X 元、每千次问答约 Y 元"，比说"成本可控"强得多。

## 7. 数据合规：决定能不能用云 API 的真正因素

| 文档密级 | LLM | Embedding | 解析 |
|---|---|---|---|
| 公开 | 云 API | 云 API | 云均可 |
| 内部 | 云 API（脱敏后） | **自托管** | 自托管 |
| 机密 | **自托管** | **自托管** | 自托管 |

原则：**原文最敏感，向量相对不敏感，但生成时的上下文最敏感。**

这里有个反直觉的点：embedding 出域看似只是传了文本，但**文本本身就是原文**——它不比生成更安全。
所以"embedding 可以随便用云 API，生成才要本地"是错误认知，两者敏感性一致。

## 8. 降级链（每个模型都要有 fallback）

| 失效 | 降级 |
|---|---|
| 主生成模型超时 / 限流 | 备用 provider（同档位）→ 更小模型 + 提示"回答质量可能下降" |
| rerank 不可用 | 跳过 rerank，用 RRF 融合结果 |
| embedding 服务不可用 | **查询侧退回纯 BM25**（可用但召回降），入库侧排队重试 |
| 解析失败 | 标记 `review_status=pending`，进人工队列，不阻塞其他文档 |
| 图库不可用 | 图谱那一路跳过，向量 + BM25 仍可答（GraphRAG 是增强不是必需） |

**关键设计：降级不能静默。** 每次降级都要在响应里带 `degraded: [rerank]`，并计入 trace。
静默降级是线上事故最常见的形态——功能还在跑，效果已经掉了一半，没人知道。

## 9. 面试口径

**Q：模型怎么接入的？**
> 分三类，因为约束不同。LLM 全走 API，DeepSeek 是 OpenAI 兼容协议，一套 SDK 就能切 provider；
> embedding 起步也走 API，因为量级不大时自托管收益抵不过运维成本；
> 解析全部本地，但不是一刀切：有文字层的走 PyMuPDF 直取（毫秒级），主力走 Docling
> （MIT、CPU 原生），啃不动的才给 MinerU 的管道后端。
> 为什么不上云？这三个里前两个根本没有线上形态——它们就是 Python 库；
> Docling 的 docling-serve 也只是 HTTP 壳，不解决算力。
> 只有 MinerU 有官方在线 API，但省下的 3GB 内存不值"原文出域 + 多一个 key + 配额约束"这几件事。
> 我把 `parse_mode: local | hybrid` 做成了配置开关，真需要的时候改一个值。
> 这三条路都走同一个 `ModelProvider` 接口，换位置只改配置。

**Q：本地什么环境？要不要私有部署？**
> 一台 16GB 无独显的机器，Docker 跑一个 PG（pgvector + pg_search），两个 Python agent 进程，
> 三个模型全走线上 API，整个环境常驻约 3GB。不需要私有部署任何模型。
> 因为项目的核心命题都在数据库里——鉴权下推、RRF 融合、归因分类，这些跟模型放哪没关系。
> 私有部署的触发条件我写下来了：数据涉密、或 chunk 过 50 万，就转自托管，而且先转 embedding 和解析，
> LLM 最后转——因为本地 7B 的质量撑不住生成这条链路。

**Q：BGE-M3 的 sparse 用上了吗？**
> 没用。BGE-M3 确实能出 dense + sparse，但 embedding API 基本只给 dense。
> 我没有为了这个能力去自托管，因为稀疏那一路我本来就用 PG 的 BM25，效果不输。
> 自托管的理由应该是数据不出域和量大后成本更低，不是为了一个已经有替代的能力。

**Q：怎么保证 embedding 一致？**
> 模型 id、版本、维度三个字段写进索引元表和行级字段，检索前强制校验，不一致直接抛错不降级。
> 换模型走双写过渡：新旧版本并存、批跑回填、评测集比 Recall、达标才切读。

**Q：OCR 用的什么？**
> 两层回答。先说"不用通用云 OCR"——云 OCR 大多只做文字识别，不保证阅读顺序和表格结构，
> 而 RAG 要的恰恰是结构：分块要按章节、引用要能定位页码、表格必须保结构。
> 再说分工是按页路由的：有文字层的 PDF 直接取文字层（PyMuPDF，毫秒级，不跑 OCR）；
> 中间态用 Docling（CPU 可跑、MIT 许可）；纯扫描件和中文复杂版面才交给 MinerU。
> 全部本地跑，MinerU 用管道后端（不用 VLM 后端，因为生成式会幻觉、且端到端结果无法归因）。
> 它本地跑的真实约束是内存：峰值 3~5GB，所以并发锁 1，而且首次要下 1~2GB 权重得提前预制。
> 但解析不在请求链路上，2~10 秒/页慢一点不影响问答延迟。

**Q：成本怎么控？**
> 一次性成本（建库）和边际成本（查询）分开算。省钱靠三件事：embed_cache 让同文本不重复嵌入、
> 意图分流跳过不必要的检索、判断类用小模型。
> 还有一条容易忽略：judge 模型必须和生成模型异源，否则自评会虚高 5~10 个点。
