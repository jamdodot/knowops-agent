# 13 服务间契约

> 为什么单独一篇：`04` §5.3 的 Q&A 只有一句"schema 用 OpenAPI 和 pydantic 双向约束"。
> 但 **Java 是真网关、Python 是真执行体，两个进程、两种语言、三种通道**——
> 这条边界不定死，就会出现"Java 多传一个字段，Python 静默忽略"这种没人发现的错。
>
> 本文是**契约的唯一真相源**，`api/openapi.yaml` 是它的可执行形态。
> 两者冲突时以 `openapi.yaml` 为准（机器可校验），并立刻回头改本文。

---

## 1. 边界：三条通道，一条都不是 A2A

| # | 通道 | 协议 | 调用方 → 被调方 | 是否 A2A |
|---|---|---|---|---|
| 1 | 知识问答 | REST + SSE | Java 网关 → `knowledge` | ❌ 应用调 agent |
| 2 | 诊断任务 | REST + SSE（有状态 Task） | Java 网关 → `fulfillment` | ❌ 应用调 agent |
| 3 | 跨域委派 | A2A JSON-RPC | `knowledge` → `fulfillment` | ✅ 唯一的 A2A |

`01` §9.1 已经把四层切开（函数调用 / MCP / REST+SSE / A2A），这里补一条**工程约束**：

> **Python 侧永远不主动调 Java 侧。** 没有第四条通道。
> 需要 Java 参与的只有两件事——取主体属性（请求时已随 `subject_ctx` 带来）和动作审批（走 Task 的 `input_required`，
> 由 Java 主动 `resume`）。**把"回调 Java"设计成通道，就等于让 Python 持有一个 Java 的凭据，故障面立刻翻倍。**

这条约束换来一个很硬的好处：**依赖方向单一**，Java 挂了 Python 只是没有新请求，不会雪崩；
Python 挂了 Java 可以降级为"检索结果列表"（`01` §10 降级行）。

## 2. 知识域为什么无状态，排障域为什么必须有状态

这是本契约里唯一一个"两边设计不对称"的地方，也是被追问概率最高的一处。

| | 知识问答 | 排障诊断 |
|---|---|---|
| 单次时长 | 首 token < 1.5s，P95 < 4s | P95 < 30s，多步工具调用 |
| 会不会中途停下等人 | 不会 | **会**：`propose_action` 后等人工审批，可能几分钟到几小时 |
| HTTP 连接能不能撑住 | 能 | **不能** |
| 结论 | 一个请求一条流，结束即结束 | **Task 资源 + 可恢复流** |

如果排障域也做成"一个请求一条流"，会得到一个经典事故：审批等了 20 分钟，
网关 60s 超时把连接掐了，Python 侧 checkpointer 停在 `human_approve`，
**但没有任何入口能把它唤醒**——任务变成幽灵状态，`chat_turn` 永远 `status=running`。

所以排障域做成 Task：

```
POST /v1/fulfillment/tasks                    → 201 {task_id} + SSE 流
  ├─ 正常跑完        → 流里出 done                 → 结束
  ├─ 需要审批/补充信息 → 流里出 input_required，**流正常关闭**，task 状态 → paused
  │                    （连接不再被占用，审批可以等一天）
  └─ 失败            → 流里出 error
POST /v1/fulfillment/tasks/{id}/resume         → 带审批结论，返回**新的一条流**
GET  /v1/fulfillment/tasks/{id}                → 断线后查状态（幂等）
POST /v1/fulfillment/tasks/{id}/cancel         → 显式取消
```

**断流 ≠ 任务失败**，这是 Task 化最实际的价值：SSE 断了重连 `GET` 查状态即可，不需要重跑整个诊断
（重跑意味着重复工具调用、重复计费，而且假设树会变）。

> 取舍要主动说：Task 化不是免费的——要维护状态表、要处理 `resume` 的幂等、要给 Task 加 TTL 清理。
> 知识域不这么做，是因为 4 秒结束的问答引入 Task 只增加状态维护成本，没有收益。
> **同一套状态机语义，只在真正需要的地方付这个代价。**

## 3. 请求体：透传条件，不透传清单

### 3.1 `subject_ctx`（唯一合法的权限载体）

```json
{
  "user_id": "u_2048",
  "account_status": "active",
  "dept_paths": ["D10", "D10.3", "D10.3.7"],
  "roles": ["employee", "fulfillment_ops"],
  "groups": ["sg_17"],
  "approval_doc_ids": ["doc_881", "doc_902"],
  "subject_epoch": 1743
}
```

| 字段 | 为什么在契约里 | 约束 |
|---|---|---|
| `account_status` | 离职/停用**一票否决**，优先于所有授权求值（ADR-0001） | 必须是 `active`，否则 Python 直接 `403 SUBJECT_DISABLED` |
| `dept_paths` | 含祖先链，父部门授权天然覆盖子部门（`05` §2.3 语义 1） | 层级 ≤ 6，URI 侧不做递归 |
| `groups` | 授权主体 > 20 时收敛为共享组（`05` §2.4） | 可为空数组 |
| `approval_doc_ids` | 例外层，不物化进 `acl_jsonb`，走 `= ANY()` | **软上限 50 条**；超限降级为强一致 join（ADR-0001 缓解措施） |
| `subject_epoch` | 主体属性版本，任一变则 +1 | 用于缓存 key、审计对齐（见 §3.3） |

### 3.2 硬禁止：不允许出现文档清单

**契约里不存在 `allowed_doc_ids` / `visible_docs` 这类字段，且 pydantic 设 `extra="forbid"`。**

理由不是洁癖，是 `05` §2 整节论证的东西：

> 一旦 Java 把清单算出来传过来，"权限是检索语句的一部分"就不成立了——
> 检索侧的条件求值变成摆设，1500 万条缓存与失效风暴原样回来。

`extra="forbid"` 是这条论证的**机器守卫**：谁哪天顺手加回 `allowed_doc_ids`，
Python 侧直接 400，而不是"跑得通但设计塌了"。这类"靠人记住的纪律"必须有代码兜底。

> 唯一的例外是 `approval_doc_ids`——它是**主体侧租约**，不是资源侧清单，
> 数量级差 4 个数量级（50 vs 1500 万），方向也相反（`05` §6.1 的两套授权）。

### 3.3 三个 epoch，别混成一个

审计已经发现过这个混淆（`11` §4 "`acl_epoch` 被 4 处引用但没定义在哪张表"），这里给最终口径：

| 名字 | 粒度 | 存在哪 | 用途 |
|---|---|---|---|
| `kb_document.acl_epoch` | **文档级** | MySQL 源 + `kb_doc_mirror` / `kb_chunk` 冗余 | 引用是否已失效的判据（`07` §3.3） |
| `subject_epoch` | **主体级** | 请求体 + `subject:{uid}` 缓存 | 缓存 key、审计对齐、幂等键 |
| `chat_turn.acl_epoch`（历史字段） | 一轮 | MySQL | **语义实为 `subject_epoch` 的拷贝**；引用级判定仍用 `citation[].acl_epoch` |

最后一行是命名债：字段名叫 `acl_epoch` 但存的是主体版本，容易被读成"文档版本"。
保留字段名是为了避免迁移，但**必须在文档里写清**，否则下次重构一定有人拿它去比文档的 `acl_epoch`。
（已记入 `11` §4 待统一。）

## 4. SSE 事件协议

### 4.1 传输约定

| 项 | 约定 | 原因 |
|---|---|---|
| `Content-Type` | `text/event-stream; charset=utf-8` | 标准 |
| 事件 id | 单调递增整数（一轮内） | 支持 `Last-Event-ID` 续传 |
| 每帧 | `id: <n>` + `event: <type>` + `data: <json>` | `data` 一定是 JSON，不做裸文本 |
| 心跳 | 每 15s 一行 `: ping` | 反代 60s 空闲会断流 |
| 终止 | `done` 或 `error`，**二者有且仅有一个** | 少了客户端永远挂着，多了状态机打架 |

**为什么是 SSE 不是 WebSocket**：这是单向流（服务端 → 客户端），不需要全双工；
SSE 走普通 HTTP，天然过网关鉴权、天然支持断线续传、天然能被 curl 调试。
上 WebSocket 的唯一理由是双向，本项目没有这个需求。

### 4.2 事件类型

| event | 何时发 | 关键字段 | 约束 |
|---|---|---|---|
| `meta` | **第一帧，必须** | `trace_id, contract_version, config_version, prompt_set_sha, degraded[], acl_fingerprint` | 先于任何内容帧 |
| `citation` | 生成正文前，先吐引用骨架（`01` §5.2 步骤 4） | `eid, doc_id, title, page_no, acl_epoch` | `eid` 全局唯一，正文只能引用出现过的 `eid` |
| `delta` | 正文增量 | `text` | 可多次 |
| `progress` | 仅排障域：节点推进 | `node, step, note` | 用于"边诊断边推进"（`01` §9.2） |
| `evidence` | 仅排障域：中间证据 | `hypothesis_id, verdict, summary` | 支撑回放与 F5 归因 |
| `action_proposal` | 待审批动作 | `action_type, params, risk_level, approval_id` | **只提议不执行**（`05` §7） |
| `input_required` | 需要人补充/审批 | `kind, schema, question` | 发出后**本流关闭**，task → paused |
| `done` | 正常结束 | `finish_reason, usage{tokens,cost_usd}, citations[]` | `finish_reason ∈ {answered, abstained, escalated, degraded}` |
| `error` | 异常结束 | `code, message, retryable, retry_after_ms` | `message` 必须脱敏 |

### 4.3 三条顺序约束（对应 `05` §5 的出口）

1. **引用先于正文**：`citation` 必须在引用它的 `delta` 之前。这样前端能先渲染引用骨架，
   而且**模型无法引用未出现过的 `eid`**——这是出口 5（引用生成）在协议层的落地。
2. **`eid` 而不是 `[1][2]`**：正文里带的是占位符，编号由前端按 `citations[]` 顺序渲染。
   引用是数据不是文本（`07` §2.3 陷阱一），一旦在流里写成 `[1]`，压缩后就会错位。
3. **降级不算错误**：rerank 超时 → `meta.degraded=["rerank"]`，流照常出 `done`。
   **拒答也不是错误**：`done.finish_reason="abstained"`。
   如果把这两种都算成 `error`，评测会把正常行为统计成失败，越权集和拒答集直接失真。

### 4.4 降级要写两处

| 位置 | 给谁看 | 形式 |
|---|---|---|
| 响应头 | 网关 / 监控 / 告警 | `X-Degraded: rerank,classify` |
| `meta` 事件 | 前端展示 + trace | `degraded: ["rerank","classify"]` |

只写一处都缺一半：头里有、流里没有 → 前端没法提示"本次结果未重排"；
流里有、头里没有 → 网关统计和告警采不到（`models.yaml` 要求"写进响应头与 trace"，就是这个意思）。

## 5. 超时、重试、幂等、取消

### 5.1 超时：传剩余预算，不传绝对时间

用 `X-Deadline-Ms: 12000`（**剩余毫秒**），不用绝对时间戳。

> 理由很实际：跨机时钟漂移几秒很常见，绝对 deadline 会因为 NTP 抖动产生偶发误判——
> 同一份代码在两台机器上表现不同，是最难查的一类 bug。

| 层 | 默认预算 | 超时后行为 |
|---|---|---|
| Java → knowledge 整体 | 15s | 关闭上游，落 `chat_turn(status='failed')`，前端出 `error DEADLINE_EXCEEDED` |
| 单次 LLM 调用 | `generate` 60s / `classify` 10s（`models.yaml`） | 按 `fallback` 降级，不直接失败 |
| 单次工具调用 | 3s（排障域查询）/ 10s（rerank） | 记 `degraded`，继续 |
| knowledge → fulfillment（A2A） | `min(父剩余 - 500ms, 30s)` | 降级为"仅文档答案 + 数据不可得"（`01` §9.5） |

**子调用必须比父预算小**，且要预留 500ms 用于组装响应——否则父级已经超时，子级还在跑，
日志里会出现"trace 显示成功但用户看到超时"。

### 5.2 重试：只在第一帧之前

| 阶段 | 能否重试 | 原因 |
|---|---|---|
| 连接失败 / 5xx / 429（未收到 `meta`） | ✅ 最多 2 次，指数退避 1s→4s 带抖动 | 用户没看到任何内容，重试无副作用 |
| 已收到 `delta` | ❌ | 用户已经看到半句话，重试会拼接出两段不同的答案 |
| 已收到 `done` | ❌（但可幂等重放，见 5.3） | — |

这条规则必须在 Java 侧实现，不能指望 Python——**一旦流出 token，重试的主体责任在消费方**。

### 5.3 幂等：不重复计费、不重复落库

```
Idempotency-Key = sha256(session_id | turn_seq | query | subject_epoch)
```

保留窗口 24h。重复请求的行为：

- 原请求已完成 → 直接重放 `done`（含原 `citations[]` 与 `usage`），**不重新推理**；
- 原请求进行中 → 返回 `409 DUPLICATE_INFLIGHT`，让调用方重连原流；
- 原请求失败 → 允许重跑。

**为什么 key 里必须有 `subject_epoch`**：权限变了还重放旧答案，等于用旧权限回答新问题。
这是幂等设计里最容易漏的一刀：幂等的是"同一件事"，不是"同一句话"。

### 5.4 取消

| 触发 | 传播链 | 收尾 |
|---|---|---|
| 客户端断开 | Java 关闭上游 → Python 收到 disconnect | 图执行到最近一个 checkpoint 停止；`chat_turn.status='canceled'` |
| 显式取消（排障域） | `POST /tasks/{id}/cancel` | task → canceled，释放工具连接与 DB 游标 |
| 服务端主动取消（预算耗尽） | `error BUDGET_EXCEEDED` | 已经产生的 token 照常计费并落 `usage`（**不能因为取消就不算钱**） |

取消的语义边界要写清：**取消 = 停止继续产生新 token，不回滚已产生的内容**。
`07` §0.1 已经规定"流式中途失败不落 assistant 消息"——取消同理，只落 `chat_turn`，不落半条回答。

## 6. 错误码

分三类，**决定调用方要不要重试**，这是错误码唯一真正有用的维度。

| 类 | code | HTTP | retryable | 谁的问题 |
|---|---|---|---|---|
| **A 契约/主体** | `INVALID_SCHEMA` | 400 | ❌ | Java 传了契约外字段（含 `allowed_doc_ids` 回潮） |
| | `SUBJECT_MISSING` | 401 | ❌ | 缺 `subject_ctx` |
| | `SUBJECT_DISABLED` | 403 | ❌ | `account_status != active`（ADR-0001 一票否决） |
| | `CONTRACT_VERSION_UNSUPPORTED` | 426 | ❌ | 版本不匹配，需升级 |
| **B 瞬时** | `RATE_LIMITED` | 429 | ✅ 按 `retry_after_ms` | 供应商限流 |
| | `UPSTREAM_UNAVAILABLE` | 502/503 | ✅ | 模型/依赖不可用 |
| | `MODEL_TIMEOUT` | 504 | ✅ | 单次调用超时，可降级重试 |
| **C 业务终止** | `DEADLINE_EXCEEDED` | 504 | ❌ | 整体预算耗尽 |
| | `BUDGET_EXCEEDED` | 402 | ❌ | 触发 `budget.on_exceed: hard_stop` |
| | `ACL_SNAPSHOT_STALE` | 409 | ❌（要修数据） | PG 快照落后于 MySQL，`06` §4 的对账会报 |
| | `DUPLICATE_INFLIGHT` | 409 | ❌（去重连） | 同一幂等键的请求仍在跑，调用方应重连原流（§5.3） |
| | `INJECTION_BLOCKED` | 422 | ❌ | 护栏拦截，属于**正常防护**，不是 bug |
| | `TASK_NOT_FOUND` / `TASK_STATE_CONFLICT` | 404 / 409 | ❌ | Task 已过期或状态不允许 resume |
| | `INTERNAL` | 500 | ❌ | 未分类异常，出现即是 bug，必须带 `trace_id` 回报 |

两条口径：

1. **`ABSTAINED` 不是错误码**，它是 `done.finish_reason`。拒答是设计内行为（`01` §6 表格最后一行）。
2. **`INJECTION_BLOCKED` 是安全能力的证据**，运维看板上应该单独计数，不能和 5xx 混在一个错误率里——
   混进去会让人以为系统不稳定，实际上是被拦掉了。

## 7. 双向约束怎么落地（这是"Java 侧怎么保证不传错字段"的答案）

`openapi.yaml` 是唯一真相源，两端都不手写 DTO。

```
api/openapi.yaml
   ├─ datamodel-codegen ──→ agent-service/api/schemas.py      （pydantic v2，extra="forbid"）
   └─ openapi-generator ──→ java-service/contract/…/dto      （spring interfaceOnly + Jakarta）
```

**为什么两端用不同工具**：`openapi-generator` 的 python 生成器产出的是"客户端库"（含 models 包、api 包、配置类），
而 Python 侧只需要**一组带严格校验的请求/事件模型**；
`datamodel-codegen` 直接产出单文件 pydantic v2 模型，并且把 `additionalProperties: false` 翻成 `extra="forbid"`
（这一点已经实测：传 `allowed_doc_ids` 会抛 `extra_forbidden`）。
Java 侧相反，需要接口骨架 + DTO 才符合 Spring 的用法，所以用 `spring` 生成器 + `interfaceOnly=true`。

> **一个生成器做不到的地方，要主动说**：SSE 那三个操作的 Java 返回类型，生成器只能给
> `ResponseEntity<String>`（它不会从 `text/event-stream` 推断出 `SseEmitter` / `Flux<ServerSentEvent>`）。
> 所以这三个方法在 Java 侧**手写**，但请求体与事件 DTO 仍然来自 codegen——
> 契约一致性保在"载荷"这一层，不保在"传输句柄"这一层。这比假装生成物能直接用要诚实。

| 手段 | 挡什么 | 在 CI 的哪一步 |
|---|---|---|
| `extra="forbid"` / `FAIL_ON_UNKNOWN_PROPERTIES` | 字段名拼错、自以为加了字段但另一端没实现 | 双方单测 |
| 生成代码而非手写 | 两侧定义漂移（最隐蔽的一类 bug） | `make codegen && git diff --exit-code` |
| golden fixtures（6 个请求 + 8 个事件 JSON） | 序列化语义差异（时间格式、枚举大小写、null vs 缺省） | 双方反序列化测试 |
| `oasdiff breaking` | 破坏性变更（删字段、改类型、加必填） | PR 门禁 |
| 契约版本号 | 灰度期间新旧版本并存 | 运行时校验 |

### 7.1 演进规则

| 变更 | 允许 | 做法 |
|---|---|---|
| 加**可选**字段 | ✅ | 直接加，老客户端忽略 |
| 加必填字段 | ❌ | 先加可选 + 默认值，下一版才必填 |
| 删字段 / 改类型 / 改语义 | ❌ | 新开 `/v2`，双版本并行一个里程碑 |
| 改枚举值 | ⚠️ | 客户端必须容忍未知枚举（`finish_reason` 尤其要注意，别写 `switch` 不带 default） |

`meta.contract_version` + 请求头 `X-Contract-Version` 双向声明；不匹配直接 `426`，
**不做静默兼容**——静默兼容会把"版本不一致"变成"数据错乱"。

## 8. A2A 契约：同一套状态机，两种绑定

`01` §9.2 定了 A2A 的字段，这里只写**与 REST 的差异部分**，避免重复。

| 项 | REST 绑定（Java → agent） | JSON-RPC 绑定（knowledge → fulfillment） |
|---|---|---|
| 调用语义 | 应用发起，**无协商** | Agent 对等，先读 Agent Card |
| 发现 | 无（配置里写死 base_url） | `/.well-known/agent-card.json` |
| 状态机 | 同一套：`submitted → working → (input_required) → completed / failed / canceled` | 同左 |
| 中断语义 | `input_required` 事件 + 流关闭 + `resume` | `TASK_STATE_INPUT_REQUIRED` + `SendMessage` 续 |
| 输出 | SSE 事件序列 | `Artifact` 的 `part[]`（`data` + `text`） |

**这张表的价值**：同一个 Task 状态机被两种传输绑定复用，所以业务代码只实现一套状态迁移，
换绑定不改状态逻辑。这正是 `01` §9.3 说的"我买的不是通信，是状态机语义"落到代码上的样子。

三条 A2A 专项约束（`05` §5 出口 6）：

1. **委派必须携带最小 `scope`**（如 `{warehouse, time_range}`），不传 `subject_ctx` 全量；
2. **被调方按自己的权限模型二次校验**，绝不因为"是自己人调的"就放宽；
3. **Part 不要 `kind` 字段**：A2A v1.0 已改为按携带字段自我标识（`text`/`url`/`raw`/`data`），
   照 v0.3 样例抄会直接跑不通（`01` §9.2 已记录这个坑）。

## 9. 契约测试与故障演练

契约写得再细，没有测试就是文档。最小可行三件：

| 测试 | 做法 | 断言 |
|---|---|---|
| **两端反序列化** | golden fixtures 双端跑 | 未知字段报错、缺失必填报错、枚举未知值不崩 |
| **事件序列** | 用录制流回放，检查顺序约束 | `meta` 首帧、`citation` 先于引用它的 `delta`、终止事件唯一 |
| **故障注入** | 切断 SSE / 让 rerank 超时 / 让 A2A 不可用 | 降级标记出现且**流正常结束**、`chat_turn.status` 正确 |

第三个最值得做：**降级路径是最不容易被测到的代码**，而它恰好是线上最常走的代码。

## 10. 面试口径

**Q：Java 和 Python 之间怎么保证不传错字段？**
> 三个层次。第一，`openapi.yaml` 是唯一真相源，两端 DTO 都是生成的，不手写，所以不会漂移；
> 第二，pydantic 用 `extra="forbid"`、Jackson 开 `FAIL_ON_UNKNOWN_PROPERTIES`，
> 拼错字段名直接 400，而不是静默忽略；第三，CI 里做 `git diff --exit-code` 检查生成物，
> 加上 oasdiff 做破坏性变更检测，删字段或改类型必须走 v2。

**Q：为什么要禁止传文档清单？**
> 因为我的核心论点是"权限是检索语句的一部分"。如果 Java 先把可见文档算成清单传过来，
> 检索侧的条件求值就变成摆设，1500 万条缓存和失效风暴原样回来。
> 所以契约里根本没有这个字段，而且 `extra="forbid"` 让它加不回来——用代码守纪律，不靠人记。

**Q：两个服务之间超时怎么定？**
> 传剩余预算，不传绝对时间戳，避免时钟漂移。子调用永远比父预算小，留 500ms 组装。
> 重试只在第一帧之前允许，一旦流出 token 就不重试——用户已经看到半句话了。
> 幂等键里带上主体版本，否则权限变了会重放旧答案。

**Q：为什么排障域要做成 Task，知识域不做？**
> 因为审批可能等几小时，HTTP 连接撑不住。连接一断，没有入口唤醒 checkpointer，
> 任务就变成幽灵状态。Task 化之后断流不等于失败，重连查状态就行。
> 知识域 4 秒结束，Task 化只增加状态维护成本，所以不做。
> 同一套状态机语义，只在真正需要的地方付这个代价。
