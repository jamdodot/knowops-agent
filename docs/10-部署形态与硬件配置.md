# 部署形态与硬件配置

前面八份文档讲的是"该怎么设计"，这一份回答一个更前置的问题：**这套东西到底能不能在一台普通电脑上跑起来。**

结论先给：

> **能，而且不需要私有部署任何模型。**
> 最终形态是 **本地只跑一个 PostgreSQL 容器 + 两个 Python 进程 + 一个 Java 进程，模型全部走线上 API**。
> 私有部署是这条路线上的**可选升级**，不是前提条件。

这个结论成立的原因，不是"凑合能跑"，而是这个项目的技术含量分布决定的——

---

## 0. 先看技术含量在哪：为什么"全 API"不丢分

面试官不会因为你调 API 而看低你，但会因为你说不清"哪些该自己控制"而看低你。

把项目按"在哪执行"重新分一遍，会发现比例很不均：

| 层 | 具体内容 | 在哪 | 占项目价值 |
|---|---|---|---|
| **判定与状态** | 权限条件求值、ACL 下推、检索融合、评测归因、会话与记忆、任务状态机 | **必须本地数据库** | **约 80%** |
| **算力** | LLM 推理、embedding 计算、rerank 打分 | 可以完全外包 | 约 10% |
| **解析** | 版面分析、OCR、结构还原 | 离线批处理，可本地可云 | 约 10% |

**算力是可替换的，判定和状态是不可替换的。**

权限那条 SQL 里没有模型，混合检索的 RRF 融合里没有模型，评测的归因分类里也没有模型。这几块才是项目的差异化，而它们全部跑在 PostgreSQL 里——**一个容器，2GB 内存，任何一台电脑都有**。

模型换一家服务商，改的是 `config/models.yaml` 里的三行；权限和评测改一次就是重写。这就是为什么硬件不构成这个项目的瓶颈。

---

## 1. 判断框架：什么必须本地，什么可以外包

不是"能云就云"，而是按三条标准过一遍。

| 标准 | 含义 | 落到本地的东西 |
|---|---|---|
| **① 状态必须就地** | 要能在一条 SQL 里参与判定的数据 | PG（chunk、向量、ACL 快照、评测结果） |
| **② 语义必须可控** | 输出格式、版本、失败行为影响下游正确性 | 解析（IR 结构）、embedding（模型版本三锁） |
| **③ 可复现** | 评测要能重跑出同样的数 | 配置快照、评测集、trace（进 PG） |

按这三条过一遍，得到下表。

| 组件 | 最终选择 | 为什么 |
|---|---|---|
| **LLM**（生成 / 规划 / 抽取 / judge） | **线上 API（DeepSeek）** | 无状态、可替换；本地跑 7B 模型质量不够，跑 32B 要 24GB 显存，不划算 |
| **Embedding** | **线上 API（BGE-M3 托管）** | 起步阶段量小，自托管收益抵不过运维成本 |
| **Rerank** | **线上 API，或本地 CPU（ONNX 量化）** | 50 条 CPU 约 300~600ms，两者都可接受 |
| **文档解析** | **全部本地（`parse_mode: local`）** | 三个是纯库没有线上形态；MinerU 虽有云 API 但默认不用，为了原文不出域与不依赖配额 |
| **PostgreSQL** | **本地 Docker（必须）** | 权限判定 + 向量 + BM25 + 评测数据都在这，是本项目的地基 |
| **Redis** | 本地 Docker（**可砍**） | 缓存可退化到 PG；只在演示语义缓存隔离时需要 |
| **MinIO** | **可砍，用本地目录** | 作品集没有多副本需求 |
| **MySQL** | **M0~M2 合并进 PG（路径 A）** | 省一个容器 1.5GB；M5 再拆出来演示 outbox |
| **Neo4j** | **M3 之前不装** | 先用 PG `relation` 表 + 递归 CTE；社区检测用 `networkx` 内存算 |
| **Java 服务** | 本地，可先弱化成轻量网关 | 权限与事务的宿主，必须存在 |

**注意：解析放在"本地"这一栏，但和"私有部署模型"不是一回事。** 见下节。

## 2. 关键澄清：自托管 ≠ 需要 GPU

这是原来 `08-模型接入方案.md` 里一个容易引起误判的表述，必须纠正过来。

原文写"OCR / 版面解析 → **GPU 自托管**"。这句话在语义上是错的——它把"自托管"和"GPU"绑在了一起。准确的说法是：

| 任务 | GPU | CPU | 普通电脑上的实际体验 |
|---|---|---|---|
| **L0 数字原生直取**（PyMuPDF） | 不需要 | **毫秒级/页** | 完全无压力，内存几十 MB |
| **L1 管道式解析**（Docling） | 不需要 | **1~3 秒/页** | 主力引擎，CPU 原生支持，可在后台常驻 |
| **L1 兜底**（MinerU pipeline） | 可选 | **2~10 秒/页** | 本地管道后端可跑；峰值 3~5GB，并发锁 1 |
| **L2 VLM 直出** | 基本需要 | 不可行 | 不进生产路径（已列为预研，不排期） |
| **Embedding 自托管**（BGE-M3，CPU/ONNX） | 可选 | 单条 50~150ms，建库 5~20 条/秒 | 查询可用，大批量建库会磨人 |
| **Rerank 自托管**（bge-reranker-v2-m3，CPU） | 可选 | 50 条 300~600ms | 完全可用 |

**关键判断是这一条：解析是入库时的一次性开销，不在请求链路上。**

一份 300 页的报告，Docling 在 CPU 上约 5~15 分钟。听起来很长，但它只在入库时跑一次，问答延迟完全不受影响。作品集阶段总共几十到几百份文档，**睡前跑一批，早上就有结果**。

**四个解析引擎全部本地跑，`parse_mode: local`。**

这里有个容易混的地方值得说清楚：PyMuPDF / pdfplumber / Camelot 是纯 Python 库，**根本没有线上形态**；Docling 只有自托管的 `docling-serve`（那是 HTTP 壳，不解决算力），也没有公开 SaaS。**只有 MinerU 有官方在线 API**（mineru.net），本地也有管道后端。

所以"能不能上云"只有一个真实选项——MinerU。而这个选项**默认不启用**：省下的 3GB 内存，不值"原文出域 + 多一个 key + 多一层配额 + 断网就不能用"这几件事。

代价就一条，但是硬约束：**MinerU 峰值 3~5GB，并发必须锁 1**，另外首次运行要下 1~2GB 权重（需提前预制）。细节见 `09-文档解析设计.md` 5.6。

"普通电脑"的真实约束因此不在算力速度，而在**内存峰值**——这才是要设计的东西。

## 3. 三档配置

### 档位一：16GB 内存，无独显（推荐，本项目的目标环境）

这是最舒服的档位，也是我建议你按这个档位写方案。

| 组件 | 形态 | 常驻内存 |
|---|---|---|
| PostgreSQL 16（pgvector + pg_search） | Docker | 1.2~1.5 GB |
| agent-knowledge（Python） | 本地进程 | ~400 MB |
| agent-fulfillment（Python） | 本地进程 | ~400 MB |
| java-service | 本地 / Docker | ~500 MB |
| Redis（可选） | Docker | ~150 MB |
| MinIO（可选，可换本地目录） | Docker | ~150 MB |
| **常驻小计** | | **≈ 3.0 GB** |
| 解析：Docling（本地，常驻可接受） | 独立进程 | 峰值 1~2 GB |
| 解析：MinerU（**仅兜底时启动**，跑完即退） | 独立进程 | 峰值 3~5 GB |

常驻 3GB，入库峰值约 8GB。16GB 机器有充足余量，开发时还能同时开 IDE 和浏览器。

**入库期间不要跑评测或大批量问答**，这是唯一需要遵守的纪律——两件事的内存峰值会叠加。

### 档位二：8GB 内存，无独显（能跑，但必须裁剪）

可行，代价是砍掉一部分功能：

| 裁剪项 | 做法 | 损失 |
|---|---|---|
| 解析只走 L0 + DOCX | 只支持数字原生 PDF / Word / Markdown，**扫描件先不支持** | 拿不到"版面分析"这个讲点，用预研方式补 |
| MinerU 改按需 | 一次只解析 5~10 份，或借一台机器离线跑完再拷结果（IR 是文件，可搬运） | 扫描件要排队，不能并发 |
| 砍 Redis | 缓存退化到 PG 表 / 进程内 LRU | 语义缓存的演示弱化 |
| 砍 MinIO | 原文件存本地目录 | 无 |
| 砍 Neo4j | PG 递归 CTE + `networkx` | 3 跳以上遍历会慢，作品集够用 |
| 两个 agent 进程 | 画像很轻（各 400MB），**不需要砍**，A2A 照常演示 | 无 |

**这里有个重要发现：L0 路线几乎不占内存。** PyMuPDF 直取一个 300 页 PDF 只有几十 MB 占用、几秒钟完成。如果你的文档以数字原生 PDF 为主（企业制度文件基本都是），**8GB 机器完全够用**。

所以 8GB 的真实结论是：**不是"做不了"，而是"扫描件要按需跑、不能并发"**。而扫描件本来就是文档解析里最边缘的场景，企业制度文件基本都是数字原生 PDF。

### 档位三：32GB + 独显（8GB VRAM 以上）

可以往上加，但**我建议不要加**，理由是收益很低：

| 可加的东西 | 加了的收益 | 值不值 |
|---|---|---|
| 自托管 BGE-M3（fp16 约 2.2GB 显存） | 省 API 费用、数据不出域 | 作品集阶段省不了几十块，**不值** |
| 自托管 reranker | 省一次网络往返 | 延迟略降，**收益很小** |
| 本地 7B/14B LLM | 可离线演示 | **质量差距明显**，生成质量是这个项目的脸面，不值得 |
| Neo4j | 图遍历更顺 | 有意义，但 PG 也能撑到 M3 |

结论：**有独显也别用来跑模型，用来跑 Docker 和 IDE 更实际。** 唯一值得的升级是把内存加到 32GB，让入库和评测能并行。

## 4. Windows + Docker Desktop 的四个坑

如果你的开发机是 Windows（大概率是），这几个坑都会踩。

**① WSL2 默认只给一半内存**

Docker Desktop 跑在 WSL2 里，默认上限是物理内存的 50%。16GB 机器只有 8GB 可用，入库时会 OOM。

```ini
# C:\Users\<你>\.wslconfig
[wsl2]
memory=10GB
processors=6
swap=4GB
```

改完 `wsl --shutdown` 重启。**这一条不做，16GB 机器等于 8GB 机器。**

**② 数据卷不要放 `/mnt/c`**

把 PG 数据目录挂在 `/mnt/c/...` 下，IO 会慢一个数量级（跨文件系统转换）。用 Docker named volume，数据实际落在 WSL2 的 ext4 里。

**③ 端口冲突**

Windows 上 5432 经常已被本机安装的 PostgreSQL 占用。用 `5433:5432` 映射，配置里改一处即可。

**④ 文件监听跨盘失效**

Python 热重载在 `/mnt/c` 上常常不触发，代码放 WSL2 内部路径，或用 `--reload` 加轮询。

## 5. 一个容器解决向量 + BM25 + 业务表

原来文档写的是"PG 装 pgvector，BM25 用 ParadeDB"，听起来像两个东西。实际可以合并：

**`paradedb/paradedb` 镜像自带 `pg_search`（真 BM25，Tantivy 实现）和 `pgvector`**，一个容器同时提供：

```sql
-- 向量那一路
ORDER BY embedding <=> $1 LIMIT 20

-- 关键词那一路（真 BM25，不是 ts_rank 的近似）
WHERE id @@@ paradedb.match('content', $2)
```

这正好满足本项目最硬的那条设计——**鉴权、向量、BM25 写进同一条 SQL**。一个容器、一份内存、一个事务边界。

> 落地前确认一下该镜像版本的许可证与 `pg_search` 社区版功能边界（企业版才有部分高级特性）。若受限，退化方案是 `pg_trgm` + `tsvector` + `zhparser`，效果略差但无许可风险。

中文分词还要另装 `zhparser` 或 `pg_jieba`。这个在自定义镜像里加一行 `apt install` 即可。

## 6. 什么时候必须转私有部署

不要现在就纠结，但要提前写清触发条件——这本身就是一个能讲的设计判断。

| 触发条件 | 转什么 | 理由 |
|---|---|---|
| **数据涉密**（真实企业文档） | embedding + 解析全本地 | 传出去的文本就是原文，敏感性等同于生成时 |
| **chunk 超过 50 万** | embedding 自托管 | API 成本超过一台 GPU 机器的折旧 |
| **需要离线演示**（断网环境） | LLM 也要本地，或全量 Mock 回放 | 见第 8 节 |
| **面试要求"完全自主可控"** | 全本地 | 这是话术题，不是技术题 |

注意第一条：**"embedding 出域比生成更安全"是错误认知**。embedding 传的文本就是原文本身。所以如果要处理真实敏感数据，第一个要私有化的不是 LLM，而是 embedding 和解析。

作品集阶段用公开文档和自造数据，这个问题不存在。

## 7. 最终形态（一张图说清）

```
┌─────────────────── 你的电脑（16GB，无独显）───────────────────┐
│                                                                │
│  Java 网关 ──REST/SSE──> agent-knowledge ──A2A──> agent-        │
│                              │                    fulfillment   │
│                              │                        │        │
│                              └────────┬───────────────┘        │
│                                       ▼                        │
│                    PostgreSQL（pgvector + pg_search）           │
│                    chunk / 向量 / ACL快照 / 评测 / 会话 / trace │
│                                       ▲                        │
│  文档目录 ──> 解析（L0 直取 / MinerU CPU，离线一次性）          │
└───────────────────────────────────────┼────────────────────────┘
                                        │ HTTPS
                        ┌───────────────▼────────────────┐
                        │  DeepSeek      → 生成/规划/判断 │
                        │  BGE-M3 API    → dense 向量     │
                        │  bge-reranker  → 重排（可选本地）│
                        └────────────────────────────────┘
```

**本地负责"记得住、判得准"；云上负责"算得快"。** 这条分界线就是整份文档的结论。

成本估算（按作品集阶段的实际用量）：

| 项目 | 估算 |
|---|---|
| 建库（500 份文档、约 5 万 chunk） | 约 30~80 元，一次性 |
| 开发期问答（约 2000 次，含失败重试） | 约 50~120 元 |
| 评测回归（20 轮 × 150 题） | 约 30~60 元 |
| **合计（2~3 个月开发期）** | **约 150~300 元** |

比升级硬件的钱少得多。这是"全 API"最实际的理由。

## 8. 演示预案：API 挂了怎么办

这是唯一真正需要提前准备的风险。面试现场网络不稳，或者对方要求断网演示，如果那一刻 500 了，前面所有设计都讲不出口。

三个措施，按成本排序：

1. **`MockProvider`（必做）**：`ModelProvider` 协议的第三个实现，返回预置响应。CI 本来就需要它（否则每次单测都真调 API），顺手就复用了。
2. **响应录制回放（推荐）**：把 50 道演示题的完整 LLM 响应录成 JSON，按 `hash(prompt)` 索引。断网时切到回放模式，**界面上标注"演示模式"**，不装成实时。
3. **降级声明（必做）**：`degraded: [llm]` 写进响应头和 trace。这一条和 `08` 文档里"降级不能静默"是同一个原则。

**不要做的是假装在线。** 面试时主动说"这块走的是录制回放，因为现场网络不稳定，实时链路我可以现在跑一遍给你看日志"，比悄悄用假数据可信得多。

## 9. 面试口径（三个可能被问到的）

**Q：你的模型全是调 API，那这个项目你自己做了什么？**
> 我做的不是模型，是模型外面那层。权限条件怎么下推到向量检索里、两路召回怎么融合、评测怎么定位到具体失败原因、上下文压缩怎么不破坏引用和权限标记——这些都不在模型里，也换不掉。模型那层我留了 `ModelProvider` 抽象，换 provider 改配置，因为它本来就该是可替换的。

**Q：为什么不私有部署？**
> 现在没有理由。私有部署的正当理由只有三个：数据涉密、量级上来后成本更低、需要离线。我目前一条都不满足。我把触发条件写下来了——chunk 过 50 万或者接真实企业数据就转自托管，embedding 和解析先转，LLM 最后转，因为 LLM 出域的风险最小、私有化的收益也最小（本地 7B 质量不够）。

**Q：你本地环境是什么？**
> 一台 16GB 无独显的机器，Docker 跑一个 PG（pgvector + pg_search），两个 Python agent 进程，模型走 API。解析用 CPU 跑 MinerU，慢但不影响请求链路，因为解析是入库时的一次性开销。**这个规模能撑住项目的全部核心命题，因为核心命题都在数据库里。**

最后这句话是重点：**把"硬件不够"翻译成"我清楚瓶颈在哪、也清楚它不在哪"**，这才是加分项。
