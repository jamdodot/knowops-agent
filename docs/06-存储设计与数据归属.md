# 06 存储设计与数据归属

> 一句话：**MySQL 是写模型（真相），PostgreSQL 是读模型（派生），数据只朝一个方向流。**

---

## 1. 存储全景

| 存储 | 版本 | 存什么 | 谁写 | 谁读 | 为什么是它 |
|---|---|---|---|---|---|
| **MySQL** | 8.0 | 文档元数据、授权、审批、动作请求、会话 | Java | Java | 强事务、组织架构同步、团队熟悉 |
| **PostgreSQL** | 16 + pgvector + pg_search | chunk、父块、向量、tsv、`acl_jsonb` | Python（消费事件） | Python | 向量 + BM25 + JSONB 过滤可在同一条 SQL |
| **Neo4j** | 5 Community | 实体、关系、社区、`MENTIONED_IN` | Python | Python | 多跳遍历与社区检测 |
| **Redis** | 7 | 主体属性缓存、语义缓存、限流、分布式锁 | 双端 | 双端 | 低延迟 + TTL + 主动失效 |
| **MinIO** | latest | 原文件、解析中间产物 | Java 写 / Python 读 | 双端 | S3 兼容，可无痛换云 |
| **Prometheus + Grafana** | — | 指标时序 | 双端 | — | 标准生态 |
| **Langfuse**（可选） | v3 | LLM trace | Python | — | 自带 PG + ClickHouse，较重，M5 再上 |

容器数：**完整形态 7 个**（mysql / postgres / redis / minio / java-service / agent-knowledge / agent-fulfillment），
M3 加 neo4j，M5 加 langfuse + prometheus + grafana。
**M0~M2 的实际形态是 1 个 PG 容器 + 3 个进程**（MySQL 合并进 PG 双 schema），见本文 §5 与 `10-部署形态与硬件配置.md`。
两者是同一份设计的"完整/收敛"关系：表结构与代码不变，只是容器怎么摆不同。

## 2. 表清单与归属

### MySQL 8（写模型，schema：`knowops`）

| 表 | 说明 | 关键字段 |
|---|---|---|
| `kb_document` | 文档主表 | `id, title, file_key, version, owner_dept, acl_mode, status, acl_from, acl_to, acl_epoch`<br>`acl_epoch` 每次 ACL 变更 +1，是"引用是否已失效"的唯一判据（见 `07` §3.3） |
| `kb_acl_grant` | **授权真相**（四种来源统一建模） | `doc_id, subject_type, subject_id, action, source, rule_expr, expire_at` |
| `kb_approval` | 审批流 | `doc_id, applicant_id, approver_id, status, expire_at, granted_context`（申请时部门/角色快照，仅审计，见 ADR-0001） |
| `kb_share_group` | 授权主体超过 20 时抽象出的组 | `id, name, members_json` |
| `kb_subject_state` | 主体状态与版本（ADR-0001 一票否决的数据来源） | `user_id, account_status, subject_epoch, updated_at`<br>`account_status != active` 必须在解析 SubjectContext 最前面拦掉；`subject_epoch` 用于缓存 key 与幂等键（`13` §3.1） |
| `action_request` | 排障域动作审批 | `trace_id, action_type, params, risk_level, status, approver_id` |
| `session` | 会话主表 | `id, user_id, domain, title, created_at, last_active_at, status` |
| `chat_message` | 消息全量原文（**不删改**） | `id, session_id, seq, role, content, created_at` |
| `chat_turn` | 一轮问答的聚合视图 | `id, session_id, trace_id, status, input_tokens, output_tokens, latency_ms, citation_json, acl_epoch`<br>`status ∈ {completed, failed, canceled}`，失败轮不进后续上下文 |
| `outbox_event` | 变更事件（发往 PG / Neo4j） | `id, event_type, payload, status, retry_count` |
| `audit_log` | 访问审计 | `user_id, action, resource_id, doc_ids, trace_id` |

### PostgreSQL 16（读模型，schema：`knowops_read`）

| 表 | 说明 | 关键字段与索引 |
|---|---|---|
| `kb_chunk` | 检索单元 | `id, doc_id, parent_id, content, section_path, page_no, acl_jsonb, acl_epoch, embed_model, embed_ver, tsv, embedding`<br>`HNSW(embedding)` + `GIN(acl_jsonb jsonb_ops)` + `GIN(tsv)`<br>**必须是 `jsonb_ops`**：`jsonb_path_ops` 只支持 `@>`，不支持 `?` / `?\|` |
| `kb_doc_mirror` | **文档级快照**（PG 本地副本，检索 SQL 要 join 它） | `doc_id, status, acl_from, acl_to, acl_epoch, version, updated_at`<br>只有元数据，不含正文；由 outbox 同步，收权走同步写 |
| `kb_parent_chunk` | 父块（喂模型用） | `id, doc_id, content, section_path` |
| `kb_chunk_restricted` | 受限内容分区（可选） | 与 `kb_chunk` 同构，单独索引，解决 HNSW 强过滤召回骤降 |
| `parse_report` | 解析质量指标 | `doc_id, engine, route, deploy, text_coverage, table_teds, reading_order_conf, header_footer_leak, empty_ratio, score`<br>`header_footer_leak` 是标准 benchmark 不测、但对检索影响可能最大的项 |
| `ingest_task` | 入库任务状态 | `doc_id, stage, status, error` |
| `langgraph_checkpoint` | 图状态（HITL 中断恢复用） | `thread_id, checkpoint_id, parent_id, state_jsonb, created_at`<br>`PK(thread_id, checkpoint_id)` |
| `summary_cache` | 滚动摘要水位缓存（派生，可重建） | `thread_id, upto_seq, summary_text, covered_msg_ids`<br>`PK(thread_id)`；丢失后可从 `chat_message` 全量重建 |

> **记忆表在第三个 schema：`knowops_mem`**（`mem_semantic` / `mem_episodic`）。
> 它既不是 MySQL 的副本，也不是检索派生物：没有上游可以重放，所以不能放 `knowops_write`（那是"待拆回 MySQL"的真相区）；
> 也不该放 `knowops_read`（那里所有东西都能从事件重建，记忆不能）。
> 单独一个 schema 还有一个附带好处——**权限与检索的报表查询天然不会误 join 到记忆表**（`07` §1.5 的"污染检索"坑）。

## 3. 为什么权限表在 MySQL 而不在 PG

这是最容易被追问的一点，答案只有一句：**权限变更发生在业务事务里，而业务事务在 MySQL。**

- 审批通过 = 改 `kb_approval.status` + 插 `kb_acl_grant` + 写审计，三件事必须原子。放 PG 就变成跨库事务。
- 组织架构（部门树、角色）来自公司主数据，同步进来天然落在 MySQL。
- ACL 的**写路径**全在 Java，**读路径**才在 Python。

所以设计成单向派生：

```
MySQL（写模型 / 真相）
   │  outbox_event（同事务写入）
   ▼
PG（读模型 / 派生） ← 只读，永不反向写
Neo4j（图 / 派生）   ← 只读，永不反向写
```

这就是 CQRS 的简化版：**写走 MySQL，读走 PG，靠事件同步，方向单一。**
好处是排查问题时永远只有一个真相源——数据不一致时，无条件以 MySQL 为准重放。

## 4. 一致性策略

| 环节 | 做法 |
|---|---|
| 事件投递 | `outbox_event` 与业务写在同一事务，避免"写了库没发消息" |
| 消费幂等 | 按 `event_id` 去重，`INSERT ... ON CONFLICT DO NOTHING` |
| 失败重试 | 指数退避 + 死信队列，超过 5 次进人工 |
| 对账 | 每日抽样比对 `kb_acl_grant` 与 `kb_chunk.acl_jsonb`，差异告警 |
| 强一致读 | **收权同步、放权异步**：撤销/收紧授权时，Java 先同步删 PG 侧快照（`kb_doc_mirror` + `kb_chunk.acl_jsonb`，幂等重试）再提交 MySQL 事务；扩权（新增文档、新增部门授权）走 outbox 异步 |

**为什么"强一致"不能写成"直接 join MySQL 授权表"**：PG 里的检索 SQL 物理上 join 不到 MySQL 的表，
除非上 FDW（跨库 JOIN 下推基本不可控）。所以真正的做法是**用写顺序保证方向性**，而不是用读操作跨库：

- **收权同步写**：撤销 = 先删快照、再提交授权删除。若 MySQL 提交失败，结果是"PG 已删、MySQL 还在" = 短暂失权，可接受；
  反过来（先提交 MySQL 再删 PG）就会出现"授权已删但还能检索到" = 越权，不可接受。
- **放权异步写**：新增授权晚几秒生效，用户只会"少看见一会儿"，可接受。
- **兜底**：`kb_doc_mirror.acl_epoch` 与 MySQL 的 `kb_document.acl_epoch` 每日对账，不一致以 MySQL 为准重放。

**允许的不一致**：文档新增到可检索，秒级延迟可接受。
**不允许的不一致**：撤销授权后仍可检索——所以撤销走"先删 PG 快照，再删 MySQL 授权"的顺序，
宁可短暂失权（少看见），不可短暂越权（多看见）。**这个方向性是安全设计的常识，写进文档。**

## 5. 本地开发的简化选项

如果你不想一开始就背 7 个容器，有两条降级路径：

> **M0~M2 的最终形态已收敛为：1 个 PG 容器 + 3 个进程（Java + 两个 agent），模型全走 API。**
> 依据是"一台 16GB 无独显的普通电脑"这个目标环境，完整推导与内存预算见
> `10-部署形态与硬件配置.md`。下面两条是它的构成方式。

### 路径 A：合并 MySQL 到 PG（推荐给赶进度）
在 PG 里建两个 schema：`knowops_write`（原 MySQL 表）+ `knowops_read`（读模型）。
- 好处：一个库，事务简单，M0 一周能起
- 代价：**失去"跨库最终一致性"这个可讲的点**，只剩同库双 schema 的读写分离
- 建议：M0~M2 用这条，M5 再拆出来演示 outbox（拆的时候业务代码几乎不用改，因为访问都走 Repository）

### 路径 B：砍掉 Neo4j
M3 之前不需要图库。GraphRAG 初期可以用 PG 的 `relation` 表存实体关系（2 跳内用递归 CTE 够用），
确认值得做再迁 Neo4j。
- 代价：Leiden 社区检测要自己写或在内存里做（用 `networkx` + `leidenalg`）

## 6. 每个库的"不可替代性"（面试用）

被问"为什么要这么多存储"时，逐个说清它解决了别人解决不了的问题：

| 库 | 不可替代之处 |
|---|---|
| MySQL | 业务事务 + 组织架构同步，且与真实企业形态一致 |
| PG | **只有它能把向量检索、BM25、JSONB 权限过滤放进同一条 SQL** |
| Neo4j | 多跳遍历与社区检测，SQL 递归 CTE 在 3 跳以上会崩 |
| Redis | TTL 与主动失效，缓存语义缓存必须能在秒级清掉 |
| MinIO | 大文件不该进数据库，且要能换成云存储 |

> 如果某个库说不出不可替代性，就该删掉它——这是我自己做技术选型时的判断标准，
> 也是面试里最容易被认可的一句话。
