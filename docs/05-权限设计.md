# 05 权限设计

> 核心命题：**权限是检索语句的一部分，不是检索之后的过滤器。**
> 这句话要成立，靠的不是一句口号，而是下面四个具体决定。

---

## 1. 权限模型四要素

| 要素                    | 定义       | 本项目取值                                           |
| ----------------------- | ---------- | ---------------------------------------------------- |
| **主体 Subject**  | 谁在问     | `user_id` + `dept_path`（含祖先链）+ `roles[]` |
| **资源 Resource** | 能看什么   | document（主）/ chunk（派生）/ 字段（排障域）        |
| **动作 Action**   | 能做什么   | read / export / query_data / propose_action          |
| **来源 Source**   | 凭什么能看 | static / dynamic / approval / public                 |

四种来源统一建模在 `kb_acl_grant`，靠 `source` 区分，**不给每种来源建一张表**——否则求值时要 union 四张表，加一种来源就要改查询。

```sql
kb_acl_grant
  id, doc_id,
  subject_type(user|dept|role), subject_id,
  action(read|export),
  source(static|dynamic|approval|public),
  rule_expr,              -- 仅 dynamic 用，如 "dept == owner_dept && level >= P7"
  granted_by, granted_at,
  expire_at               -- 仅 approval 用
```

## 2. 第一个决定：不把权限展开成文档清单

### 2.1 反面做法

最直觉的实现是"算出用户能看的文档 id 列表，检索时 `doc_id IN (...)`"。

| 问题                 | 后果                                           |
| -------------------- | ---------------------------------------------- |
| 5 万文档 × 300 用户 | 缓存 1500 万条 id，内存与失效成本都不可接受    |
| 文档新增/权限变更    | 所有相关用户的清单都要重算，**失效风暴** |
| IN 列表上万          | SQL 退化、plan 不稳定                          |
| 排查越权             | 只能看最终列表，无法解释"为什么这条能看"       |

### 2.2 本项目的做法：条件求值

把权限表达成**可判定的条件**，跟着查询一起下发。

`kb_chunk.acl_jsonb` 存授权快照：

```json
{
  "v": "scoped",                  // public | org | scoped
  "depts": ["D10.3"],             // 可见部门（父部门授权天然覆盖子部门）
  "roles": ["knowledge_admin"],
  "groups": ["sg_17"],            // 共享组（授权主体 > 20 时用它收敛）
  "users": ["u_1024"],
  "from": "2026-01-01T00:00:00Z",
  "to": null
}
```

用户属性展开成：

```json
{
  "user_id": "u_2048",
  "dept_paths": ["D10", "D10.3", "D10.3.7"],   // 自身 + 所有祖先，层级通常 ≤ 6
  "roles": ["employee", "fulfillment_ops"],
  "groups": ["sg_17"],                         // 共享组，与 acl_jsonb.groups 求交
  "approval_doc_ids": ["doc_881", "doc_902"],  // 审批临时授权，通常 < 50 条
  "subject_epoch": 1743                        // 主体属性版本，任一变则 +1
}
```

**为什么这样展开**：主体维度小且变化慢（部门层级最深 6 层、角色不过十几个），资源维度大且变化快。
**展开小的一边，条件判断大的一边**——这是整个设计的地基。

### 2.3 必须先说清楚：标签能表达什么，不能表达什么

`depts` / `roles` / `users` 这几个字段本质是「**资源 → 主体集合**」的归属声明，
也就是把权限**物化**到了资源侧。它不是权限模型，是权限模型的**缓存视图**。
真相永远在 `kb_acl_grant` 表里，`acl_jsonb` 只是为了让鉴权能下推而生成的派生数据。

| 能表达                             | 不能表达                                                                                          |
| ---------------------------------- | ------------------------------------------------------------------------------------------------- |
| 全员公开（`v=public`）           | **否定授权**（"部门可见但实习生除外"）→ 当前设计不支持，需加 `deny_*` 字段并让 deny 优先 |
| 某部门及子部门可见                 | **关系型授权**（"我上级可见"、"项目成员可见"）                                              |
| 某角色可见                         | **时间/状态相关**（在职、试用期、离职保留期）                                               |
| 少量点对点（`users` 字段，几条） | **大规模个体授权**（每人一个标签 = 标签爆炸，失去意义）                                     |

**三个必须显式定义、否则一定出事的语义**：

1. **部门继承方向**。当前实现是「授权给 D10 → D10 及其所有后代可见」，
   靠用户侧展开祖先链（`[D10, D10.3, D10.3.7]`）与文档侧 `depts` 求交实现。
   如果业务要求「仅直属可见，不含子部门」，就要改成精确匹配。
   **两种语义企业里都有人用，搞反了要么批量越权、要么批量失权**，必须写进契约文档。
2. **并集 vs 否定**。求值语义是「任一来源命中即可见」，没有 deny 优先级。
   一个人同时因部门授权和审批授权可见某文档，撤销部门授权后他仍应可见——所以不能做成"最后一条授权生效"。
3. **例外层不进标签**。审批授权与点对点共享**不物化**到 `acl_jsonb`，走小集合 `= ANY()`。
   原因是它们变化太快（审批到期、单点撤销），物化意味着每次审批都要刷 chunk，写放大不可接受。

### 2.4 什么时候标签方案会崩，以及怎么演进

| 规模                   | 方案                                                                                  | 触发迁移的信号                   |
| ---------------------- | ------------------------------------------------------------------------------------- | -------------------------------- |
| 单个文档授权主体 < 20  | 直接写进 `acl_jsonb`                                                                | —                               |
| 20 ~ 200               | 抽象成 **share_group**，文档只存 `group_id`；用户侧解析出所属 group 集合，用 `?\|` 匹配 | 单文档 `users` 数组开始变长      |
| > 200 或需要关系型授权 | 上 **ReBAC**（Zanzibar 式 relation tuple），可用 SpiceDB / OpenFGA              | 需要"项目成员""上级"这类动态关系 |

**为什么不到万不得已不上 ReBAC**：ReBAC 的权限求值需要递归展开关系图，
**展开过程无法和向量检索写进同一条 SQL**，一旦引入就回到"先取权限集、再过滤"的老路，
恰好破坏了本项目最核心的性质（鉴权与召回同语句）。这是真实的取舍，不是保守。

> 面试可以直接这么答："我不是不能上 ReBAC，是不划算——我的授权 90% 是部门/角色这类粗粒度归属，
> 标签物化就能下推到检索；真上 ReBAC，递归求值只能前置，反而退化成两段式查询。"

## 3. 第二个决定：一条 SQL 里同时做检索和鉴权

```sql
WITH permitted AS (
  SELECT c.id, c.parent_id, c.content, c.doc_id, c.embedding
  FROM kb_chunk c
  JOIN kb_doc_mirror d ON d.doc_id = c.doc_id      -- PG 内的文档级快照（不是 MySQL 的 kb_document）
  WHERE d.status = 'active'
    AND d.acl_from <= now()
    AND (d.acl_to IS NULL OR d.acl_to > now())
    AND (
          c.acl_jsonb->>'v' = 'public'
       OR c.acl_jsonb->'depts'  ?| $2::text[]     -- dept_paths
       OR c.acl_jsonb->'roles'  ?| $3::text[]     -- roles
       OR c.acl_jsonb->'groups' ?| $4::text[]     -- share groups
       OR c.acl_jsonb->'users'  ?  $1             -- user_id
       OR c.doc_id = ANY($5::text[])              -- approval_doc_ids（例外集合）
    )
)
SELECT id, content,
       1 - (embedding <=> $6) AS score
FROM permitted
ORDER BY embedding <=> $6
LIMIT 20;
```

> **为什么是 `kb_doc_mirror` 而不是 `kb_document`**：文档元数据与授权真相在 MySQL（`06-存储设计` §3），
> PG 里只是派生副本。同一条 SQL 要能 join 它，就必须有一张 PG 本地的文档级快照表——
> 否则这句 SQL 在物理上就跨库了，根本执行不了。这张表只存 `doc_id / status / acl_from / acl_to / acl_epoch / version`，
> 由 outbox 同步，**不含正文**。

要点：

| 细节                                                  | 原因                                     |
| ----------------------------------------------------- | ---------------------------------------- |
| 鉴权条件在 `permitted` CTE 里，与向量排序同一条语句 | 不存在"先召回再过滤"的时间窗             |
| `?` / `?\|\|` 是 jsonb 顶层键或数组元素的包含判断 | **索引必须用默认 `jsonb_ops`**；`jsonb_path_ops` 只支持 `@>`，用它会直接报错找不到操作符 |
| 部门用祖先链展开，而非递归查子树                      | 单次查询 O(1)，避免递归 CTE 拖慢检索     |
| 审批授权走独立小集合 `= ANY()`                      | 它是用户维度的例外，无法表达成资源侧条件 |

> 一个可选优化：把 `acl_jsonb` 里的三个维度拆成 `text[]` 列（`acl_depts/acl_roles/acl_groups/acl_users`），
> 用数组 `&&` 判重叠。数组 GIN 比 jsonb `?|` 少一层封装，实测快 20%~30%，代价是列数变多、加维度要改表。
> **当前不做的理由**：50w~200w chunk 下瓶颈在 HNSW 而不在过滤，先留扩展点。

### 混合检索同样下推

BM25 那一路是同一个 `permitted` CTE，只是排序函数换成 `ts_rank`。两路结果在应用层做 RRF 融合，
**融合的是已鉴权结果**，不是全量结果——这点很重要，融合不会放大可见范围。

### 性能上的一个坑

pgvector 的 HNSW 是近似索引，带强过滤时可能出现"候选集被过滤光导致召回骤降"。
三个手段，按成本递增：

1. **pgvector 0.8+ 的 iterative index scan**：过滤后不足 k 条时继续扫描索引。
2. **粗细分区**：`public` / `org` 这类大面（约 90% chunk）走一张表全量 HNSW；
   `scoped` 受限内容（约 10%）单独建表，用更小的索引 + 更强的过滤。两路结果合并。
3. **按部门分区表**：只有 chunk 量过千万才值得。

> 面试可以讲：这不是理论问题，是我在压测里撞到的——过滤条件一加，Recall 从 0.9 掉到 0.6，
> 因为 HNSW 只扫了很小一段候选就没了。

## 4. 第三个决定：缓存主体属性，不缓存结果文档集

这是最容易被做错的地方。

| 缓存什么                                                     | 失效频率                                                   | 结论                             |
| ------------------------------------------------------------ | ---------------------------------------------------------- | -------------------------------- |
| 结果：`user → [doc_id...]`                                | 文档新增、权限变更、部门调动、审批到期 → **极高频** | 不缓存                           |
| 输入：`user → {dept_paths, roles, groups, approval_doc_ids, subject_epoch}` | 仅人员/组织/审批变化 → 低频                               | **缓存 5 分钟 + 事件失效** |

```python
@cache(key="subject:{user_id}", ttl=300)
def resolve_subject(user_id) -> SubjectContext: ...

# 失效事件
#   org.dept_changed / role.changed / approval.granted / approval.revoked
# 注意：document.* 事件不失效此缓存
```

好处：**文档侧的任何变化都不需要清用户缓存**，因为缓存的是"我是谁"，不是"我能看什么"。

代价：多一次属性求值（一次 join，< 2ms），换来的是彻底避开失效风暴。

## 5. 第四个决定：权限贯穿整条 Agent 链路

只守住 `retrieve` 那一条 SQL 是不够的。Agentic RAG 有八个地方会漏（第 8 条是历史会话回看，最晚发现的一条）：

| 环节                  | 泄漏方式                               | 防护                                                                                                    |
| --------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| **1. 多轮检索** | 第二轮用"更宽"的条件重查               | `AuthContext` 全程只读，节点拿不到修改权，构造时 `frozen=True`                                      |
| **2. 查询改写** | 改写把"我们部门"改成"公司所有部门"     | 改写结果与原始 query 做范围一致性检查；改写 prompt 显式禁止扩大范围                                     |
| **3. 图谱扩展** | 图里存的是全局关系，扩展出的邻居没过滤 | `graph_expand` 返回的 chunk 必须再过一次同一个 filter，**图查询结果一律视为候选，不视为已授权** |
| **4. 父块回填** | 子块可见但父块跨了另一份受限文档       | 父块继承 `doc_id`，同一 filter 重查一次，不复用子块结果                                               |
| **5. 引用生成** | 模型编造引用编号指向未召回文档         | 引用只能从本次 `evidence` 集合里选；`verify_citations` 校验编号 ∈ 证据集                           |
| **6. A2A 委派** | 内部调用被当成"可信"而放宽             | 委派必须携带最小 `scope`；被调方按自己的权限模型二次校验，**绝不继承调用方权限**                |
| **7. 语义缓存** | A 的问题命中 B 的缓存答案              | 缓存 key = `hash(query_embedding_bucket + acl_fingerprint)`，指纹含 dept_paths 与 approval 摘要       |
| **8. 历史会话回看** | 授权撤销后，历史回答里仍存着受限内容全文 | 渲染时比对 `citation.acl_epoch` 与文档当前 `acl_epoch`，不一致则置灰"原文已失权"，**不可展开、不可跳转** |

第 8 条是最晚发现的一条：前面的防护都在"回答时"，但用户还能**翻旧会话**。
旧会话里存着的是当时合法、现在已失权的文档全文——等于给撤销操作留了个后门。
所以引用不能只存文字，必须存 `acl_epoch`（权限版本号），渲染时做一次比对。
详见 `07-记忆与会话设计.md` §3.3。

第 7 条尤其容易踩：语义缓存上线后效果很好，然后某天发现跨部门串答案。
**只要缓存的是"答案"，就必须把授权上下文编进 key。**

第 3 条也很隐蔽：很多人以为"图里查出来的东西总是对的"，但图是全局构建的，权限是查询时才有意义的。

## 6. 权限变更的传播

### 6.1 两套授权，方向相反

这是"部门那一套"和"审批那一套"能融合、又必须分开建模的根本原因：

| | 部门 / 角色 | 审批 / 点对点 |
|---|---|---|
| 声明方向 | **资源 → 主体**（这份文档谁能看） | **主体 → 资源**（这个人被批准看什么） |
| 存在哪 | 资源侧 `acl_jsonb.depts/roles` | 主体侧 `approval_doc_ids` |
| 关系形态 | 一对多且稳定（一个部门几百人） | 一对一且临时（一条审批一个文档） |
| 变更频率 | 低（组织架构调整时） | 高（随申请产生、到期消失） |
| 求值方式 | 与用户 `dept_paths` 求交 | 与候选 `doc_id` 求交 |

**融合点只有一个：同一条 `WHERE` 里的 `OR`。**
不是把两套模型合成一套，而是把两种方向相反的编码都归约成布尔谓词。

### 6.2 为什么不能"先算集合再合并"

反面做法：

```python
visible = dept_set | approval_set          # 合并
visible.discard(doc_id)                    # 撤销部门授权
```

**这里会误删。** 如果某文档同时在两个集合里（既被部门授权、又被审批授权），
撤销部门授权时 `discard` 会把审批那一路的可见性也一并抹掉。
而集合本身不携带来源信息，你无法判断"它当初为什么在里面"。

谓词模式没有这个问题：撤销部门授权 = 从 `acl_jsonb.depts` 移除该部门，
`approval_doc_ids` 不动，重新求值时任一路成立即仍可见。

> **删除永远作用在"来源"上，不作用在"结果"上。**
> 这是谓词模型相对集合模型的根本优势，也是"融合"能在工程上成立的前提。

### 6.3 三条传播链路，一个求值点

| 授权类型 | 撤销时改什么 | 失效什么 |
|---|---|---|
| 部门 / 角色（资源声明） | 刷 `kb_chunk.acl_jsonb` 快照 | 不清用户缓存 |
| 审批（主体租约） | 改审批状态 → 重算 `approval_doc_ids` | 清 `subject:{uid}` |
| 点对点共享（资源声明） | 改 `acl_jsonb.users` | 不清用户缓存 |

三条链路走向完全不同，但**汇合在同一个求值点**——这就是为什么融合只需要一条 `OR`，
而不是在应用层写两套判定再合并。

> 注意区分**点对点共享**和**审批授权**：前者是资源属性（"这份文档给这个人"），可物化进 `users`；
> 后者是主体租约（"这个人被批准看这份文档"），带时效，不能物化。同为 user→doc，语义不同，归属也不同。

### 6.4 事件流

```
文档 ACL 变更
  → Java 写 kb_acl_grant + outbox 表（同一事务）
  → 异步消费 → 批量 UPDATE kb_chunk SET acl_jsonb = ...
  → 不需要失效任何用户缓存（见第 4 节）
  → 触发越权集回归（CI 必跑，不是可选）
```

**为什么用 outbox**：MySQL 与 PG 是两套库，无法用本地事务保证一致。
outbox + 幂等消费（按 `event_id` 去重）+ 每日对账任务（抽样比对 grant 与 chunk.acl_jsonb）是唯一稳的做法。

**一致性窗口**：只要方向对，"允许不一致"就说得清——**扩权可以慢几秒（用户只是少看见一会儿），收权不能慢**。
所以实现上是"收权同步写、放权异步写"：撤销时先同步删 PG 侧快照再提交 MySQL 事务，
失败则回滚，最坏结果是短暂失权而不是短暂越权。跨库 join 那条路走不通（PG 检索 SQL 物理上 join 不到 MySQL），
只能靠写顺序保证方向性。这个取舍要写进文档——面试官会问"撤销权限后多久生效"。

## 7. 排障域的权限（另一套模型）

知识域是文档级 ACL，排障域是**行列级 + 动作级**，两者不能共用一套规则。

| 维度               | 做法                                                                                                          |
| ------------------ | ------------------------------------------------------------------------------------------------------------- |
| **行级**     | 不在 prompt 里约束，而是在 SQL 层强制注入 `WHERE warehouse_id IN ($allowed)`。模型永远看不到越权的行        |
| **列级**     | 敏感字段（手机号、地址）在**出库时**就脱敏，进模型上下文之前                                            |
| **动作级**   | Agent 只产出 `propose_action`，写 `action_request` 等审批；Agent 进程持有的数据库账号**没有写权限** |
| **跨域委派** | 知识域委派给排障域时只传 `scope = {warehouse, time_range}`，排障域按自己的规则再校验一遍                    |

> 一句话区分：**知识域防"看到不该看的"，排障域防"做了不该做的"。**
> 前者靠检索条件，后者靠能力剥夺（不给写权限），而不是靠 prompt 说"不要写"。

## 8. 怎么证明它真的有效

设计说得再好，没有验证就是自说自话。

### 越权集构造

```
4 类角色（普通员工 / 部门管理员 / 跨部门协作 / 审批授权者）
  × 20 份不同归属文档
  = 80 组，每组 1~2 个只指向该文档的问题
```

判定方法不看"有没有返回内容"（Agent 可能拒答也可能泛泛而谈），
而是看 **回答里有没有出现该文档的稀有特征串**（特定编号、专有名词）——用黑名单匹配，可自动化。

### 门禁

| 检查                      | 阈值     | 失败后果           |
| ------------------------- | -------- | ------------------ |
| 越权泄漏率                | 必须 = 0 | **阻断合并** |
| 拒答泄漏率                | 必须 = 0 | 阻断合并           |
| ACL 快照与 grant 对账差异 | = 0      | 告警               |
| 语义缓存指纹覆盖率        | = 100%   | 阻断合并           |

### 边界用例清单（面试最容易被追问）

| 场景            | 期望行为                                                         |
| --------------- | ---------------------------------------------------------------- |
| 审批到期        | 到期时刻起立刻不可见，缓存同步失效                               |
| 部门调动        | 旧部门文档立刻不可见，新部门文档立刻可见                         |
| 共享撤销        | 后续问答不可见；历史会话保留原答案但标记"原文已失权"             |
| 文档升级版本    | 旧版本 chunk 下线，新版本入索引，引用指向新版本页码              |
| 管理员/审计角色 | 可看全部但**每次访问留审计日志**，且审计日志不可被自己删除 |
| A2A 委派        | 被调方不得因"内部调用"而放宽                                     |
| 语义缓存        | 跨用户不得命中                                                   |
| 跨部门共享冲突  | 多来源取并集（任一来源授权即可见），但撤销时必须所有来源都撤销才失权   |

最后一条容易被忽略：一个人同时因"部门授权"和"审批授权"能看到某文档，撤销部门授权后他仍应可见——
因为审批还在。所以**求值必须是"任一来源满足即可"，而不是"最后一条授权生效"**。

### 授权叠加用例（最容易被重构改坏的一组）

这一类用例既不是"越权"也不是"失权"，而是**多来源叠加后的撤销语义**。
必须单独成组、进 CI，否则某次重构把谓词改成集合合并，测试不会报警。

前置：用户 `u_2048`（`dept_paths=[D10]`），文档 `doc_X` 同时被「部门 D10」和「审批单 AP-01」授权。

| 用例 | 操作 | 期望 | 说明 |
|---|---|---|---|
| U1 | 无操作 | 可见 | 两路同时命中 |
| U2 | 撤销部门 D10 | **仍可见** | 审批 AP-01 仍在——这是本设计的正确行为，不是漏洞 |
| U3 | 撤销审批 AP-01 | **仍可见** | 部门 D10 仍在（对称用例，同样重要） |
| U4 | 两路都撤销 | 不可见 | 只有全撤才失权 |
| U5 | 审批自然到期 | **仍可见** | 到期只让一路失效 |
| U6 | 审批到期 + 撤销部门 | 不可见 | |
| U7 | 部门授权改为 D10.3（子部门） | 仍可见 | 祖先链命中 |
| U8 | 用户调至 D20 | 见下方业务语义决策 | 依赖审批是否绑定申请时部门 |

**U6 的实现验证点**：撤销部门授权时，SQL 必须只删除
`source='static' AND subject_type='dept' AND subject_id='D10'` 那一条 grant，
**不能**按 `doc_id` 批量删——按文档删会把审批那条一起删掉，这正是集合模式会犯的错。

### 已决策：审批独立生效（ADR-0001）

U8 暴露了一个技术之外的问题：**审批授权是否依赖申请时的部门归属？**

**已拍板：采用方案 A —— 审批独立生效。详见 `docs/adr/0001-审批授权独立生效.md`。**

| 方案 | 语义 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| **A. 审批独立生效** | 审批一旦通过，在有效期内独立于组织架构 | 实现简单、可解释、契合"授权是契约" | 调岗后仍可看旧部门文档直到到期 | **已采纳** |
| B. 审批绑定上下文 | 存申请时部门，部门变化则失效 | 更收敛 | 矩阵组织下"绑定哪个部门"无法定义；求值要回溯，破坏单 SQL | 否决 |

**决策落地必须区分三个"失效"维度**（混淆任意两个都会出事）：

| 维度 | 触发 | 是否使审批失效 |
|---|---|---|
| 授权失效 | 审批到期、主动撤销 | 是 |
| **主体失效** | 离职、账号停用 | **是，一票否决，且优先于所有授权求值** |
| 组织变更 | 调岗、部门调整 | 否 |

"审批独立"独立的是**组织架构**，不是**人是否在职**。离职员工因审批未到期仍可访问，
是这类设计最常见的严重漏洞——账号状态检查必须放在 `SubjectContext` 解析最前面。

**六条缓解措施**（缺一即视为决策未落地）：`granted_context` 审计快照、调岗触发审批复核、
单条有效期上限 90 天、单人持有量软上限 50 条（超限降级为强一致 join）、月度审计报表、访问留痕到具体审批单。

### 谓词模式的额外红利：可解释性

因为每个条件都独立成立，系统可以逐条回答"**你为什么能看到这份文档**"：

```
doc_X 对 u_2048 可见，命中 2 路：
  1. 部门授权：D10（来源 static，授权人 admin，2026-03-01）
  2. 审批授权：AP-01（审批人 李经理，2026-11-01 通过，2026-12-01 到期）
```

集合模式只能回答"在集合里"，说不出为什么。企业知识库的权限申诉、合规审计场景里，
这个能力比性能优化更值钱。

## 9. 场景支持矩阵

### 9.1 先回答典型场景

> 「某用户的可见文档 = 部门共享授权 + 全公司可见文档 + 单独授权的部分文档，取并集」

**支持。而且这正是本设计的默认语义——并集。**

但要强调一点：**并集是谓词层面的并集，不是先把三份清单算出来再合并。**
如果先算清单，就回到了 2.1 节说的 1500 万条缓存问题。

对应到 SQL，四路来源各是一个条件，用 `OR` 连起来：

| 来源 | 条件 | 备注 |
|---|---|---|
| 全公司可见 | `acl_jsonb->>'v' = 'public'` | 也可拆出 `org`（限本公司，排除子公司） |
| 部门共享 | `acl_jsonb->'depts' ?\| $dept_paths` | 祖先链展开，父部门授权覆盖子孙 |
| 角色可见 | `acl_jsonb->'roles' ?\| $roles` | |
| 共享组 | `acl_jsonb->'groups' ?\| $group_ids` | 授权主体多时用它收敛 |
| 点对点（少量） | `acl_jsonb->'users' ? $user_id` | 超过 20 个转共享组 |
| 审批临时授权 | `doc_id = ANY($approval_doc_ids)` | 不物化进标签，走小集合 |

**这里有个实现陷阱**：很多系统把"部门那一套"和"审批那一套"分成两个查询再合并，
结果漏掉"某文档既被部门授权、又被审批授权"时的撤销逻辑（撤销部门授权后审批那路还应该在）。
用同一条 `OR`，天然合并，不会漏。

### 9.2 走查示例

用户张伟：`user_id=u_2048`，`dept_paths=[D10, D10.3, D10.3.7]`，
`roles=[employee, fulfillment_ops]`，审批例外 `[doc_E]`。

| 文档 | 授权配置 | 结果 | 命中哪一路 |
|---|---|---|---|
| A | `v=public` | 可见 | 全公司 |
| B | `depts=[D10.3]` | 可见 | 部门（祖先链含 D10.3） |
| C | `depts=[D10.3.9]` | **不可见** | 兄弟部门不在祖先链上 |
| D | `depts=[D20]` | 不可见 | 无交集 |
| E | 无任何 `depts`，仅有审批记录 | 可见 | 审批例外集合 |
| F | `roles=[knowledge_admin]` | 不可见 | 角色未命中 |
| G | `depts=[D10]` + `users=[u_2048]` | 可见 | 两路都命中（并集，去重） |
| H | `v=public` 但 `deny_users=[u_2048]` | **本设计不支持** | 见 9.5 |

### 9.3 资源侧：授权对象

| 能力 | 支持度 | 说明 |
|---|---|---|
| 全员公开 | 支持 | `v=public` |
| 限本公司（排除子公司） | 支持 | `v=org` + 租户字段 |
| 指定部门（含子部门） | 支持 | 默认语义，靠祖先链匹配 |
| 指定部门（仅直属，不含子部门） | 受限 | 需切换为精确匹配；**这是全局开关，一旦确定不能混用** |
| 指定角色 | 支持 | |
| 指定用户（点对点） | 支持（少量） | > 20 转共享组 |
| 共享组 | 支持 | `kb_share_group`，文档只存 group_id |
| 多条件组合（部门 OR 角色 OR 用户） | 支持 | 并集 |
| 多条件同时满足（AND，如"部门内且职级≥P7"） | 受限 | 靠规则层**预计算物化**，不在查询时求值 |
| 否定授权（部门可见但实习生除外） | **不支持** | 需加 `deny_users`/`deny_roles`，且 deny 优先 |
| 密级比较（密级 ≤ 用户密级） | 受限 | 可写 `(acl->>'level')::int <= $lv`，但索引效果差，建议物化成角色 |

### 9.4 主体侧：用户属性

| 能力 | 支持度 | 说明 |
|---|---|---|
| 一人多部门（兼职/矩阵组织） | 支持 | `dept_paths` 可为多条链 |
| 一人多角色 | 支持 | 角色集合 |
| 部门层级继承 | 支持 | 任意深度，靠祖先链 |
| 角色层级继承（admin ⊃ employee） | 扩展即可 | 在解析主体时把角色闭包展开进 `roles` |
| 外部用户组（AD/LDAP） | 支持 | 等同角色处理 |
| 组织调动即时生效 | 受限 | 事件 + 缓存 TTL，严格即时需走强一致读 |
| 离职/停用即时失效 | 受限 | 需在主体解析时校验账号状态，否则 token 有效期内仍可访问 |

### 9.5 明确不支持的（要主动说）

| 场景 | 为什么不做 | 要做的话怎么扩 |
|---|---|---|
| 否定授权（deny） | 增加优先级语义，与并集冲突，容易引发误判 | 加 `deny_*` 字段，`WHERE ... AND NOT (deny 命中)` |
| 关系型授权（"我上级可见"、"项目成员可见"） | 需递归求值，无法与向量检索同语句（见 2.4） | ReBAC（SpiceDB / OpenFGA） |
| 段落级/字段级文档权限 | 粒度太细，运营成本高于收益 | chunk 级已可单独设 `acl_jsonb`，但需人工维护 |
| 附件（文档内图片）独立权限 | 附件未作为独立资源建模 | 附件升格为 resource，与 doc 建关联 |
| 依赖授权（看完 A 才能看 B） | 属于流程控制，不属于访问控制 | 在会话层做状态机，不进权限模型 |

### 9.6 一句话边界（面试用）

> 支持"并集式"的粗粒度授权：公开、部门（含子部门）、角色、共享组、点对点、审批临时六路取并集，
> 且六路在同一条检索语句里判定。
> 不支持否定授权和关系型授权——前者需要优先级语义，后者需要递归求值，都会破坏"鉴权与召回同语句"这个性质。
> 这两个是明确的技术取舍，不是遗漏。

## 10. 一句话总结（面试用）

> 我把权限拆成两层：**条件层**解决"大面可见"（部门、角色、公开），**例外层**解决"个体授权"（审批、点对点共享）。
> 条件层跟着检索语句走，一条 SQL 里完成鉴权和召回；例外层是几十条 id 的小集合，用 `= ANY()` 拼上去。
> 缓存的是主体属性而不是结果清单，所以文档侧怎么变都不用清缓存。
> 最后把同一条授权上下文贯穿到多轮检索、查询改写、图谱扩展、父块回填、引用校验、A2A 委派、语义缓存、历史会话回看这八个出口——
> 少堵一个，前面全部白做。
