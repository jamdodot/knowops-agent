# 文档解析设计

解析是 RAG 的上限。下游所有优化——分块、嵌入、检索、重排——都在这个上限之下工作。
这份文档说明当前主流设计、2026 年的关键变化，以及本项目的路由策略。

---

## 1. 不是两代，是四层

谈"管道 vs VLM"之前，先要看到最便宜的那一层，很多项目直接跳过了：

| 层 | 做法 | 成本 | 适用 |
|---|---|---|---|
| **L0 数字原生直取** | PyMuPDF / pdfplumber / Camelot 直接读 PDF 文字层与矢量内容 | **最低，无需 GPU** | 有文字层的 PDF、规则表格 |
| **L1 管道式** | 版面检测 → 区块分类 → OCR → 阅读顺序 → 结构还原 | 中（CPU 可跑） | 扫描件、复杂版面 |
| **L2 VLM 直出** | 整页渲染成图，一个视觉语言模型直接输出 Markdown / 结构化 | 高（需 GPU） | 扫描件、手写、怪版面 |
| **L3 混合双后端** | 管道 + VLM 双后端 + 级联路由 | 中高 | **2026 生产系统的主流拓扑** |

**很多人一上来就在 L1/L2 里选，忘了 L0。** 一个有文字层的 PDF 用 MinerU 跑一遍要 0.76 秒/页，
用 PyMuPDF 抽文字是毫秒级，而且**结果更准**——OCR 反而会引入识别错误。

判据只有一条：**文字覆盖率**。抽出文本非空白字符数 / 预估字符数 > 阈值就走 L0。
`90%` 以上直接取，`40%~90%` 走管道补齐，`40%` 以下才认为没有文字层。

## 2. 两代路线的真实差别

### L1 管道式

```
页面光栅 → 版面检测(如 DocLayout-YOLO / RT-DETR)
        → 区块分类(标题/正文/表格/公式/图注/页眉页脚)
        → 各区块分别识别(PaddleOCR / TableFormer / UniMERNet)
        → 阅读顺序重排(基于坐标 + 规则 + 排序模型)
        → 拼装 Markdown / JSON
```

| 优点 | 缺点 |
|---|---|
| 每步可解释、可单独替换、可只跑其中几段 | **误差级联**：版面框错了，OCR 再强也没用 |
| 输出确定性，同页多次跑结果一致 | 工程栈重，多模型多依赖 |
| 便于业务定制（金融优化表格、政企优化红头文件） | 阅读顺序重排规则难覆盖多栏/图文混排 |

**误差级联是它最大的现实问题**，而且很隐蔽：单看每个模块指标都不错，合起来就不稳定。
排查时发现不是某个模型差，而是链路太长、边界条件太多——"一堆小概率偏差在复杂文档里叠加"。

### L2 VLM 直出

```
页面渲染成图 → 一个 VLM → 直接吐 Markdown
```

| 优点 | 缺点 |
|---|---|
| **阅读顺序天然正确**（模型直接"看懂"版面） | **会幻觉**——生成式模型的固有风险 |
| 架构极简，一个模型一次前向 | 错了不知道错在哪个环节，难局部调试 |
| 对怪版面、手写、彩色背景适应性强 | 需要 GPU；超长页面受分辨率和 token 限制 |

## 3. 2026 年的关键变化：界线正在溶解

这是过去一年最重要的变化，不了解就会做出过时的判断。

### 3.1 小模型打赢了大模型

公开榜单（OmniDocBench）上，排在前面的不是 GPT 级通用视觉大模型，而是**专用小模型**：

| 模型 | 参数量 | 说明 |
|---|---|---|
| PaddleOCR-VL | 0.9B | 中文场景强，许可证友好 |
| MinerU2.5 | 1.2B | 表格/公式/CJK 综合强 |
| Granite-Docling | 258M | IBM，端侧可用 |

而 200B+ 的通用视觉大模型排在它们后面。

**原因很简单：文档解析是"窄而深"的任务。** 通用大模型的视觉能力被摊薄在无数任务上，
而专用模型把全部容量压在版面、表格、公式这几件事上。**参数规模在这里不是决定性因素，分辨率工程才是。**

### 3.2 管道与 VLM 的界线被"溶解"了，不是谁赢了

MinerU2.5 的做法最能说明问题：

> **先对降采样图解码全局布局，再裁剪区域用高分辨率重读。**
> 版面检测和文字识别被融合进同一个模型的两次 pass。

它既不是纯管道（没有一个独立的版面检测模型串在流水线上），也不是纯 VLM 直出（不是一次前向出全文）。
所以"管道 vs VLM"这个二选一的问题本身在失效。

**结论：不要再问"选哪一代"，要问"双后端怎么路由"。**

### 3.3 一个必须注意的坑：自报分数和公开榜差 2 分

多个模型 README 上写的分数，比公开榜单高 2 分左右。
**排期前先自己复现一个数**，不要拿厂商自报数字做技术决策。

## 4. 真正决定质量的是三件事，不是文字识别

文字抽取已经基本解决——所有工具都能把纯文本抽对。**方差全在下面三处**：

### 4.1 表格

表格在向量库里变成一坨扁平数字，是 RAG 最典型的静默失败：
chunk 看起来很正常，回答却微妙地、自信地错。

- 输出格式选 **HTML**（能保 `rowspan`/`colspan`），不要拍平
- 规则表格（有框线、财务表格）**用 Camelot 直接读矢量内容**，不需要 GPU，比任何模型都准
- 评测用 **TEDS**（树编辑距离），不要用文本相似度

### 4.2 阅读顺序

多栏页面的分栏拼错、图注离表格两个 chunk 远、侧边栏插进正文中间——**顺序错了，再好的 embedding 都救不回来**。
因为下游切块依赖文本顺序。

### 4.3 页眉页脚清洗（最容易被忽略，影响却最大）

这是我认为最值得单独讲的一条：

> 页眉页脚、水印、页码、目录页如果不清洗，会被原样解析保留，
> **切块后变成一批高度相似的垃圾块，检索时白白挤占召回名额。**

一份 200 页的报告，页眉重复 200 次，在向量空间里形成 200 个几乎相同的点，
查询时它们会挤掉真正该召回的内容。**这属于"没洗掉"而不是"识别错"，所以很多团队查不出来。**

MinerU 之所以在归档类任务里被反复选用，很大程度是因为它做了两件大多数工具跳过的事：
**自动页眉页脚移除** + **跨页表格合并**。这两件事单独就值好几分下游检索质量。

所以本项目把清洗单独成阶段，并且**清洗规则可配置**（不同来源的文档页眉模式不同）。

## 5. 最终方案：Docling 主力，MinerU 兜底

**核心观点：选型的重点不是"选哪个工具"，而是"怎么分工 + 怎么路由"。**

前面几节讲的是行业格局，这一节是本项目在**一台 16GB 无独显电脑**上的收敛结论。
和常见推荐（MinerU 当主力）相反，这里把两者角色对调，理由见 5.1。

### 5.1 为什么主力是 Docling 而不是 MinerU

三个理由，按决策权重排序：

| 权重 | 维度 | Docling | MinerU |
|---|---|---|---|
| **1** | **许可证** | **MIT，无附加条件** | Apache-2.0 **+ 附加条件（有营收门槛）** |
| **2** | **格式覆盖** | PDF / DOCX / PPTX / HTML / XLSX / MD **一个引擎全包** | 只做 PDF |
| **3** | **依赖与内存** | `pip install` 即用，纯 CPU，占用低 | 依赖重，峰值 3~5GB，CPU 慢 |

**第 1 条是决定性的。** 这个项目的定位是"能拿去公司落地、能在面试里讲"，许可干净比准确率高 2 分重要得多。

**第 2 条是实际收益。** 企业知识库是 PDF + Word + PPT 混合的。如果 MinerU 当主力，Office 格式仍要 Docling 补，结果变成"两个引擎都在关键路径上"，复杂度翻倍。反过来让 Docling 当主力，**Office 格式直接吃掉，PDF 也基本够用，MinerU 只在疑难 PDF 上出现**。

**那 MinerU 留着做什么？** 它有两个 Docling 比不了的能力：

- **中文复杂版面**：竖排、多栏混排、公式密集、合并单元格复杂的表格
- **页眉页脚自动移除 + 跨页表格合并**：这两件事在大批量归档里对检索质量影响极大（见 4.3）

所以 MinerU 的定位是**兜底专家**——出现频率低，但每次出现都是 Docling 啃不动的硬骨头。

> 这个分工的好处是：**MinerU 不在关键路径上**。它 CPU 慢（2~10 秒/页）、内存峰值高（3~5GB），
> 但因为只在少数文档上按需启动，这两个缺点都不构成问题。

### 5.2 四路路由（按页判断，不按文件）

```
                    ┌─ Office 格式 ────────→ Docling（原生解析）────────┐
                    │                                                  │
文件 → 探测 ────────┼─ 覆盖率 > 90% ───────→ L0 直取 PyMuPDF ──────────┼→ 质量闸门 → 统一 IR → 清洗 → 分块
                    │    规则表格 → Camelot/pdfplumber 补表            │        │
                    ├─ 覆盖率 40~90% ──────→ Docling parse ────────────┤        │ 不合格
                    │                                                  │        ▼
                    └─ 覆盖率 < 40% ──────→ MinerU pipeline + OCR ─────┘   MinerU 兜底一次
                                                                              │ 仍不合格
                                                                              ▼
                                                                        人工复核队列（不阻塞）
```

四个关键点：

1. **按页判断，不按文件。** 一份 300 页报告常常前 10 页是扫描件、后面全是数字原生。整份一刀切必然有一半处理错。
2. **L0 优先。** 有文字层就直接取，毫秒级且**比 OCR 更准**（OCR 会引入识别错误）。很多项目直接跳到"选哪个 OCR"，忽略了最便宜也最准的一层。
3. **质量闸门决定要不要兜底。** 不是"Docling 跑完就完事"，而是产出 IR 后检查表格完整度与阅读顺序置信度，不达标才调 MinerU。**兜底是有条件的，不是默认路径。**
4. **低置信进复核队列，不阻塞。** 入库流水线不能因为一份文档卡住。

### 5.3 VLM 直出为什么不在生产路径

L2（VLM 整页直出）是 2026 年的技术热点，但**本项目不用**，三个理由：

- **没有 GPU**：VLM 直出在 CPU 上慢到不可用（每页数十秒到分钟级）
- **不可归因**：端到端输出一个 Markdown，出了错你不知道是版面错了、识别错了还是顺序错了，评测无法定位
- **收益重叠**：它擅长的场景（扫描件、复杂版面）已经被 MinerU 兜底覆盖

保留为**预研项**：只在 `docs` 里记录路线与判断依据，不进入实现。面试被问"你怎么看 VLM 解析"，答"我评估过，在我这个硬件和归因要求下不划算，触发条件是有了 GPU 且要处理手写体"——这比硬上一个跑不动的组件更专业。

### 5.4 配置

路由与闸门全部写在配置里，不写死在代码（`config/parse.yaml`）：

```yaml
parse:
  probe:
    text_coverage_high: 0.90
    text_coverage_low: 0.40
    layout_complexity_high: 0.70     # 多栏 / 公式 / 合并单元格密度
  routes:
    office:   { engine: docling }
    native:   { engine: pymupdf, table: camelot_or_pdfplumber }
    pipeline: { engine: docling }
    scanned:  { engine: mineru, backend: pipeline, ocr: true }
  rescue:
    engine: mineru                   # 仅当质量闸门不通过
    backend: pipeline
  quality_gate:
    min_table_integrity: 0.85
    min_reading_order_conf: 0.70
    on_fail: rescue_then_review
  clean:
    strip_header_footer: true
    strip_watermark: true
    drop_toc: true                   # 目录页对检索无价值，纯噪声
```

### 5.5 实施顺序（不要一次全上）

| 阶段 | 做什么 | 覆盖率 |
|---|---|---|
| **M1** | L0 直取 + Docling（PDF/Word/PPT） | 约 80% 的企业文档 |
| **M1 末尾** | 质量闸门 + `parse_report` 指标 | 能看出剩下 20% 差在哪 |
| **M2** | MinerU 兜底接入 | 补上复杂版面与扫描件 |
| **不排期** | VLM 直出 | 只写预研，不实现 |

**先做 80% 再补 20%**，这样 M1 就能跑通全链路，而不是卡在解析上。

### 5.6 托管形态：哪些必须本地，哪些能走云 API

这一节回答一个很具体的问题：**这四个工具，哪些是本地部署、哪些有线上 API？**

先给事实，再给决策。两者要分开——事实是"能不能"，决策是"要不要"。

| 工具 | 形态 | 线上 API | 本项目决策 |
|---|---|---|---|
| **PyMuPDF** | 纯 Python 库 | **没有** | 本地（唯一选项） |
| **pdfplumber / Camelot** | 纯 Python 库 | **没有** | 本地（唯一选项） |
| **Docling** | Python 库 + `docling-serve` | **无公开 SaaS**；IBM watsonx 有托管版（企业采购） | 本地 pip。`docling-serve` 是自托管，不解决算力 |
| **MinerU** | 本地部署 / 桌面端 / **官方在线 API** | **有**（mineru.net） | **本地**（云 API 保留为备选开关） |

**前三个工具没有选择余地，第四个有。**

它们的价值是"直接读 PDF 内部结构"，这个动作本地做是毫秒级、零成本的。传上云要做的是：序列化、上传、排队、解析、回传——**多了一圈往返，却一点算力都没省下来**。

Docling 的 `docling-serve` 容易被误解成云服务，它其实只是 FastAPI 壳：解决"把解析变成 HTTP 接口"，**不解决"没有算力"**，镜像 4.4GB 起步。

只有 MinerU 是真的两种形态都能跑：本地管道后端（CPU 可跑、2~10 秒/页）和官方在线 API（异步任务制）。

#### 决策：全部本地

```
parse_mode: local
```

四个引擎都跑在本机。理由不是"本地更先进"，而是**本地更简单**，并且省下的东西正好是当前阶段最需要的：

| 本地跑省掉 | 云 API 需要承担 |
|---|---|
| 不用申请第三个 key | 多一个凭证要管、要轮换 |
| 不受配额约束，一次入库 500 份也不用排队等额度 | 免费额度口径不透明，Pro 才给 API |
| **原文不出域**，将来接真实文档不用返工 | 上传的就是原文，最敏感的那类数据 |
| 断网可用，面试现场演示不怕网络 | 依赖外网，现场挂掉很难看 |
| 成本可预测（只有电费和 CPU 时间） | 按页计费，评测回归会持续烧钱 |
| 出错能断点调试，能改源码 | 黑盒，错了只能提工单 |

**代价只有一条，而且是可管理的：内存峰值 3~5GB。**

所以 `resources.mineru_concurrent: 1` 是硬约束——不是保守，是并发必然 OOM。同时解析是入库时的一次性开销、不在请求链路上，慢和吃内存都不影响问答延迟。

这里要提前把一个坑写死：**MinerU 首次运行会下载约 1~2GB 权重**。必须提前预制（`weights.prebake: true`），否则第一次入库会卡在下载上，而且报错信息很不明确。

#### 保留一个开关，而不是保留一条代码路径

配置里有 `parse_mode: local | hybrid`，`hybrid` 时只有兜底那一路改走云 API。

**这不是"以后可能用"的占位，它把接口约束固定下来了。** 因为云 API 和本地库的调用模型完全不同：

```
本地库：  parse(file) → IR                （同步，等返回值）
云 API：  submit(file) → task_id → poll → download zip   （异步，任务制）
```

这个差异会往下渗透：任务表要落库（进程重启能续）、要退避轮询、结果链接有时效必须及时落盘。**如果照本地库的习惯写成同步阻塞，一份 200 页文档会卡住工作进程十几分钟。**

所以 `mineru_cloud` 那段配置默认 `enabled: false`，但字段是完整的。真要切的时候，改一个值就能接上，不用重新设计。

#### 什么时候才值得切到 hybrid

写成触发条件，不是现在纠结：

| 触发条件 | 说明 |
|---|---|
| 有大量扫描件要批量处理，且本机只有 8GB | 内存是硬墙，只能外包 |
| 接入了涉密文档，需要按文档分级路由 | 公开走云、涉密走本地，混合形态才有意义 |
| 要并发处理（≥3 份同时） | 本地锁 1 会成为吞吐瓶颈 |

如果只是"想省点内存"，不值得——省 3GB 换掉上面那张表里的六条，不划算。

#### 一个必须记下来的许可证问题

L0 那一路用的 PyMuPDF 是 **AGPL-3.0**。这是整条解析链上**最容易被漏掉的许可**，因为它看起来只是个"工具函数"，不像模型权重那样显眼。

- 作品集自用、开源项目：无碍
- **闭源商用或对外 SaaS：要么买 Artifex 商业授权，要么换 `pypdfium2`（Apache-2.0，同能力，速度接近，接口不同需包一层）**

这条和 `8. 许可证` 那节讲的 Docling(MIT) / MinerU(Apache-2.0+阈值) 是同一类判断，只是它藏在最底下那一层。**"先看 LICENSE 再看 benchmark"这个顺序，要一直贯彻到 L0。**

## 6. 输出不能只有 Markdown

只输出 Markdown 会丢掉三样 RAG 必需的东西：

| 丢失 | 后果 |
|---|---|
| 页码 | 引用无法定位到"第 3 页"，用户无法核对 |
| 版面坐标 | 无法做高亮、无法定位原文 |
| 块级类型 | 无法区分"这是正文"还是"这是表注"，分块策略没法差异化 |

所以中间层必须是一个**统一 IR**：

```python
@dataclass
class Block:
    id: str
    type: Literal["title", "text", "table", "formula", "caption", "list", "figure"]
    content: str          # Markdown/HTML/LaTeX
    page_no: int
    bbox: tuple[float, float, float, float]   # 版面坐标，用于高亮与溯源
    level: int | None     # 标题层级
    parent_id: str | None # 标题树
```

**IR 是管道与 VLM 两条路线的统一出口**——不管用哪个引擎，下游分块只认 IR。
这是让"换引擎不改下游"成立的前提。

## 7. 质量度量（不做这步，后面全在猜）

解析质量必须量化，而且要能**区分"解析坏了"还是"检索坏了"**：

```sql
parse_report (
  doc_id, page_count,
  text_coverage,        -- 文本覆盖率
  table_recall,         -- 表格识别率（识别出的表格数/OCR检测到的表格数）
  table_teds,           -- 表格结构相似度
  reading_order_score,  -- 阅读顺序得分
  empty_ratio,          -- 空块率
  garbled_ratio,        -- 乱码率
  header_footer_leak,   -- 页眉页脚残留率 ← 容易被忽略
  ocr_confidence,       -- 平均置信度
  score, review_status
)
```

**低分文档进人工复核队列，不阻塞其他文档入库。** 这是"解析失败不拖垮整条链路"的关键。

`header_footer_leak` 这一项是本项目专门加的：它不体现在任何标准 benchmark 里，
但对检索质量的影响可能比表格还原率更大。

## 8. 许可证：一个比准确率更优先的选型维度

这一点在技术对比文章里几乎没人讲，但企业落地时是硬门槛：

| 工具 | 许可 | 注意 |
|---|---|---|
| **Docling** | MIT | 最干净，可无条件商用 |
| **PyMuPDF**（L0 直取） | **AGPL-3.0** | **闭源商用/SaaS 需买 Artifex 授权，或换 `pypdfium2`（Apache-2.0）** |
| pdfplumber / Camelot | MIT | 友好 |
| PaddleOCR-VL | Apache-2.0 | 友好 |
| DeepSeek-OCR | MIT | 友好 |
| **MinerU** | Apache-2.0 **+ 附加条件** | 有营收门槛条款；在线服务需署名 |
| Marker | 权重有额外许可 | 权重不能无条件商用 |

**建议的选型顺序：先看 LICENSE，再看 benchmark。**

**PyMuPDF 那行是这一节最容易漏的一条**——因为它藏在最底下那一层，看起来只是个"读文本的工具函数"，
不像模型权重那样显眼。但它恰恰是 AGPL，闭源商用会牵连整个产品。
所以配置里预留了 `license_fallback: pypdfium2`：同能力、Apache-2.0、速度接近，只是接口要包一层。

本项目是作品集项目，不受营收条款影响，但**在文档里写出来**——这说明选型时考虑过法务维度，
而不是只看了榜单。真实企业里这一条常常直接否决掉基准最好的那个。

## 9. 面试口径

**Q：文档解析的主流设计是什么？**
> 分四层看：数字原生直取、管道式、VLM 直出、双后端混合。
> 2026 年的关键变化是管道和 VLM 的界线被溶解了——MinerU2.5 的做法是先用降采样图解码全局布局，
> 再裁剪区域高分重读，把版面检测和识别融进一个模型的两次 pass。
> 所以现在不该问"选哪一代"，该问"双后端怎么路由"。

**Q：为什么不全用 VLM？**
> 四个原因。一是有文字层的 PDF 用直取更快更准，OCR 反而引入错误；二是生成式会幻觉，
> 低容错场景（合同金额、条款编号）需要确定性输出；三是端到端输出无法归因——
> 结果错了你不知道是版面错了、识别错了还是顺序错了，评测就定位不到失败原因；
> 四是我的机器没有 GPU，VLM 在 CPU 上慢到不可用。
> ThoughtWorks 的技术雷达也把 VLM 端到端放在 Assess 阶段，低容错场景仍需混合方案。

**Q：解析质量怎么保证？**
> 先量化再优化。我单独建了 parse_report，除了常规的覆盖率、表格 TEDS、阅读顺序，
> 还加了一个别人不测的指标：页眉页脚残留率。
> 因为页眉重复 200 次会在向量空间形成 200 个几乎相同的点，查询时挤掉真正该召回的内容——
> 这属于"没洗掉"，不是"识别错"，所以特别难查。
> 低分文档进人工复核队列，不阻塞其他文档。

**Q：主力为什么是 Docling 而不是 MinerU？**
> 三个理由，按权重排：许可、格式覆盖、依赖。
> 第一，Docling 是 MIT 无附加条件，MinerU 是 Apache-2.0 加营收门槛条款。
> 第二，Docling 一个引擎吃掉 PDF + DOCX + PPTX + HTML，而 MinerU 只做 PDF——
> 如果让它当主力，Office 格式还得 Docling 补，变成两个引擎都在关键路径上。
> 第三，Docling pip 装完就能跑且吃 CPU，MinerU 依赖重、峰值 3~5GB。
> 准确率上 MinerU 在中文复杂版面上确实更强，这就是我留着它的原因。

**Q：那 MinerU 还留着做什么？**
> 兜底专家。只在三种情况下出现：中文复杂版面（竖排、多栏混排、公式密集、复杂合并单元格）、
> 纯扫描件、或者 Docling 产出过了不质量闸门（表格完整率 < 0.85 或阅读顺序置信度 < 0.7）。
> 关键是它**不在关键路径上**，所以 CPU 慢（2~10 秒/页）、内存高这些缺点都不构成问题——
> 它出现频率低，但每次出现都是 Docling 啃不动的硬骨头。
> 顺带说，它做的两件事大多数工具会跳过：自动页眉页脚移除、跨页表格合并。
> 这两件对检索质量的影响比准确率高 2 分大得多。

**Q：这几个工具是本地部署还是有线上 API？**
> 先分事实和决策。事实是：PyMuPDF、pdfplumber、Camelot 是纯库，**根本没有线上 API**；
> Docling 有 `docling-serve`，但那是自托管 REST，解决"变 HTTP 接口"不解决"没算力"，官方也没有公开 SaaS；
> **只有 MinerU 有官方在线 API**，而且它本地也能跑（管道后端 CPU 可跑）。
> 决策是：**全部走本地**。不是因为云不好，而是本地省掉六件事——不用第三个 key、
> 不受配额约束、原文不出域、断网可演示、成本可预测、出错能断点调试。
> 云唯一的好处是省 3GB 内存，而为这 3GB 放弃上面六条不划算。
> 但我把 `parse_mode: local | hybrid` 做成了配置开关——因为云 API 是异步任务制，
> 和本地库的同步调用模型完全不同，这个约束值得提前写进配置，而不是等要用时再设计。

**Q：全本地的话，资源上要注意什么？**
> 一条硬约束：**MinerU 并发必须锁 1**。它峰值 3~5GB，并发必然 OOM，所以配置里
> `mineru_concurrent: 1` 不是保守，是物理限制。
> 另外它首次运行要下 1~2GB 权重，必须提前预制，否则第一次入库会卡在下载，
> 而且报错信息很不明确——这类"首次使用时才暴露"的问题最浪费时间。
> 剩下都好办：解析是入库时的一次性开销、不在请求链路上，所以 2~10 秒/页的慢
> 不影响问答延迟，睡前跑一批早上收结果。

## 11. 一句话总结（面试用）

> **解析不是选一个工具，是设计一套路由。**
> 有文字层就直取（最快最准），没有就 Docling（MIT、全格式、CPU），啃不动才 MinerU 兜底。
> 主力选 Docling 不是因为它准确率最高，而是因为**它许可干净、一个引擎覆盖全格式、且不在关键路径上带来额外成本**；
> MinerU 留作兜底专家，用它最强的两件事：中文复杂版面和页眉页脚清洗。
> 部署形态也跟着这条分工走：**四个引擎全部本地，`parse_mode` 留一个开关可切 hybrid。**
> 统一 IR 是唯一出口，所以换引擎不用改下游。
